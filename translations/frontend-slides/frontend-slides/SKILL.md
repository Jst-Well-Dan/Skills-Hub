# 前端幻灯片

创建零依赖、富含动画且完全在浏览器中运行的 HTML 演示文稿。

## 核心原则

1. **零依赖** — 使用内联 CSS/JS 的单个 HTML 文件。无需 npm，无需构建工具。
2. **展示，而非描述** — 生成视觉预览，而非抽象选项。人们通过亲眼看到效果来发现自己想要什么。
3. **独特设计** — 拒绝千篇一律的“AI 垃圾感”。每份演示文稿都必须让人感觉是量身定制的。
4. **渐进式披露** — 首先读取轻量级样式索引。对于大胆模板，使用小型预览卡展示样式预览，只有在用户选定该模板后才加载完整的 `design.md`。
5. **固定 16:9 舞台（不可妥协）** — 每个演示文稿均使用 1920×1080 幻灯片画布，并将其作为整体缩放以适配视口。幻灯片在包括手机在内的任何屏幕上都必须保持 16:9。不要为了适配设备而重新排布幻灯片内容。

## 设计美学

你往往会趋向于生成普通、符合常见分布的输出。在前端设计中，这会形成用户所谓的“AI 垃圾感”美学。要避免这一点：打造富有创意、独特且能带来惊喜和愉悦的前端。

重点关注：

- 字体排印：选择美观、独特且有趣的字体。避免 Arial 和 Inter 等普通字体，改用能够提升前端美感的鲜明字体。
- 色彩与主题：坚定采用统一连贯的美学。使用 CSS 变量保持一致性。以主色为核心并搭配鲜明强调色，效果优于怯弱、平均分布的配色。可从 IDE 主题和文化美学中汲取灵感。
- 动效：使用动画营造效果和微交互。对于 HTML，优先使用纯 CSS 方案。React 环境可用时，使用 Motion 库。聚焦高影响力时刻：一次编排良好、采用错落呈现（animation-delay）的页面加载，比零散的微交互更能带来愉悦感。
- 背景：营造氛围和纵深感，不要默认使用纯色。叠加 CSS 渐变、使用几何图案，或添加符合整体美学的情境化效果。

避免常见的 AI 生成式美学：

- 过度使用的字体家族（Inter、Roboto、Arial、系统字体）
- 陈词滥调的配色方案（尤其是白色背景上的紫色渐变）
- 可预测的布局与组件模式
- 缺乏特定情境个性的模板化设计

进行创造性诠释，做出真正贴合情境、出人意料且富有设计感的选择。在明暗主题、不同字体和不同美学之间进行变化。你仍然容易在多次生成中趋向常见选择（例如 Space Grotesk）。务必避免这一点：跳出框架思考至关重要！

## 固定舞台规则

以下不变规则适用于每份演示文稿中的每一张幻灯片：

- 每个演示文稿都要有一个填满浏览器窗口的视口包装器。
- 每张幻灯片都在固定的 1920×1080 舞台内创作。
- 舞台统一缩放以适配视口。可以出现上下黑边或左右黑边，但不得重新布局内容。
- 不要使用响应式断点为手机重新排列幻灯片内容。
- 在 1920×1080 设计尺寸下使用固定的幻灯片内部尺寸。
- 幻灯片可见性必须通过 `.active` / `.visible` 控制，并使用 `viewport-base.css` 中的 `visibility`、`opacity` 和 `pointer-events`。不要使用 `display: none` / `display: block` 切换幻灯片；后续布局类（如 `.slide-content { display: flex; }`）可能覆盖它们，导致所有幻灯片同时可见。
- `clamp()` 仅可用于舞台之外的非幻灯片 UI，或完整舞台不切实际的小型后备预览。
- 包含对 `prefers-reduced-motion` 的支持
- 切勿直接对 CSS 函数取负值（`-clamp()`、`-min()`、`-max()` 会被静默忽略）— 应改用 `calc(-1 * clamp(...))`

**生成时，读取 `viewport-base.css` 并在每份演示文稿中包含其完整内容。**

### 内容密度模式

询问用户这主要是一份用于阅读的演示文稿，还是一份用于演讲的演示文稿，然后围绕其回答进行设计：

| 密度模式 | 最适合 | 设计方式 |
| ------------- | -------- | --------------- |
| **低密度 / 演讲者主导** | 公开演讲、主题演讲式分享、现场讲解 | 每张幻灯片一个观点、大字号、强视觉层级、充足留白、最多 1-3 个要点，需要时增加幻灯片数量 |
| **高密度 / 阅读优先** | 报告、讲义、异步审阅、详细内部文档 | 内容更加自洽的幻灯片、结构化网格/表格/注释，在可读的前提下使用 4-8 个要点或 4-6 张卡片，间距更紧凑但仍经过精心设计 |

基础限制仍然适用：不得滚动、不得溢出、面板不得重叠，文字不得小于舒适阅读尺寸。如果内容超过所选密度模式的容量，应将其拆分到更多幻灯片中，而不是不断缩小直到显得拥挤。

## 阶段 0：检测模式

确定用户想要什么：

- **模式 A：新建演示文稿** — 从零创建。前往阶段 1。
- **模式 B：PPT 转换** — 转换 .pptx 文件。前往阶段 4。
- **模式 C：增强** — 改进现有 HTML 演示文稿。读取它、理解它并进行增强。**遵循下面的模式 C 修改规则。**

### 模式 C：修改规则

增强现有演示文稿时，固定舞台适配是最大的风险：

1. **添加内容之前：** 统计现有元素，并对照密度限制进行检查
2. **添加图片：** 将图片放入 1920×1080 幻灯片画布内。如果幻灯片内容已达上限，则拆分为两张幻灯片
3. **添加文字：** 每张幻灯片最多 4-6 个要点。超过限制？拆分为后续幻灯片
4. **任何修改之后都要验证：** 幻灯片舞台仍保持 16:9、卡片中的文字没有溢出、面板没有重叠，并且在 1280×720 以及一个手机视口下的截图显示正确
5. **主动重组：** 如果修改会导致溢出，自动拆分内容并告知用户。不要等用户提出要求

**向现有幻灯片添加图片时：** 先将图片移到新幻灯片，或减少其他内容。绝不要在未检查现有内容是否已经填满 1920×1080 幻灯片舞台的情况下添加图片。

## 阶段 1：内容探索（新演示文稿）

**一次性提出所有问题**，让用户一次填写完毕。如果当前环境提供原生结构化提问 UI，则使用它；否则，在一条简洁消息中提出问题，并提供编号清晰的选项：

**问题 1 — 用途**（标题："用途"）：
这份演示文稿用于什么场景？选项：推介文稿 / 教学-教程 / 会议演讲 / 内部演示

**问题 2 — 长度**（标题："长度"）：
大约需要多少张幻灯片？选项：短篇 5-10 / 中篇 10-20 / 长篇 20+

**问题 3 — 内容**（标题："内容"）：
你是否已经准备好内容？选项：全部内容已准备好 / 粗略笔记 / 只有主题

**问题 4 — 密度**（标题："密度"）：
演示文稿应该呈现怎样的内容密度？选项：

- "低密度 / 演讲者主导" — 突出核心观点，减少文字，提供更多视觉留白
- "高密度 / 阅读优先" — 提供更多自洽细节，便于异步阅读

**不要在阶段 1 询问内联编辑。** 用户不应在看到草稿前就选择编辑方式。内联编辑是草稿完成后的辅助功能：默认包含该功能，除非用户明确要求锁定文件或仅用于导出。

记住用户的密度选择。它会影响幻灯片数量、字号层级、每张幻灯片的文字量、布局密度，以及是偏向具有电影感的演讲型幻灯片，还是内容自洽的阅读型幻灯片。

如果用户已有内容，请他们分享。

### 步骤 1.2：图片评估（如提供图片）

如果用户选择“无图片” → 跳到阶段 2。

如果用户提供图片文件夹：

1. **扫描** — 列出所有图片文件（.png、.jpg、.svg、.webp 等）
2. **逐张检查图片** — 使用智能体可用的图像理解能力。如果无法读取图片，则使用文件名/元数据，并仅在必要时请用户澄清
3. **评估** — 针对每张图片说明：展示了什么、可用或不可用（附理由）、代表什么概念、主色是什么
4. **共同设计大纲** — 精选图片与文字共同决定幻灯片结构。这不是“先规划幻灯片，再添加图片”，而是从一开始就同时围绕两者进行设计（例如，3 张截图 → 3 张功能幻灯片，1 个徽标 → 标题/结束幻灯片）
5. **确认大纲**，可用时使用相同的结构化提问机制：“这个幻灯片大纲和图片选择是否合适？”选项：看起来不错 / 调整图片 / 调整大纲

**预览中的徽标：** 如果识别出可用徽标，在阶段 2 的每个样式预览中嵌入该徽标（base64）— 让用户看到品牌采用三种不同样式后的效果。

## 阶段 2：样式探索

**这是“展示，而非描述”阶段。** 大多数人无法用语言准确表达设计偏好。

### 步骤 2.0：直接生成 3 个样式预览

根据用途、受众、氛围和内容密度，生成 3 个风格鲜明的单页 HTML 预览，展示字体排印、色彩、动画和整体美学。

不要询问用户是想要多个选项还是预设选择器。默认的探索体验始终是视觉对比。

如果用户已经给出想要的氛围，则采用该氛围。如果没有，则根据场合、受众、内容和重要程度推断可能合适的氛围。各选项之间要有足够差异，让用户能通过视觉做出反应，而不必预先准确描述自己的品味。

如果用户明确指定某个预设或大胆模板，将其作为一个选项，并围绕它生成其余预览选项。

读取 [STYLE_PRESETS.md](STYLE_PRESETS.md) 获取稳妥的预设候选项。如果存在 [bold-template-pack/selection-index.json](bold-template-pack/selection-index.json)，也读取这个紧凑索引，但此时不要读取任何 `design.md` 文件。

| 氛围                | 建议预设                                  |
| ------------------- | -------------------------------------------------- |
| 令人印象深刻/自信 | Bold Signal、Electric Studio、Dark Botanical       |
| 兴奋/充满活力   | Creative Voltage、Neon Cyber、Split Pastel         |
| 平静/专注        | Notebook Tabs、Paper & Ink、Swiss Modern           |
| 鼓舞人心/令人感动      | Dark Botanical、Vintage Editorial、Pastel Geometry |

**预览组合规则：**

- 默认生成 3 个预览：1 个来自 `STYLE_PRESETS.md` 的稳妥预设、至少 1 个来自 `bold-template-pack/selection-index.json` 的大胆模板，以及 1 个自由创意选项。
- 自由创意选项可以是第二个大胆模板，也可以是自行生成的定制设计。选择能够针对用户的场合、受众、氛围和内容形成最强、最有用对比的方案。
- 不要强制所有富有表现力的选项都来自模板库。如果需求简述中存在比现有模板更鲜明、更具体的设计机会，应使用自由创意选项进行自由设计。
- 对于保守或高风险的演示文稿，稳妥预设应格外克制；选择平静、正式程度较高的大胆模板；自由创意选项则应选择另一个克制的模板，或采用权威而非装饰性的定制设计。
- 对于富有表现力的演示文稿，保留稳妥预设作为易读的后备选项；选择一个鲜明的大胆模板；让自由创意选项更具冒险精神、符合具体情境，并与另外两个预览明显不同。
- 如果大胆模板的匹配度不佳，应将自由创意选项用作定制设计，或退回另一个稳妥预设，而不是强行使用模板。

**定制自由创意设计规则：**

- 遵循上面的“设计美学”部分：拒绝常见的“AI 垃圾感”、默认字体/配色/布局选择、白底紫色渐变的陈词滥调，以及千篇一律的仪表盘/卡片式外观。
- 匹配用户所述的场合、受众、氛围/感觉和内容密度。定制设计应让人感觉是专门为这份演示文稿创作的，而不只是“时尚”。
- 提出明确的视觉主张：鲜明的字体排印、坚定的配色、易于识别的布局系统，以及一个强有力的氛围或图形元素。
- 确保它能扩展到完整演示文稿。预览必须体现一个可扩展到章节、内容、引语、对比和结束幻灯片的设计系统。
- 使用固定 1920×1080 舞台规则，并通过与其他选项相同的预览真实性检查。
- 切勿在幻灯片本身呈现 "custom"、"wildcard"、"AI-generated" 或设计过程标签。

**大胆模板选择规则：**

- 根据 `mood`、`tone`、`best_for`、`avoid_for`、`formality`、`density` 和 `scheme` 匹配用户的用途和氛围。
- 将 `best_for` 示例视为参考信号，而非严格的行业筛选条件。
- 确保三个预览彼此真正不同。
- 选择大胆模板候选项后，仅从选择索引中的 `preview_md` 路径读取这些候选项的 `preview.md` 文件。
- `preview.md` 仅用于标题幻灯片预览。在用户选定最终模板之前，不要读取完整的 `design.md` 文件。
- 除非最终选定模板的 `design.md` 缺少关键实现细节，否则不要读取或复制 `template.html`。

**预览真实性规则（不可妥协）：**

- 每个样式预览都必须看起来像用户演示文稿中真实的第一张幻灯片，而不是诊断卡片。
- 切勿在幻灯片上呈现内部工作流文字：不得出现 `preview`、`generated from`、`preview.md`、`template`、`preset`、`style option`、`Option A/B/C`、文件名、路径或源文档标签。
- 切勿在幻灯片本身呈现模板名称或 slug 名称。模板/样式名称只能出现在发给用户的消息中。
- 切勿将用户需求备注呈现为幻灯片内容，例如 "sharp and provocative"、"safe option"、"bold option"、"for internal sharing" 或 "audience: ..."，除非用户明确希望该原句出现在演示文稿中。
- 如果幻灯片需要界面装饰，只使用真实的演示文稿信息：演示文稿标题、章节标题、日期、作者、公司、页码，或来自用户材料的真实内容短语。
- 打开预览之前，检查可见文字；如果出现任何内部元数据，则进行修改。

将预览保存到 `.frontend-slides/slide-previews/`（style-a.html、style-b.html、style-c.html）。每个预览都应自包含且紧凑，展示一张带动画的标题幻灯片。

自动为用户打开每个预览。

### 步骤 2.1：用户选择

询问（标题："样式"）：
你更喜欢哪个样式预览？选项：样式 A：[名称] / 样式 B：[名称] / 样式 C：[名称] / 混合元素

如果选择“混合元素”，询问具体要求。

## 阶段 3：生成演示文稿

使用阶段 1 的内容（纯文字，或文字 + 精选图片）和阶段 2 的样式生成完整演示文稿。

如果提供了图片，步骤 1.2 中的幻灯片大纲已经将其纳入。如果没有，则使用 CSS 生成的视觉元素（渐变、形状、图案）增添视觉趣味 — 这是一条受到完整支持的一等实现路径。

在整个演示文稿中应用用户选择的密度：

- **低密度 / 演讲者主导：** 使用更多幻灯片，并减少每张幻灯片中的观点数量。优先采用大标题、短语、视觉隐喻、章节节奏点、引语/陈述幻灯片，以及适合演讲者的节奏。
- **高密度 / 阅读优先：** 让幻灯片内容更加自洽。使用结构化网格、对比表格、带注释的图示、说明文字和简洁的解释性文案。保持强层级感，让它呈现经过设计的效果，而不是把文档直接粘贴到幻灯片上。

如果用户所述需求混合了两种模式，选择更接近的一种，而不是创造一个中间选项：面向现场受众的说服型演示默认为低密度；用于异步传阅或详细审阅的演示默认为高密度。

绝不要让高密度变成视觉杂乱。如果高密度幻灯片开始溢出，应将其拆分或重新设计为更清晰的结构。

如果用户选择了 `bold-template-pack` 中的大胆模板，在生成前读取该模板的完整 `design.md`。不要读取其他大胆模板。将 `design.md` 视为设计配方：

- 保留其中的字体、配色、装饰语汇、间距节奏和组件语法。
- 无论源模板最初使用 `deck-stage.js` 还是视口流式 CSS，都要将最终演示文稿生成为固定 1920×1080 舞台，并统一缩放以适配视口。
- 将 `design.md` 中的视口流式值视为设计比例，并转换为 1920×1080 舞台坐标。不要在最终演示文稿中将其保留为实时视口重排规则。
- 输出必须保持为单个自包含的 Frontend Slides HTML 文件。
- 不要复制演示幻灯片内容，也不要过于刻板地模仿源模板。
- 仅将 `template.html` 作为最后手段的实现参考，并且只用于已选模板。
- 生成后，通过浏览器渲染截图同时检查内容溢出和面板重叠。仅检查 `scrollHeight` 并不足够，因为网格面板可能在视觉上相互覆盖。

如果用户选择了自行生成的定制自由创意选项，将该预览的 CSS 和布局视为设计配方：

- 保留其中的字体、配色、装饰语汇、间距节奏、网格逻辑和组件语法。
- 将同一视觉系统扩展到完整演示文稿。用户选择定制方向后，不要切换到预设或大胆模板。
- 从该系统中设计缺少的幻灯片布局，而不是从其他样式导入模式。
- 与其他演示文稿一样，保持输出为固定舞台、单文件，并完成视觉验证。

**生成前，读取以下支持文件：**

- [html-template.md](html-template.md) — HTML 架构和 JS 功能
- [viewport-base.css](viewport-base.css) — 强制 CSS（完整包含）
- [animation-patterns.md](animation-patterns.md) — 所选氛围的动画参考

**关键要求：**

- 单个自包含 HTML 文件，所有 CSS/JS 均内联
- 在 `<style>` 块中包含 viewport-base.css 的完整内容
- 使用 Fontshare 或 Google Fonts 中的字体 — 切勿使用系统字体
- 添加详细注释，说明每个部分
- 每个部分都需要清晰的 `/* === SECTION NAME === */` 注释块

## 阶段 6：分享与导出（可选）

交付后，**询问用户：** _“你想分享这份演示文稿吗？我可以将其部署到一个实时 URL（适用于包括手机在内的任何设备），或将其导出为 PDF。”_

选项：

- **部署到 URL** — 可在任何设备上使用的分享链接
- **导出为 PDF** — 适用于电子邮件、Slack 和打印的通用文件
- **两者都要**
- **不用了，谢谢**

如果用户拒绝，则到此停止。如果他们选择一项或两项，则按以下步骤继续。

### 6A：部署到实时 URL（Vercel）

这会将演示文稿部署到 Vercel — 一个免费的托管平台。该链接适用于任何设备（手机、平板电脑、笔记本电脑），并会一直保持在线，直到用户将其下线。

**如果用户从未部署过，请逐步指导：**

1. **检查是否已安装 Vercel CLI** — 运行 `npx vercel --version`。如果未找到，先安装 Node.js（macOS 上运行 `brew install node`，或从 https://nodejs.org 下载）。

2. **检查用户是否已登录** — 运行 `npx vercel whoami`。
   - 如果尚未登录，请解释：_“Vercel 是一项免费托管服务。你需要一个账户才能部署。我来一步步指导你：”_
     - 步骤 1：请用户在浏览器中访问 https://vercel.com/signup
     - 步骤 2：他们可以使用 GitHub、Google 或电子邮件注册 — 选择最方便的方式即可
     - 步骤 3：注册完成后，运行 `vercel login` 并按照提示操作（它会打开浏览器窗口进行授权）
     - 步骤 4：使用 `vercel whoami` 确认登录
   - 等待用户确认已经登录，然后再继续。

3. **部署** — 运行部署脚本：

   ```bash
   bash scripts/deploy.sh <path-to-presentation>
   ```

   该脚本接受文件夹（包含 index.html）或单个 HTML 文件。

4. **分享 URL** — 告知用户：
   - 实时 URL（来自脚本输出）
   - 该链接适用于任何设备 — 可以通过短信、Slack 或电子邮件发送
   - 若以后想将其下线：访问 https://vercel.com/dashboard 并删除项目
   - Vercel 免费套餐额度充足 — 他们不会被收费

**⚠ 部署注意事项：**

- **本地图片/视频必须与 HTML 一同部署。** 部署脚本会自动检测 HTML 中通过 `src="..."` 引用的文件并将其打包。但如果演示文稿通过 CSS `background-image` 或非常规路径引用文件，脚本可能无法检测到。**部署前请验证：** 打开已部署的 URL，检查所有图片是否正常加载。如果有图片损坏，最稳妥的修复方法是将 HTML 及其全部资源放入同一个文件夹，然后部署该文件夹，而不是部署单独的 HTML 文件。
- **演示文稿包含大量资源时，优先部署文件夹。** 如果演示文稿位于一个包含同级图片的文件夹中（例如 `my-deck/index.html` + `my-deck/logo.png`），应直接部署该文件夹：`bash scripts/deploy.sh ./my-deck/`。这比部署单个 HTML 文件更可靠，因为整个文件夹内容会按原样上传。
- **带空格的文件名可以使用，但可能引发问题。** 脚本可以处理文件名中的空格，但 Vercel URL 会将空格编码为 `%20`。如果可以，请避免在图片文件名中使用空格。如果用户的图片名包含空格，脚本会进行处理；但如果图片仍无法正常显示，解决办法是将文件名中的空格改为连字符。
- **重新部署会更新同一个 URL。** 对同一演示文稿再次运行部署脚本会覆盖此前的部署。URL 保持不变 — 无需分享新链接。

### 6B：导出为 PDF

该流程会将每张幻灯片捕获为截图，并将它们合并为 PDF。非常适合作为电子邮件附件、嵌入文档或打印。

**注意：** 动画和交互不会被保留 — PDF 是静态快照。这是正常且符合预期的；请告知用户，以免他们感到意外。

1. **运行导出脚本：**

   ```bash
   bash scripts/export-pdf.sh <path-to-html> [output.pdf]
   ```

   如果未提供输出路径，PDF 将保存在 HTML 文件旁边。

2. **后台处理过程**（向用户简要说明）：
   - 无头浏览器以 1920×1080（标准宽屏）打开演示文稿
   - 逐张截取每张幻灯片
   - 将所有截图合并为一个 PDF
   - 脚本需要 Playwright（一种浏览器自动化工具）— 如果缺失，它会自动安装

3. **如果 Playwright 安装失败：**
   - 最常见的问题是 Chromium 下载失败。运行：`npx playwright install chromium`
   - 如果仍然失败，可能是网络/防火墙问题。请用户尝试更换网络。

4. **交付 PDF** — 脚本会自动打开它。告知用户：
   - 文件位置和大小
   - 它可以在任何地方使用 — 电子邮件、Slack、Notion、Google Docs、打印
   - 动画会被替换为其最终视觉状态（仍然美观，只是静态呈现）

**⚠ PDF 导出注意事项：**

- **首次运行较慢。** 脚本会安装 Playwright，并将 Chromium 浏览器（约 150MB）下载到临时目录。每次运行只会执行一次。提醒用户首次运行可能需要 30-60 秒 — 同一会话中的后续导出会更快。
- **幻灯片必须使用 `class="slide"`。** 导出脚本通过查询 `.slide` 元素来查找幻灯片。如果演示文稿使用其他类名，脚本会报告 "0 slides found" 并失败。此技能生成的所有演示文稿都使用 `.slide`，因此这只会影响外部创建的 HTML。
- **本地图片必须能够通过 HTTP 加载。** 脚本会启动本地服务器并通过该服务器加载 HTML（以便 Google Fonts 和相对图片路径正常工作）。如果图片使用绝对文件系统路径（例如 `src="/Users/name/photo.png"`），而不是相对路径（例如 `src="photo.png"`），则无法加载。生成的演示文稿始终使用相对路径，但转换而来或用户提供的演示文稿可能不是 — 请根据需要检查并修复。
- **只要本地图片位于 HTML 文件所在目录中（或相对于该目录），它们就会出现在 PDF 中。** 导出脚本通过 HTTP 提供 HTML 的父目录，因此 `src="photo.png"` 等相对路径可以正确解析 — 包括带空格的文件名。如果图片仍未出现，请检查：(1) 图片文件是否确实存在于引用路径，(2) 路径是否为相对路径，而不是 `/Users/name/photo.png` 之类的绝对文件系统路径。
- **大型演示文稿会生成较大的 PDF。** 每张幻灯片都会被捕获为完整的 1920×1080 PNG 截图。一份包含 18 张幻灯片的演示文稿可能生成约 20MB 的 PDF。如果 PDF 超过 10MB，请询问用户：_“PDF 大小为 [size]。需要我压缩它吗？画面会略微降低清晰度，但文件会小很多。”_ 如果用户同意，使用 `--compact` 标志重新运行导出：
  ```bash
  bash scripts/export-pdf.sh <path-to-html> [output.pdf] --compact
  ```
  这会以 1280×720 而不是 1920×1080 进行渲染，通常可以将文件大小减少 50-70%，且视觉差异很小。

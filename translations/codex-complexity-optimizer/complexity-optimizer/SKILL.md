# 复杂度优化器

## 核心规则

仅在理解并能够保留当前行为时进行优化。相比正确性不明确的大规模重写，应优先选择经过测试验证的小幅改进。

## 默认行为

当用户要求分析、扫描、审计、审查代码库或“给我一份报告”时，自动生成完整的复杂度报告。无需用户指定报告字段。

默认报告内容：

- 已分析的范围以及检测到的技术栈/测试命令。
- 按可能影响从高到低排列的主要发现。
- 每项发现对应的文件和行号。
- 当前模式以及其成本可能较高的原因。
- 估算的当前复杂度。
- 建议的更改。
- 更改后的估算复杂度。
- 风险级别。
- 所需的测试、基准测试或手动检查。
- 明确说明未修改任何文件，除非用户明确要求实施更改。

仅当用户要求实施、修复、优化、应用、更改、重构，或以其他方式明确要求修改代码时，才编辑文件。如果用户仅要求分析或报告，请勿修改文件。

## 工作流程

1. 建立基线：
   - 确定语言、框架、测试命令、构建命令和性能敏感路径。
   - 在修改代码之前检查现有测试。
   - 扫描代码仓库时，运行 `scripts/analyze_complexity.py <repo>` 获取第一轮热点列表。

2. 对优化机会进行排序：
   - 优先处理热路径、大输入量路径、渲染循环、数据库/API 循环和共享工具中的代码。
   - 区分算法复杂度问题与常数因子层面的清理。
   - 不要修补每条警告。将扫描器输出视为线索，而不是证据。
   - 对于仅要求报告的请求，应检查足够多的相关上下文代码，以估算当前复杂度和建议方案的复杂度；不要止步于原始扫描器输出。

3. 证明行为：
   - 找到或添加针对待更改函数/组件的聚焦测试。
   - 覆盖边界情况：空输入、重复项、排序稳定性、null/缺失值、错误、权限、分页、时区和修改操作的副作用。
   - 如果缺少测试且行为存在歧义，请进行最小范围的重构，或在更改语义前询问预期行为。

4. 保守优化：
   - 当键的相等性稳定时，使用 map/set 替代重复的线性查找。
   - 仅在数据形态适合时，使用索引、分组、双指针扫描、扫描线逻辑、二分查找、记忆化、批处理或预计算替代嵌套扫描。
   - 在 UI 代码中，通过稳定的 props、记忆化派生数据、虚拟化、防抖处理以及将高成本工作移出渲染路径来减少不必要的渲染。
   - 在数据访问代码中，通过批量获取、join、预加载、缓存或批处理消除 N+1 行为，同时保留授权和过滤逻辑。

5. 验证：
   - 运行相关测试以及类型检查/lint/构建命令。
   - 当复杂度改进不明显或性能至关重要时，添加微基准测试或测量。
   - 报告原始复杂度、新复杂度、已更改文件、运行的测试以及任何残余风险。

## 第一轮扫描器

使用技能目录中随附的扫描器：

```bash
python3 scripts/analyze_complexity.py /path/to/repo --format markdown
python3 scripts/analyze_complexity.py /path/to/repo --format json
```

该扫描器会标记 Python、JavaScript、TypeScript、JSX/TSX、Java、Go、C、C++、C#、Ruby、PHP 和 Swift 文件中的常见模式。它有意优先提供易于理解的线索，而不是追求完美的静态分析。

如果扫描器没有报告任何内容，仍应手动检查已知热路径。渲染抖动、数据库查询模式和框架生命周期问题通常需要结合具体代码仓库的上下文进行判断。

## 优化安全检查清单

编辑前：

- 确认数据规模足够大，复杂度优化确实有意义。
- 确认优化保留了调用方可能依赖的输出顺序。
- 确认对象标识、可变性和引用共享不属于公开行为的一部分。
- 确认缓存具有有效的失效策略。
- 确认去重不会合并显示标签相同但实际不同的记录。
- 确认数据库批处理保留租户、权限、软删除、分页和排序约束。

编辑后：

- 先运行范围较小的测试，再运行覆盖范围最广的相关测试/构建命令。
- 如果已有或新增了基准测试，请比较优化前后的基准测试数据。
- 保持补丁范围集中。避免对无关文件造成格式变动。

# Markdown 格式化器

将纯文本或 Markdown 转换为结构清晰、便于阅读的 Markdown。目标是在不改变任何原始内容的前提下，帮助读者快速掌握要点、重点和结构。

**核心原则**：仅调整格式并修复明显的错别字。绝不添加、删除或改写内容。

## 用户输入工具

当此技能需要向用户提问时，请遵循以下工具选择规则（按优先级排序）：

1. **优先使用内置用户输入工具**，即当前智能体运行时公开的工具，例如 `AskUserQuestion`、`request_user_input`、`clarify`、`ask_user` 或任何等效工具。
2. **后备方案**：如果不存在此类工具，则输出带编号的纯文本消息，并要求用户针对每个问题回复所选编号或答案。
3. **批量提问**：如果工具支持每次调用提出多个问题，则将所有适用问题合并到一次调用中；如果仅支持单个问题，则按优先级逐一提问。

下文中具体的 `AskUserQuestion` 引用仅为示例——在其他运行时中，请替换为本地等效工具。

## 脚本目录

脚本位于 `scripts/` 子目录中。`{baseDir}` = 此 SKILL.md 所在目录的路径。解析 `${BUN_X}` 运行时：如果已安装 `bun` → `bun`；如果 `npx` 可用 → `npx -y bun`；否则建议安装 bun。将 `{baseDir}` 和 `${BUN_X}` 替换为实际值。

| 脚本 | 用途 |
|--------|---------|
| `scripts/main.ts` | 带 CLI 选项的主入口点（使用 remark-cjk-friendly 处理 CJK 强调格式） |
| `scripts/quotes.ts` | 将 ASCII 引号替换为全角引号 |
| `scripts/autocorrect.ts` | 通过 autocorrect 添加 CJK/英文间距 |

## 偏好设置（EXTEND.md）

按以下优先级顺序检查 EXTEND.md——找到的第一个文件生效：

| 优先级 | 路径 | 作用域 |
|----------|------|-------|
| 1 | `.baoyu-skills/baoyu-format-markdown/EXTEND.md` | 项目 |
| 2 | `${XDG_CONFIG_HOME:-$HOME/.config}/baoyu-skills/baoyu-format-markdown/EXTEND.md` | XDG |

**EXTEND.md 支持以下设置**：

| 设置 | 值 | 默认值 | 说明 |
|---------|--------|---------|-------------|
| `auto_select` | `true`/`false` | `false` | 跳过标题和摘要选择，自动选取最佳结果 |
| `auto_select_title` | `true`/`false` | `false` | 仅跳过标题选择 |
| `auto_select_summary` | `true`/`false` | `false` | 仅跳过摘要选择 |
| 其他 | — | — | 默认格式化选项、排版偏好 |

## 用法

工作流分为两个阶段：先**分析**（理解内容），再**格式化**（应用格式）。Claude 负责内容分析和格式化（步骤 1-5），然后运行脚本修复排版问题（步骤 6）。

## 工作流

### 步骤 1：读取并检测内容类型

读取用户指定的文件，然后检测内容类型：

| 指示特征 | 分类 |
|-----------|----------------|
| 包含 `---` YAML frontmatter | Markdown |
| 包含 `#`、`##`、`###` 标题 | Markdown |
| 包含 `**粗体**`、`*斜体*`、列表、代码块、引用块 | Markdown |
| 以上均无 | 纯文本 |

**如果检测到 Markdown，请使用 `AskUserQuestion` 询问：**

```
检测到现有 Markdown 格式。你希望如何处理？

1. 优化格式（推荐）
   - 分析内容，改善标题、粗体和列表，以提升可读性
   - 运行排版脚本（间距、强调格式修复）
   - 输出：{filename}-formatted.md

2. 保留原始格式
   - 保留现有 Markdown 结构
   - 仅运行排版脚本
   - 输出：{filename}-formatted.md

3. 仅修复排版
   - 直接在原文件上运行排版脚本
   - 不创建副本，直接修改原文件
```

**根据用户的选择：**
- **优化**：继续执行步骤 2（完整工作流）
- **保留原始格式**：跳至步骤 5，复制文件，然后执行步骤 6
- **仅修复排版**：跳至步骤 6，直接在原文件上运行

### 步骤 2：分析内容（读者视角）

仔细阅读全部内容。从读者的角度思考：怎样才能帮助他们快速理解并记住关键信息？

分析应涵盖以下维度：

**2.1 重点与关键洞见**
- 作者提出的核心论点或结论
- 令人意外的事实、数据点或反直觉观点
- 令人印象深刻的引语或措辞精彩的句子（金句）

**2.2 结构评估**
- 内容是否具有清晰的逻辑脉络？具体是什么？
- 是否存在缺少标题的自然章节边界？
- 是否存在大段连续文本，可以通过视觉分隔改善阅读体验？

**2.3 对读者重要的信息**
- 可操作的建议或要点
- 关键概念的定义和解释
- 隐藏在段落中的列表或列举内容
- 以表格呈现会更清晰的比较或对照

**2.4 格式问题**
- 标题层级缺失或不一致
- 一个段落中混合了多个主题
- 并列项目以段落形式书写，而非列表
- 代码、命令或技术术语未标记为代码
- 明显的错别字或格式错误

**将分析保存到文件**：`{original-filename}-analysis.md`

分析文件是步骤 3 的蓝图。使用以下格式：

```markdown
# 内容分析：{filename}

## 重点与关键洞见
- [列出发现]

## 结构评估
- 当前脉络：[描述]
- 建议章节：[列出候选标题并简述理由]

## 对读者重要的信息
- [列出可操作事项、关键概念、隐藏的列表、潜在表格]

## 格式问题
- [列出具体问题及其位置引用]

## 发现的错别字
- [列出所有明显的错别字及修正内容，或填写“未发现”]
```

### 步骤 3：检查或创建 Frontmatter、标题和摘要

检查 YAML frontmatter（`---` 块）。如果缺失，则创建。

| 字段 | 处理方式 |
|-------|------------|
| `title` | 参见下方的**标题生成** |
| `slug` | 从文件路径推断，或根据标题生成 |
| `summary` | 一句话的简洁摘要（参见下方的**摘要生成**） |
| `description` | 更详细的描述性摘要（参见下方的**摘要生成**） |
| `coverImage` | 检查同一目录中是否存在 `imgs/cover.png`；如果存在，则使用相对路径 |

#### 标题生成

无论是否已存在标题，除非设置了 `auto_select_title`，否则都要运行标题优化流程。

**准备工作**——阅读完整文本并提取：
- 核心论点（一句话：“这篇文章讲什么？”）
- 最有影响力的观点或结论
- 读者痛点或好奇心触发点
- 最令人印象深刻的比喻或金句

使用 `references/title-formulas.md` 中的公式**生成候选标题**：

1. 根据文章的内容、语气和结构，选择**最匹配的 2-3 个钩子公式**（参见参考资料中的“When to pick each formula”）
2. 生成 **1-2 个直白标题**（描述性或陈述性，不使用公式——清晰且准确）
3. 如果用户指定了方向（例如“让它更有悬念”），优先遵循该方向
4. 总计：**4-5 个候选标题**

通过 `AskUserQuestion` 展示：

```
请选择一个标题：

1. [钩子标题 A] —（推荐）[公式名称]
2. [钩子标题 B] — [公式名称]
3. [钩子标题 C] — [公式名称]
4. [直白标题 D] — 直白
5. [直白标题 E] — 直白

输入编号，或输入自定义标题：
```

将最有力的钩子标题放在首位，并标记为 `(recommended)`。有关原则和禁止使用的模式，请参阅 `references/title-formulas.md`。

如果第一行是 H1，请将其提取到 frontmatter 中，并从正文中移除。如果 frontmatter 已包含 `title`，将其作为上下文参考，但仍需生成新的候选标题——现有标题可能不够有力。

**跳过行为**：如果 `auto_select: true` 或 `auto_select_title: true`，则跳过用户提示，直接使用排名第一的候选标题。

#### 摘要生成

直接生成两个版本（无需用户选择），并将二者都存储在 frontmatter 中：

| 字段 | 长度 | 用途 |
|-------|--------|---------|
| `summary` | 1 句话，约 50-80 个字符 | 简洁的钩子——用于信息流、社交分享、SEO 元数据 |
| `description` | 2-3 句话，约 100-200 个字符 | 更丰富的上下文——用于文章预览、新闻简报文案 |

**原则**：

- 向读者传达**核心价值**，而不仅仅是主题
- 优先使用具体细节（数字、结果、具体方法），避免模糊描述
- `summary` 应有冲击力且内容完整；`description` 可以通过补充细节进一步展开
- 如果 frontmatter 已包含 `summary` 或 `description`，则保留现有内容，只生成缺失的字段

**禁止使用的模式**：

- “本文介绍了……”“本文探讨了……”
- 只有主题描述，没有价值主张
- 用不同措辞重复标题

标题写入 frontmatter 后，正文中不应再包含 H1（避免重复）。

### 步骤 4：格式化内容

根据步骤 2 的分析应用格式。目标是使内容便于快速浏览，并让关键要点不容错过。

**格式化工具箱：**

| 元素 | 使用时机 | 格式 |
|---------|-------------|--------|
| 标题 | 自然的主题边界、章节分隔 | `##`、`###` 层级 |
| 粗体 | 关键结论、重要术语、核心要点 | `**粗体**` |
| 无序列表 | 并列项目、功能列表、示例 | `- 项目` |
| 有序列表 | 连续步骤、排名项目、操作流程 | `1. 项目` |
| 表格 | 比较、结构化数据、选项矩阵 | Markdown 表格 |
| 代码 | 命令、文件路径、技术术语、变量名 | `` `行内代码` `` 或围栏代码块 |
| 引用块 | 值得注意的引语、重要警告、引用文本 | `> 引用` |
| 分隔线 | 主要主题之间的过渡 | `---` |

**格式化原则——不要做什么：**
- 不要添加句子、解释或评论
- 不要删除或缩短任何内容
- 不要重新措辞或改写作者原文
- 不要添加带有主观评价的标题（例如“惊人发现”——应使用中性的描述性标题）
- 不要过度格式化：并非每句话都需要加粗，也并非每个段落都需要标题

**格式化原则——应该做什么：**
- 保留作者的表达风格、语气和每一个字
- **加粗关键结论和核心要点**——即读者会标记出来的句子
- 仅当并列结构明确存在时，才将段落中的并列项目提取为列表
- 在主题确实发生转换的位置添加标题——优先使用生动、具体的标题，而非泛泛的标题（例如使用“3 天搞定 vs 传统方案”，而非“方案对比”）
- 使用表格呈现隐藏在段落中的比较或结构化数据
- 使用引用块呈现金句、令人印象深刻的陈述或重要警告
- 修复明显的错别字（依据步骤 2 的发现）

### 步骤 5：保存格式化文件

另存为 `{original-filename}-formatted.md`

**备份现有文件：**

```bash
if [ -f "{filename}-formatted.md" ]; then
  mv "{filename}-formatted.md" "{filename}-formatted.backup-$(date +%Y%m%d-%H%M%S).md"
fi
```

### 步骤 6：执行排版脚本

在输出文件上运行格式化脚本：

```bash
${BUN_X} {baseDir}/scripts/main.ts {output-file-path} [options]
```

**脚本选项：**

| 选项 | 简写 | 说明 | 默认值 |
|--------|-------|-------------|---------|
| `--quotes` | `-q` | 将 ASCII 引号替换为全角引号 `"..."` | false |
| `--no-quotes` | | 不替换引号 | |
| `--spacing` | `-s` | 通过 autocorrect 添加 CJK/英文间距 | true |
| `--no-spacing` | | 不添加 CJK/英文间距 | |
| `--emphasis` | `-e` | 修复 CJK 强调格式中的标点问题 | true |
| `--no-emphasis` | | 不修复 CJK 强调格式问题 | |

**示例：**

```bash
# 默认：启用间距和强调格式修复，禁用引号替换
${BUN_X} {baseDir}/scripts/main.ts article.md

# 启用所有功能，包括引号替换
${BUN_X} {baseDir}/scripts/main.ts article.md --quotes

# 仅修复强调格式问题，跳过间距处理
${BUN_X} {baseDir}/scripts/main.ts article.md --no-spacing
```

**脚本执行以下操作（取决于选项）：**
1. 修复 CJK 强调/粗体格式中的标点问题（默认：启用）
2. 通过 autocorrect 添加 CJK/英文混排间距（默认：启用）
3. 将 ASCII 引号替换为全角引号（默认：禁用）
4. 格式化 frontmatter YAML（始终启用）

### 步骤 7：完成报告

显示一份报告，总结所做的全部更改：

```
**格式化完成**

**文件：**
- 分析：{filename}-analysis.md
- 格式化结果：{filename}-formatted.md

**内容分析摘要：**
- 发现的重点：X 个关键洞见
- 金句：X 个令人印象深刻的句子
- 已修复的格式问题：X 项

**已应用的更改：**
- Frontmatter：[已添加/已更新]（title、slug、summary）
- 添加的标题：X 个（##：N，###：N）
- 添加的粗体标记：X 个
- 创建的列表：X 个（从段落 → 列表转换）
- 创建的表格：X 个
- 添加的代码标记：X 个
- 添加的引用块：X 个
- 修复的错别字：X 个 [逐项列出：“原文” → “修正后”]

**排版脚本：**
- CJK 间距：[已应用/已跳过]
- 强调格式修复：[已应用/已跳过]
- 引号替换：[已应用/已跳过]
```

根据实际更改调整报告——省略未发生更改的类别。

## 注意事项

- 保留原始写作风格和语气
- 为代码块指定正确的语言（例如 `python`、`javascript`）
- 遵循 CJK/英文间距规范
- 分析文件是一份工作文档——它有助于确保发现的问题与实际格式化结果保持一致

可通过 EXTEND.md 进行自定义配置。有关路径和支持的选项，请参阅**偏好设置**部分。

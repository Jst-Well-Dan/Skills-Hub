# 归藏社交卡片技能

为小红书/Rednote、微信公众号、文章封面和平台缩略图创建精致的社交卡片套件。

本技能自成一体。它借鉴归藏 PPT 风格系统的视觉原则，但不得编辑原始 PPT 技能及其模板或参考资料。如果原始 PPT 技能可用，可以读取它，但只能用于参考。

生成的内容必须存放在任务文件夹中，而不是技能根目录中。默认使用本仓库内的 `local-tests/<slug>/`，或者使用用户明确要求的输出文件夹。不要创建 `social-card-*`、`livephoto-*`、`wechat-*`、`output/` 等根级任务文件夹，也不要在 `SKILL.md` 旁边放置零散的渲染资源。

## 需要生成的内容

本技能适用于：

- 社交卡片/轮播图组：封面加内容页，尤其是小红书/Rednote 3:4 图片。
- 当用户要求 Live Photo / 实况照片并提供视频证据或屏幕录制时，制作简短的实况照片动态卡片。
- 当用户拥有高质量视频素材，并希望制作几乎不添加或完全不添加文字的单视频、二宫格、三宫格或四宫格动态卡片时，制作素材优先的实况照片拼图布局。
- 当用户有三个短视频、三个结果、三个视角，或希望把高信息密度的对比保留在一个图卡单元中时，制作三连实况照片拼图。
- 实况照片的长视频输入处理：判断应当裁剪、加速、拆分成三连拼图，还是在渲染前向用户询问具体时间范围。
- 微信公众号封面组合：一个 `21:9` 主封面加一个 `1:1` 方形封面，并在同一个 HTML 中组合展示以供视觉检查。
- 截图较多的产品帖子、文章封面、教程轮播图、户外/生活方式笔记、AI/产品更新解读。
- 需要归藏风格瑞士式或编辑杂志式布局的社交图片。

本技能不适用于：

- 完整幻灯片或横向 PPT 网站。此类任务请使用 PPT 技能。
- 长篇视频生成。此类任务请使用视频技能。本技能只支持使用视频替换静态图片槽位、受布局约束的简短实况照片卡片。
- 不涉及布局或文章提取需求的纯图片编辑。

### Rednote 类目能力范围（能力圈）

最常见的 11 个 Rednote（小红书）类目分为三组。逐项方案路由请参阅 `references/category-cookbook.md`。

**具备较强的端到端能力**（文字、结构和图片叙事均在能力范围内）：

- 旅行 (Travel)、职场 (Workplace)、推荐 (Recommended，需先明确子类型)。

**文字和结构能力较强；图片需要由用户提供或来自素材库：**

- 游戏 (Game)、影视 (Film/TV)、美食 食谱方向 (Food — recipes only)、彩妆 教程方向 (Makeup — tutorials only)、健身 (Fitness)、家居 (Home)、穿搭 精选方向 (Outfit — capsule/essay only)。

**超出范围——应诚实说明限制，而不是承诺结果：**

- 美食 菜品大片摆盘 (food-photography showcase)。
- 穿搭 日常 OOTD 全身 (daily OOTD body shots; we cannot generate or simulate)。
- 情感 梦核 / 氛围感装饰风 (dreamcore / aesthetic-light styling — clashes with both Editorial and Swiss)。
- Y2K / 千禧辣妹 / 哥特萝莉 / kawaii decorated aesthetics。
- 图片本身就是全部交付物的纯摄影展示帖。

当请求落入第三组时，应在接收需求时明确指出无法完成的内容——不要悄悄套用不符合用户意图的布局。

## 核心原则

表达优先。目标不是把文字硬塞进海报，而是把原始素材转化为清晰的视觉论点。

对每一页，都要判断：

- 浏览者应当在一眼之内理解什么？
- 哪些证据、截图或图片能够支持它？
- 哪些文字必须放大，哪些可以变成说明文字或元数据？
- 哪些内容可以删除，因为它们属于帖子正文，而不是图片？

## 工作流程

### 1. 接收需求

只收集会改变输出结果的缺失信息：

- 目标平台和比例。
- 原始文本、字幕、文章或标题。
- **Rednote 类目**——如果用户指定了 11 个常见类型之一（旅行 / 职场 / 游戏 / 影视 / 美食 / 彩妆 / 穿搭 / 家居 / 健身 / 情感 / 推荐），通过 `references/category-cookbook.md` 路由，以找到正确方案并确认请求是否位于能力圈内（参见上方的 “Rednote Category Capability”）。如果请求落入超出范围的分组，应在设计**之前**告知用户，不要悄悄套用其他方案。
- 用户提供的图片/截图，以及每张图片应出现的位置。**对于 News / Tutorial / Data / Review 内容，应主动询问用户是否有截图或照片**——它们构成证据层。没有真实材料的海报往往会显得空洞。
- 如果用户要求实况照片，则确认其提供的视频素材。将用户提供的视频视为正常路径；来自网络的免费视频仅用于演示/推广场景，或用户明确要求获取外部素材时使用。确认目标平台，因为时长不同：小红书支持 `5s`；微信公众号实况照片应保持为 `3s`，且必须通过 iPhone 上传。裁剪前，读取 `references/live-photo-production.md`，并将请求归类为单个实况照片、三连拼图或长视频输入处理。如果源视频过长或包含多个可用时刻，应先进行低成本诊断，然后只询问一次用户是希望裁剪、加速、拆分到多个视频槽，还是使用用户指定的时间范围。如果源视频短于目标时长，询问用户是提供更长的片段、接受更短的实况照片，还是明确允许定格/慢放。如果重要焦点不明确，可以提出可能的裁剪/放大选项，但应由用户在执行前决定。
- **如果用户只提供了文字（完全没有图片），设计前询问一次：**

  ```
  这篇我需要 1-2 张图。三种走法：
  A. 你自己有照片 / 截图，传给我（推荐——最不"AI 感"）
  B. 我去 Pexels / Unsplash / Flickr 帮你找
  C. 用 AI 生成
  ```

  用一句话推荐 A——自己的照片能让海报看起来不像 AI 生成。接受用户的任何选择（包括“都行你看着办”）并继续。**之后不要再次询问，也不要在多个回合中不断引导用户选择 A。**这个问题只问一次。
- 用户指定的首选风格：Swiss Style、杂志/编辑式、科技、户外等。
- 硬性限制：标题文字、`1:1` 封面不使用图片、必须包含硬件照片、保持截图可读等。

如果用户已经提供了足够的上下文，应基于合理假设继续。

如果内容涉及当前产品发布、政策、价格、声明或新闻，应通过浏览验证不稳定事实，并在最终回复中引用来源。

### 2. 提取故事

设计之前，先把原始素材转化为页面计划。

对于 Rednote：

- 第 1 页是封面钩子。
- 第 2-N 页每页只承载一个观点。
- 大多数帖子使用 5-9 页。当页面下方变得空旷时，应压缩内容或合并页面。
- 细节留在帖子正文中；图片应承载钩子、对比、清单和鲜明结论。

对于微信：

- 始终生成成对系统：`21:9` 主封面和 `1:1` 方形封面。
- 在同一个 HTML 文件中构建两个封面，并添加组合预览区域，以便一起检查它们的视觉关系。
- `21:9` 保留完整或接近完整的标题、副标题和一个强烈的视觉关系。
- `1:1` 使用从长标题提炼出的简短标题：大号居中文字，默认不使用图片，也不塞入拥挤的副标题。

### 3. 选择风格模式

每套内容选择一种模式。**这两个系统并不与特定内容类型绑定**——改变的是视觉立场，而不是可以讨论的话题。职场文章可以采用 Editorial；旅行账本也可以采用 Swiss。应根据希望营造的感受选择，而不是按类目查表。

**Editorial Magazine x E-ink** 包含：

- 衬线体/宋体展示文字 + 安静的无衬线正文，以及纸张 + 墨水配色。
- 暖色纸张底色上的氛围层（纸张颗粒/水墨晕染/WebGL 画布）。
- 账本式行列、旁注、引语和大幅图片槽——营造杂志专题感。
- 适合希望页面呈现舒缓、克制、手工排版质感的场景。

**Swiss International** 包含：

- Inter / Helvetica 气质，大字号展示文字使用很细的字重，小字号标签使用等宽字体。
- 严格左对齐的网格、发丝线和一种高饱和强调色。
- 卡片填充矩阵、KPI 塔、横向条形图、编号陈述——营造系统化/数据化质感。
- 适合希望页面显得经过工程设计、量化明确、果断有力的场景。

如果两种风格都适用于某项内容，问题就变成编辑意图：“这是专题故事还是发布说明？”决定模式的是这一点，而不是主题本身。

除非用户明确要求混合风格，否则不要在同一图组中混用两个视觉系统。

然后选择一个主题：

- Editorial Magazine x E-ink 使用六种杂志配色之一：Ink Classic、Indigo Porcelain、Forest Ink、Kraft Paper、Dune 或 Midnight Ink（唯一的深色变体；仅用于游戏主视觉/夜景摄影/电影感封面）。
- Swiss International 使用四种强调色方案之一：IKB Blue、Lemon Yellow、Lemon Green 或 Safety Orange。

精确 CSS 令牌请读取 `references/theme-presets.md`。除非用户有严格的品牌要求，否则不要自行创造任意颜色。

### 4. 规划页面

创建简洁的内部计划：

```text
Page 01 / cover / hook / image source / layout intent
Page 02 / point / key copy / visual evidence / layout intent
...
```

当用户要求审批时，应在渲染前展示此计划。否则将其作为内部计划并继续执行。

使用 `references/layout-recipes.md` 选择页面结构。避免每一页都重复使用“标题加卡片”布局。

对于 3:4 图片，编码前检查 `references/portrait-fill.md`。简短表格或账本必须扩展成完整的竖版构图，可以加入引语栏、图片证据、旁注、更大的行高或背景主视觉区域。

面向受众的文案必须描述用户的真实场景，而不是制作方法。`3s`、`5s`、`Live Photo`、`triple collage`、`information budget`、`long-video intake`、`speed-up`、`highlight detection`、`one action point` 或 `layout template` 等内部术语可以指导规划、文件命名、QA 备注和交付摘要，但不得成为 H1、钩子或正文主体，除非用户明确要制作介绍这些概念的教学帖子。渲染之前，以真实浏览者的身份重新阅读每一条可见标题：如果它听起来像任务要求，就替换为具体场景文案。

不要仅为了满足自动密度警告而添加模板之外的装饰。额外标尺、侧边栏、伪时间轴、装饰标签或虚构徽章必须来自现有布局方案或用户要求。如果出现密度警告，应通过选择更合适的方案、调整真实内容大小，或基于视觉理由接受提示性警告来解决；不要在卡片上添加毫无意义的 UI。

对于实况照片卡片，先把它们作为普通社交卡片进行规划，再决定动态内容的作用：一个动作点、一个小流程、前后变化、三个并行结果，或氛围/证据。唯一的结构变化是一个或多个图片槽变成视频槽。保持相同的比例、裁剪、安全区域、排版和风格模式规则；将静态图片的裁剪逻辑应用于视频流。第一帧必须通过与静态图片相同的检查：不得过度裁剪，关键 UI/内容仍然可读，卡片仍遵循所选布局方案。渲染前读取 `references/live-photo-production.md`。

对于素材优先的实况照片拼图卡片，应让视频素材主导。少用或不用文案：单视频封面使用一个短标题就够了，二宫格/三宫格/四宫格版本通常不应添加文字。当单视频封面在视频画面上叠加文字时，使用 M16 Image-Led Cover / 图上文字规则：先进行主体映射，选择安全安静区，Editorial 衬线体/宋体标题使用常规至中等字重，文字使用纸张奶油色，默认不使用覆盖整个画布的遮罩。不要为了让叠加层显得经过设计而虚构额外的引题、元信息、发丝线、标签、标尺、徽章、副标题或解释制作流程的术语。如果只有一个标题，就让排版本身承担布局作用：根据短语换行，克制地处理字号、字距、对齐和位置。将源视频中已有的文字视为画面的一部分；除非用户要求，否则只需避免添加新文字。

### 4.5. 复制种子模板

不要从头编写 HTML。根据第 3 步选择的风格模式挑选一个种子模板：

- Editorial Magazine × E-ink → 将 `assets/template-editorial-card.html` 复制到任务文件夹并命名为 `index.html`。
- Swiss International → 将 `assets/template-swiss-card.html` 复制到任务文件夹并命名为 `index.html`。

种子模板已经接入：字体加载、主题令牌、全部三种海报尺寸（`.poster.xhs` / `.poster.square` / `.poster.wide`）、组合预览框架、颗粒/背景层，以及布局方案引用的全部类定义。

在 `<html>` 元素上设置主题/强调色：

- Editorial：`<html data-theme="ink-classic | indigo-porcelain | forest-ink | kraft-paper | dune | midnight-ink">`。
- Swiss：`<html data-accent="ikb | lemon-yellow | lemon-green | safety-orange">`。

将 `<!-- POSTERS_HERE -->` 后的单个占位海报替换为每页一个 `<section class="poster ...">` 块，每个块采用所选布局方案的 HTML 骨架（Editorial 使用 M01-M16，Swiss 使用 S01-S12）。绝不要加载错误模板的类系统：Editorial 方案依赖衬线展示文字 + ledger/marginalia/pipeline-v；Swiss 方案依赖 Inter + card-fills + matrix/h-bar/kpi-tower。混用会在无明显报错的情况下破坏布局。

### 5. 构建与渲染

默认实现方式：

- 默认在 `local-tests/<slug>/` 下创建任务文件夹，或创建在用户指定的输出文件夹中。绝不要把生成的任务文件夹、渲染图片、MOV 文件、`.pvt` 包或下载的源素材放在 `SKILL.md` 旁边的技能根目录中。
- 将源图片放入 `assets/`。
- 从第 4.5 步复制的种子模板开始，而不是空白文件。最好仅逐页修改 `<!-- POSTERS_HERE -->` 区域。如果任务需要自定义布局 CSS，应在复制的文件中添加一个命名清晰、仅限该任务的样式块，并重置语义化默认值（`figure { margin:0; }`，避免浏览器默认间距造成意外）。
- 使用 Playwright 或浏览器截图工具导出每个 `.poster` 或 `.cover` 节点。
- 将渲染图片保存到 `output/`。
- 验证尺寸并检查渲染后的 PNG。
- 保留使用 `node validate-social-deck.mjs <task-dir>` 进行自动检查的能力。它检查溢出（R1）、页脚碰撞（R2）、Swiss 粗体展示文字（R3）、最小字号（R4）、四分带密度（R5）、`.h-xl` 行数上限（R6）、浏览器默认 figure 外边距漂移（R7）、视觉边界/底部留白（R8），以及标题与内容之间的间距（R9）。任何 FAIL 都会返回退出码 1——当用户要求自动检查时，应在最终交付前修复。WARN 为提示性警告，但仍应阅读。

实况照片分支：

- 渲染前确定信息预算：`3s` 适合一个动作点；`5s` 适合一个小流程；三连拼图适合三个并行片段，但不适合复杂故事；长视频需要先诊断再编辑。
- 对于较长的源视频，不要声称能够进行精确的自动精彩片段检测。先探测时长/分辨率，制作稀疏的联系表，然后在裁剪、加速、拆分/三连拼图或向用户询问时间范围之间做出选择。
- 从每个视频槽中提取第一帧，将其放入最终静态卡片布局，并在制作 `.pvt` 之前展示/检查该预览。这样能以低得多的 token 和渲染成本发现裁剪及层级问题。
- 根据平台时长渲染配套 MOV：小红书为 `5s`，微信公众号为 `3s`。
- 从清晰且具有代表性的帧中提取关键 JPG。
- 使用 `makelive` 将 `JPG + MOV` 打包成 `.pvt`；通过 AirDrop 将 `.pvt` 作为一个整体项目传输，以便在 iPhone 上测试。
- 验证尺寸、时长、帧数、包内容和动态质量。视觉检查优先使用联系表式帧条，这样只需要人工/模型检查最终的拼接图片。精确命令和故障模式检查请使用 `references/live-photo-production.md`。

不要在图片中放置可见的操作说明、键盘快捷键或使用解释。

对于 Editorial Magazine x E-ink，应使用分层背景系统。优先使用细腻的 WebGL 水墨流动画布，或冻结的程序化画布加纸张颗粒。读取 `references/background-systems.md`；不要只使用平坦的米色背景，也不要添加覆盖整页的网格/圆点背景。

### 6. 图片和截图处理

当用户提供截图时：

- 除非用户要求重新设计，否则保留截图内容。
- 优先采用程序化框架：目标比例画布、安全内边距、干净背景、可读截图。
- 不要拉伸截图。
- 如果截图清晰度很重要，应扩大截图区域并减少附近文字。

#### 图上文字构图

只要海报将文字放在照片上方（全出血封面、大图片槽、生成图片叠加），就应遵循 `references/image-overlay.md`：

- **先筛选，仅在需要时着色。**覆盖画布面积 ≥60% 的照片必须先通过 `image-overlay.md` 中的安静区和光照测试。先在没有遮罩的情况下构图；如果缩略图检查失败，只在标题区域周围添加局部、与图片色调一致的着色层。不要默认使用覆盖整个画布的渐隐层。
- **必须进行主体映射。**放置标题之前，使用 Read 工具读取图片，用自然语言描述主体的脸部/焦点特征所在位置，并在主视觉块旁边以 HTML 注释记录主体映射。文字只能放在已记录的安全区域中。
- **裁剪纪律——在每张照片上内联设置 `object-position`。**模板默认值（`center 50%`）只是后备设置，并非推荐值。对于每个 `<img>`，都应根据主体位置作出判断并内联写明，例如中景人物使用 `style="object-position:center 62%"`，天空占比较大且主体位于地平线附近的风景使用 `center 30%`，前景装备使用 `center 70%`。范围参见 `references/components.md` 中的表格，人脸照片的具体要求参见 `image-overlay.md`。跳过此步骤会在竖向比例（`r-3x4`、`r-21x9`）下悄悄将主体裁出画面。
- **缩略图测试。**将渲染后的 PNG 缩小到 360 px 宽，并确认标题仍清晰可读。如果标题与照片相互干扰，应移动标题、更换照片，或添加局部且与图片色调一致的着色层；如果照片显得沉闷无生气，则说明着色层过重，或这张照片本身不适合图上文字。

Editorial 深色封面（例如使用游戏主视觉的游戏日志）和带主视觉照片的 Swiss 封面都必须进行这些检查。跳过检查是已知的失败模式（参见 `style-system.md` Anti-Pattern D）。

当用户没有图片时：

- 仅当第 1 步的“三选一”环节选择了 B（网络素材）或 C（AI 生成）时，才进入此分支。绝不要在用户未选择的情况下悄悄进入 B 或 C。
- 对于 C（AI 生成）：只在确实能增加价值的地方使用生成位图，通常为 1-2 页。生成符合页面视觉职责的图片，而不是通用装饰。除非明确需要，否则生成图片中不得嵌入标题、页码、徽标或虚假 UI 标签。
- 对于 B（网络素材）：参见下方“网络素材图片”章节。

#### 网络素材图片（用户没有图片时的后备方案）

当用户没有截图/照片，且生成位图不适合页面角色时（例如 Editorial 氛围照片、户外/生活方式背景、游戏封面图、真实产品照片），应从网络获取图片，而不是让页面内容显得单薄。

原则：**先获取，后披露，由用户决定是否署名。**不要根据猜测的许可证预先过滤来源——用户是最终构图的权利责任方，由用户决定可接受的内容。

推荐来源按优先顺序排列如下。**以下五种均为无需支付许可费用的免费层级素材库**；不得从付费图库网站（视觉中国 / Getty / 站酷海洛等）获取素材。

1. **Unsplash** — `https://unsplash.com/s/photos/<keyword>`。适合户外/生活方式/氛围背景。英文关键词效果最好。许可证较宽松，但仍需逐项核实。
2. **Pexels** — `https://www.pexels.com/search/<keyword>/` 或 `https://www.pexels.com/zh-cn/search/<keyword>/`。**原生支持中文关键词搜索**——能够补足 Unsplash 在国内场景（中文街景 / 国风物件 / 本地地名）上的缺口。当主题与中国相关或关键词为中文时，优先使用此来源。依据 Pexels License 免费使用。
3. **Flickr CC-licensed pool** — `https://www.flickr.com/search/?text=<keyword>&license=2%2C3%2C4%2C5%2C6%2C9`。许可证过滤器（`license=2,3,4,5,6,9`）将结果限制为 Creative Commons 照片。用于填补“纪实真实感”缺口：街头摄影、情境中的人物、真实室内空间，以及 Unsplash/Pexels 缺少的非摆拍场景。如果用户选择署名，必须保留 CC 署名。
4. **Wallhaven** — `https://wallhaven.cc/search?q=<keyword>`。适合游戏/动漫/壁纸主题。内容由用户上传，权利状态未经核实。
5. **直接网页搜索**——需要特定主题时使用，例如产品渲染图、游戏画面或历史照片。使用 WebFetch / WebSearch 查找候选 URL。

Editorial 模式的素材选择顺序：**Pexels（关键词为中文/与中国相关时）→ Unsplash → Flickr CC（需要真实生活质感时）→ 直接搜索**。Swiss 模式很少需要这些素材——产品渲染图、UI 截图和主视觉式图片应由用户提供或通过 AI 生成，而不是使用图库素材。

获取方法：

- 使用 WebFetch 或 `curl` 将图片下载到任务文件夹的 `assets/` 目录中。
- 根据用途而不是哈希值命名文件：`assets/hero-mountain.jpg`、`assets/ui-pulse-card.png`。
- 在图片旁边的 `assets/SOURCES.md` 文件中记录来源 URL（每个文件一行：`hero-mountain.jpg ← <url>`）。即使用户拒绝在最终图片中署名，也必须这样做——这能为内容作者保留来源记录。

获取完成后，应在最终确定设计**之前**向用户披露来源：

```
我从 <site> 取了这些图：
- assets/hero-mountain.jpg — <url>
- assets/ui-pulse-card.png — <url>

⚠️ 版权未经核实。请你判断是否可用。
是否需要在图文中标注来源？
- 要：我把 "Photo · <site> · @<author>" 加到对应页脚 / 角标。
- 不要：原样使用,不加注释。
```

如果用户选择“标注”——添加小号 `mono` 说明文字（Swiss：角落中的 `.t-meta` 18-20px；Editorial：图片槽旁边的 `.label`）。绝不要让署名挤入布局的焦点区域。

如果用户选择“不标注”——直接继续，不再提示。来源信息仍保留在 `assets/SOURCES.md` 中，供用户自行记录。

如果某张图片只是复合构图中的众多元素之一（例如九宫格中的一张），用户可以合理地不署名。不要强制添加会破坏布局的来源标签。

### 7. 交付

**先展示给用户，仅在用户要求时验证。**每次渲染后自动运行验证器耗时太长，会延迟用户看到结果。默认流程：

1. 渲染完成后，立即以内联方式向用户展示渲染图片（使用绝对路径），并用一句话概括完成的内容。
2. 只问一个问题：**“先你自己看，还是我先自动核查一遍？”**
3. 如果用户说“我自己看”/“先给我”/“no need”——到此停止，让用户检查，并根据用户提出的问题继续处理。
4. 如果用户说“你查吧”/“auto-check”/“yes”——这时才运行 `node validate-social-deck.mjs <task-dir>`，修复所有 FAIL，并在最终交付前重新渲染。说明所有密度/上限 WARN。

绝不要在向用户展示之前悄悄运行验证器——每次检查可能耗费数分钟，而且用户通常能更快发现问题。

最终回复（用户检查后或要求自动检查后）应包括：

- 输出文件夹路径。
- 在适用时，通过绝对路径以内联方式展示渲染图片。
- 简要说明尺寸和验证状态（或“尚未验证，等待你的检查”）。
- 对于任何从网络获取的图片：来源 URL + 网站 + 用户作出的署名决定。
- 对于实况照片：`.pvt` 包路径、用于调试的 `JPG + MOV` 组合、目标平台时长和验证摘要。
- 对于实况照片发布：提醒用户两件事：平台限制（小红书 `5s`、微信公众号 `3s`）和发布路径（通过 AirDrop 将 `.pvt` 包作为一个整体项目传输到 iPhone，然后从对应移动应用的发布入口发布；桌面端/网页端上传路径通常无法将 `.pvt` 识别为可发布的实况照片）。
- 如果用户无法使用 iPhone/AirDrop 发布路径（例如仅有桌面端工作流、使用 Android，或平台不支持实况照片），可以提供降级交付方案：从同一个 MOV 源导出简短循环 GIF 或静音 MP4 片段。GIF/MP4 能保留动态证据，但会失去实况照片点按播放的体验。切换到此后备方案前，应先征得用户确认。
- 所有尚未解决的风险，例如源图片分辨率较低。

## 不可妥协的要求

- 绝不要编辑原始归藏 PPT 技能或任何从其他地方复制的上游技能。
- 绝不要在技能根目录中创建生成内容。所有任务产物默认必须位于 `local-tests/<slug>/` 下，或位于用户指定的输出文件夹中。禁止创建 `social-card-*`、`livephoto-*`、`wechat-*` 等根级生成文件夹，也禁止放置零散输出资源。
- 不要创建随机的装饰性 SVG 椭圆、色块、水滴、贴纸或毫无意义的圆圈。
- 不要默认使用嵌套卡片或通用 SaaS 卡片布局。
- 不要让文字溢出、接触边缘或与页脚区域发生碰撞。在 flex 纵向布局中使用 `margin-top: auto` 固定 `.foot`，绝不要使用 `position: absolute` 将其覆盖在不断增长的内容上。
- 内容溢出时，编辑前先测量溢出量。小幅溢出应采用小幅修复：`1-40px` 表示轻微移动/收紧，`40-90px` 表示局部压缩，`90-160px` 表示轻微压缩标题或段落，只有 `160px+` 才应触发方案变更或内容删除。修复后检查 R8 底部留白，避免页面从溢出摆向底部出现巨大空白带。
- 不要让标题紧贴下一个内容块。主要展示标题下方通常至少保留 `28px`；局部标题至少保留 `16px`。依赖视觉检查之前，先使用验证器 R9。
- 不要让文字小到无法在移动设备上阅读。
- 不要在 Swiss 展示标题上内联编写 `font-size` + `font-weight`。应使用类型化类（`.h-hero` / `.h-statement` / `.h-xl` / `.num-mega`）。字号为 80-120px、字重为 700-900 的标题不属于 Swiss；“越大越细”是硬性规则。
- 不要交付只有平坦纸张背景、每一行都有等宽标签且没有氛围层的 Editorial 海报。运行 `references/style-system.md` 中的 Editorial Identity Test——仅有衬线标题并不能让海报成为 Editorial。
- 不要伪造数据、发布信息或百分比。
- 除非用户明确接受，否则不要裁掉人脸、关键 UI 文字或硬件/产品细节。
- 不要在不说明的情况下把视频卡片变成虚假的静态序列。如果源视频短于目标时长，应询问用户是否提供更长的源视频、使用更短但符合平台要求的时长，或明确记录所采用的定格/慢放处理。
- 不要跳过实况照片的第一帧预览。视频是带有动态效果的图片槽；在渲染 MOV 之前，其第一帧必须符合静态 3:4 布局和裁剪规则。
- 不要让结果视频在浅裁剪区域中滚动穿过不同章节的边界；这会产生“视频重叠”故障。打包前应检查联系表并选择稳定的时间窗口。
- 为提升可读性而放大/裁剪视频时，不要猜测用户的视觉重点。应向用户说明裁剪/放大的取舍，并在用户确认后执行，除非请求已经明确指出焦点区域。
- 不要通过盲目裁剪 `21:9` 封面来复用成 `1:1`。应分别为每种比例进行构图。
- **3:4 卡必须吃满画布**。Content (text + image + data) 必须覆盖 ≥75% 画布高度。任何 >15% 画布高度的纯空白带都需要"留白理由"：(a) hero image 自带呼吸、(b) 单句宣言式 hero statement、(c) 段落顶/底 leading & trailing whitespace（前后总和 ≤15%）。**禁止用 `<div style="flex: 1"></div>` 上下夹击把内容塞到中段**——杂志页留白逻辑不适用于社交卡（杂志靠对开页吸收留白，社交卡逐张独立刷，欠填看着像 PPT 漏排）。Recipe-by-recipe 最小密度见 `references/layout-recipes.md` 每条 recipe 的「Minimum density」段。Render 后必须跑 `qa-checklist.md` 的 4 横带密度检查。

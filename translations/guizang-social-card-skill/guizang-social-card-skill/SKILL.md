# 归藏社交卡片 Skill

为小红书/Rednote、微信公众号、文章封面和平台缩略图创建精致的社交卡片套装。

此 skill 是自包含的。它借鉴归藏 PPT 风格系统的视觉原则，但不得编辑原始 PPT skill、其模板或参考资料。如果原始 PPT skill 可用，可以只读方式将其作为参考。所有生成的工作成果应放在当前项目或用户指定的输出文件夹中。

## 产出内容

此 skill 适用于：

- 社交卡片/轮播图集：封面加内容页，尤其是小红书/Rednote 3:4 图片。
- 微信公众号封面组合：一张 `21:9` 主封面加一张 `1:1` 方形封面，并在同一个 HTML 中组合展示以便视觉检查。
- 以截图为主的产品帖子、文章封面、教程轮播图、户外/生活方式笔记、AI/产品更新解读。
- 需要归藏风格瑞士式或编辑杂志式布局的社交图片。

此 skill 不适用于：

- 完整幻灯片或横向 PPT 网站。请使用 PPT skill。
- 长视频生成。请使用视频 skill。
- 不涉及布局或文章提取要求的纯图片编辑。

### Rednote 类目能力范围（能力圈）

Rednote（小红书）最常见的 11 个类目分为三档。逐类路由方案见 `references/category-cookbook.md`。

**具备强大的端到端能力**（文本、结构和图片叙事均在范围内）：

- 旅行（Travel）、职场（Workplace）、推荐（Recommended，需先指定子类型）。

**文本与结构能力强；图片需由用户提供或从素材库获取：**

- 游戏（Game）、影视（Film/TV）、美食 食谱方向（Food — 仅食谱）、彩妆 教程方向（Makeup — 仅教程）、健身（Fitness）、家居（Home）、穿搭 精选方向（Outfit — 仅胶囊衣橱/文章型内容）。

**超出范围——应坦诚说明限制，不要承诺无法实现的结果：**

- 美食 菜品大片摆盘（美食摄影展示）。
- 穿搭 日常 OOTD 全身（日常 OOTD 全身照；我们无法生成或模拟）。
- 情感 梦核 / 氛围感装饰风（梦核/氛围灯光风格——与 Editorial 和 Swiss 都冲突）。
- Y2K / 千禧辣妹 / 哥特萝莉 / kawaii 装饰美学。
- 图片本身就是全部交付物的纯摄影展示帖。

当请求落入第三档时，应在需求接收阶段明确说明我们无法完成的部分——不要悄悄套用一个偏离用户意图的布局。

## 核心原则

表达优先。目标不是把文字硬塞进海报，而是把来源内容转化为清晰的视觉论点。

对每一页，都要判断：

- 观众应该一眼理解什么？
- 哪些证据、截图或图片可以支撑它？
- 哪些文字必须放大，哪些可以变成说明文字或元数据？
- 哪些内容可以删除，因为它们属于帖子正文，而不是图片？

## 工作流程

### 1. 需求接收

只收集会改变输出结果的缺失信息：

- 目标平台和比例。
- 源文本、字幕、文章或标题。
- **Rednote 类目**——如果用户指定了 11 种常见类型之一（旅行 / 职场 / 游戏 / 影视 / 美食 / 彩妆 / 穿搭 / 家居 / 健身 / 情感 / 推荐），通过 `references/category-cookbook.md` 路由以找到正确方案，并确认请求是否在能力圈内（见上方“Rednote 类目能力范围”）。如果请求落入超出范围的档位，应在设计**之前**告知用户，不要悄悄套用其他方案。
- 用户提供的图片/截图，以及每张图应出现的位置。**对于新闻/教程/数据/评测类内容，应主动询问截图或照片**——它们是证据层。没有真实素材的海报往往会显得空洞。
- **如果用户只提供了文本（完全没有图片），设计前只询问一次：**

  ```
  这篇我需要 1-2 张图。三种走法：
  A. 你自己有照片 / 截图，传给我（推荐——最不"AI 感"）
  B. 我去 Pexels / Unsplash / Flickr 帮你找
  C. 用 AI 生成
  ```

  用一句话推荐 A——自己的照片最能让海报摆脱 AI 生成感。接受用户的任何选择（包括“都行你看着办”）并继续。**之后不要再次询问，也不要在多个轮次中持续引导用户选择 A。**这个问题只能问一次。
- 用户指定的首选风格：瑞士风格、杂志/编辑风格、科技、户外等。
- 硬性约束：标题文字、`1:1` 封面不得使用图片、必须包含硬件照片、保持截图可读等。

如果用户已经提供了足够的上下文，则基于合理假设继续。

如果内容涉及当前产品发布、政策、价格、声明或新闻，应通过浏览验证可能变化的事实，并在最终回复中引用来源。

### 2. 提取故事

设计前，先将来源内容转化为页面计划。

对于 Rednote：

- 第 1 页是封面钩子。
- 第 2-N 页每页只承载一个观点。
- 大多数帖子使用 5-9 页。当页面下部过空时，压缩或合并页面。
- 细节和延伸内容留给帖子正文；图片应承载钩子、对比、清单和鲜明结论。

对于微信：

- 始终制作成对系统：`21:9` 主封面和 `1:1` 方形封面。
- 在同一个 HTML 文件中构建两张封面，并添加组合预览区，以便一起检查它们的视觉关系。
- `21:9` 保留完整或接近完整的标题、副标题和一个强有力的视觉关系。
- `1:1` 使用从长标题中提炼的简化短标题：大号居中文字，默认不使用图片，不塞入拥挤的副标题。

### 3. 选择风格模式

每套作品选择一种模式。**这两种系统并不绑定特定内容类型**——改变的是视觉立场，而不是可以表达的话题。职场文章可以使用 Editorial；旅行账本也可以使用 Swiss。应根据希望营造的感受选择，而不是通过类目查表决定。

**Editorial Magazine x E-ink** 的特点：

- 衬线体/宋体展示字搭配安静的无衬线正文，使用纸张与墨水配色。
- 在温暖纸张底色上叠加氛围层（纸张颗粒/水墨晕染/WebGL canvas）。
- 账本式行列、边注、醒目引语、大幅照片区——呈现杂志专题感。
- 最适合希望页面呈现舒缓、深思熟虑、手工排印质感的场景。

**Swiss International** 的特点：

- Inter / Helvetica 质感，大字号展示文字使用极细字重，小字号标签使用等宽字体。
- 严格的左对齐网格、发丝细分隔线和一种高饱和强调色。
- 卡片填充矩阵、KPI 高塔、水平条形图、编号陈述——呈现系统/数据感。
- 最适合希望页面呈现工程化、量化、果断感的场景。

如果两种风格都适合某段内容，问题就转化为编辑意图：“这是一篇专题故事，还是一则发布说明？”决定模式的是这个问题，而不是主题本身。

除非用户明确要求混合风格，否则不要在同一组图片中混用两套视觉系统。

然后选择一个主题：

- Editorial Magazine x E-ink 使用 6 种杂志配色之一：Ink Classic、Indigo Porcelain、Forest Ink、Kraft Paper、Dune 或 Midnight Ink（唯一的深色变体；仅用于游戏主视觉/夜景摄影/电影感封面）。
- Swiss International 使用 4 种强调色之一：IKB Blue、Lemon Yellow、Lemon Green 或 Safety Orange。

精确 CSS token 请阅读 `references/theme-presets.md`。除非用户有严格的品牌要求，否则不要随意创造颜色。

### 4. 规划页面

创建简洁的内部计划：

```text
Page 01 / cover / hook / image source / layout intent
Page 02 / point / key copy / visual evidence / layout intent
...
```

如果用户要求审批，则在渲染前展示该计划。否则在内部使用并继续执行。

使用 `references/layout-recipes.md` 选择页面结构。避免每页都重复使用“标题加卡片”的布局。

对于 3:4 图片，编码前检查 `references/portrait-fill.md`。简短表格或账本必须扩展成完整的竖版构图，可加入引语栏、图片证据、边注、更高的行距或背景主视觉区。

### 4.5. 复制种子模板

不要从头编写 HTML。根据第 3 步选择的风格模式选取一个种子模板：

- Editorial Magazine × E-ink → 将 `assets/template-editorial-card.html` 复制到任务文件夹并命名为 `index.html`。
- Swiss International → 将 `assets/template-swiss-card.html` 复制到任务文件夹并命名为 `index.html`。

种子模板已配置：字体加载、主题 token、全部三种海报尺寸（`.poster.xhs` / `.poster.square` / `.poster.wide`）、组合预览框架、颗粒/背景层，以及布局方案所引用的全部类定义。

在 `<html>` 元素上设置主题/强调色：

- Editorial：`<html data-theme="ink-classic | indigo-porcelain | forest-ink | kraft-paper | dune | midnight-ink">`。
- Swiss：`<html data-accent="ikb | lemon-yellow | lemon-green | safety-orange">`。

将 `<!-- POSTERS_HERE -->` 后面的单个占位海报替换为每页一个 `<section class="poster ...">` 块，每个块使用所选布局方案的 HTML 骨架（Editorial 使用 M01-M16，Swiss 使用 S01-S12）。绝不要加载错误模板的类系统：Editorial 方案依赖衬线展示字体、账本/边注/垂直流程线；Swiss 方案依赖 Inter、卡片填充、矩阵/水平条形图/KPI 高塔。混用会在无明显报错的情况下破坏布局。

### 5. 构建与渲染

默认实现方式：

- 在当前工作区创建任务文件夹，例如 `social-card-<slug>/`。
- 将源图片放入 `assets/`。
- 从第 4.5 步复制的种子模板开始，不要使用空白文件。逐页制作时，优先只修改 `<!-- POSTERS_HERE -->` 区域。如果任务需要自定义布局 CSS，则在复制的文件中添加一个命名清晰、仅限当前任务的代码块，并重置语义元素默认样式（`figure { margin:0; }`，避免浏览器默认间距造成意外）。
- 使用 Playwright 或浏览器截图工具导出每个 `.poster` 或 `.cover` 节点。
- 将渲染图片保存到 `output/`。
- 验证尺寸并检查渲染后的 PNG。
- 保留使用 `node validate-social-deck.mjs <task-dir>` 进行自动检查的能力。它检查溢出（R1）、页脚碰撞（R2）、Swiss 粗体展示字（R3）、最小字号（R4）、四横带密度（R5）、`.h-xl` 行数上限（R6）和浏览器默认 figure 外边距漂移（R7）。任何 FAIL 都会返回退出码 1——用户要求自动检查时，必须在最终交付前修复。WARN 仅为建议，但应阅读。

不要在图片中放置可见的操作说明、键盘快捷键或使用解释。

对于 Editorial Magazine x E-ink，应使用分层背景系统。优先采用微妙的 WebGL 墨水流动画布或冻结的程序化画布，再叠加纸张颗粒。阅读 `references/background-systems.md`；不要只使用平坦的米色背景，也不要添加覆盖整页的网格/圆点背景。

### 6. 图片与截图处理

当用户提供截图时：

- 除非用户要求重新设计，否则保留截图内容。
- 优先使用程序化装裱：目标比例画布、安全内边距、干净背景、可读截图。
- 不要拉伸截图。
- 如果截图清晰度很重要，应扩大截图区域并减少周围文字。

#### 图上文字构图

每当海报将文字叠加在照片上（全出血封面、大型图片区、生成图片覆盖层）时，都应遵循 `references/image-overlay.md`：

- **先筛选，必要时才加色调遮罩。**覆盖画布 ≥60% 的照片必须先通过 `image-overlay.md` 中的安静区和光线测试。先在不加遮罩的情况下构图；如果缩略图检查失败，只在标题区域添加局部、与图片色调协调的遮罩。不要默认使用覆盖整个画布的渐变衰减。
- **必须进行主体映射。**放置标题前，使用 Read 工具读取图片，用自然语言描述主体的人脸/视觉焦点所在位置，并将主体映射以 HTML 注释放在主视觉块旁边。文字只能放在记录的安全区域中。
- **严格控制裁剪——每张照片都必须内联设置 `object-position`。**模板默认值（`center 50%`）只是兜底，不是推荐值。应根据主体位置为每个 `<img>` 做出判断并内联写入，例如：半身主体使用 `style="object-position:center 62%"`，天空占比较高且主体位于地平线附近的风景使用 `center 30%`，前景装备使用 `center 70%`。范围见 `references/components.md` 中的表格，人脸照片细则见 `image-overlay.md`。跳过此步骤会在高纵横比（`r-3x4`、`r-21x9`）中悄悄将主体裁出画面。
- **缩略图测试。**将渲染后的 PNG 缩小到 360 px 宽，确认标题仍然清晰可读。如果标题与照片相互干扰，则移动标题、更换照片或添加局部且与图片色调协调的遮罩；如果照片看起来失去活力，说明遮罩过重或照片本身不适合叠加文字。

Editorial 深色封面（例如使用游戏主视觉的游戏日志）和带主视觉照片的 Swiss 封面都必须进行这些检查。跳过它们是已知失败模式（见 `style-system.md` 的 Anti-Pattern D）。

当用户没有图片时：

- 只有当第 1 步“三选一”环节选择了 B（网络素材）或 C（AI 生成）时，才进入此分支。绝不能悄悄转入 B 或 C——必须遵循用户的选择。
- 对于 C（AI 生成）：仅在确有价值的位置使用生成位图，通常为 1-2 页。生成的图片应匹配页面的视觉角色，而不是充当泛化装饰。除非明确需要，否则生成图片中不要嵌入标题、页码、Logo 或虚假 UI 标签。
- 对于 B（网络素材）：参见下方“网络素材图片”部分。

#### 网络素材图片（用户没有图片时的兜底方案）

当用户没有截图/照片，且生成位图不适合页面角色时（例如 Editorial 氛围照片、户外/生活方式背景、游戏封面图、真实产品照片），应从网络获取素材，而不是让页面显得单薄。

政策：**先获取，后披露，由用户决定是否署名。**不要根据猜测的许可证预先筛选来源——用户是最终作品的权利责任人，应由用户决定哪些素材可以接受。

推荐来源按优先级排列如下。**以下五类均为无需支付许可费的免费层素材库**；我们不从付费图库（视觉中国 / Getty / 站酷海洛等）获取素材。

1. **Unsplash** — `https://unsplash.com/s/photos/<keyword>`。适合户外/生活方式/氛围背景。英文关键词效果最好。许可证较宽松，但仍需逐案核实。
2. **Pexels** — `https://www.pexels.com/search/<keyword>/` 或 `https://www.pexels.com/zh-cn/search/<keyword>/`。**原生支持中文关键词搜索**——弥补 Unsplash 在国内场景（中文街景 / 国风物件 / 本地地名）方面的不足。当主题与中国相关或关键词为中文时，优先使用此来源。可依据 Pexels License 免费使用。
3. **Flickr CC 授权素材池** — `https://www.flickr.com/search/?text=<keyword>&license=2%2C3%2C4%2C5%2C6%2C9`。许可证筛选器（`license=2,3,4,5,6,9`）会将结果限制为 Creative Commons 照片。它可补足“纪实真实感”的缺口：街头摄影、情境中的人物、真实室内环境，以及 Unsplash/Pexels 缺少的非摆拍场景。如果用户选择署名，必须保留 CC 署名。
4. **Wallhaven** — `https://wallhaven.cc/search?q=<keyword>`。适合游戏/动漫/壁纸主题。内容由用户上传，权利状况未经核实。
5. **直接网页搜索** — 当需要特定主题时使用，例如产品渲染图、游戏画面、历史照片。使用 WebFetch / WebSearch 查找候选 URL。

Editorial 模式的选择顺序：**Pexels（关键词为中文/主题与中国相关时）→ Unsplash → Flickr CC（需要真实生活质感时）→ 直接搜索**。Swiss 模式通常很少需要这些来源——产品渲染图、UI 截图和主视觉式图片应由用户提供或通过 AI 生成，而不是使用图库素材。

获取方式：

- 使用 WebFetch 或 `curl` 将图片下载到任务文件夹的 `assets/` 目录。
- 按用途而不是哈希值命名文件：`assets/hero-mountain.jpg`、`assets/ui-pulse-card.png`。
- 在图片旁的 `assets/SOURCES.md` 文件中记录来源 URL（每个文件一行：`hero-mountain.jpg ← <url>`）。即使用户不希望在最终图片中署名，也必须这样做——这能为人类作者保留素材来源记录。

获取后，在最终确定设计**之前**向用户披露来源：

```
我从 <site> 取了这些图：
- assets/hero-mountain.jpg — <url>
- assets/ui-pulse-card.png — <url>

⚠️ 版权未经核实。请你判断是否可用。
是否需要在图文中标注来源？
- 要：我把 "Photo · <site> · @<author>" 加到对应页脚 / 角标。
- 不要：原样使用,不加注释。
```

如果用户选择“标注”——添加小号 `mono` 说明文字（Swiss：角落使用 `.t-meta` 18-20px；Editorial：在图片区旁使用 `.label`）。不要让署名文字挤占布局的视觉焦点区域。

如果用户选择“不标注”——直接继续，不再说明。素材来源仍保存在 `assets/SOURCES.md` 中，供用户自行查阅。

如果某张图片只是组合设计中的多个元素之一（例如九宫格中的一张照片），用户可以合理地选择不署名。不要强制添加会破坏布局的来源标签。

### 7. 交付

**先展示给用户，按需验证。**每次渲染后自动运行验证器耗时太长，会延误用户看到结果。默认流程：

1. 渲染完成后，立即以内联方式向用户展示渲染图片（使用绝对路径），并用一句话概述完成的内容。
2. 只问一个问题：**“先你自己看，还是我先自动核查一遍？”**
3. 如果用户回答“我自己看”/“先给我”/“no need”——在此停止，让用户检查，并根据其反馈继续。
4. 如果用户回答“你查吧”/“auto-check”/“yes”——此时才运行 `node validate-social-deck.mjs <task-dir>`，修复所有 FAIL，并在最终交付前重新渲染。说明密度/行数上限相关的 WARN。

绝不要在展示给用户之前悄悄运行验证器——每轮验证可能耗时数分钟，而且用户通常能更快发现问题。

最终回复（用户审阅完毕或要求自动检查后）应包括：

- 输出文件夹路径。
- 适用时，以绝对路径内联展示渲染图片。
- 关于尺寸和验证结果的简短说明（或“尚未验证，等待你的审阅”）。
- 对于任何从网络获取的图片：来源 URL、网站，以及用户作出的署名决定。
- 所有尚未解决的风险，例如源图片分辨率较低。

## 不可妥协的规则

- 绝不编辑原始归藏 PPT skill 或任何从其他来源复制的上游 skill。
- 不要创建随机装饰性 SVG 椭圆、斑点、雨滴、贴纸或毫无意义的圆形。
- 不要默认使用嵌套卡片或通用 SaaS 卡片布局。
- 不要让文字溢出、贴边或与页脚带碰撞。在 flex 列中使用 `margin-top: auto` 固定 `.foot`，绝不要使用 `position: absolute` 将其覆盖在不断增长的内容上。
- 不要让文字小到无法在手机上阅读。
- 不要在 Swiss 展示标题上内联编写 `font-size` + `font-weight`。使用类型化类（`.h-hero` / `.h-statement` / `.h-xl` / `.num-mega`）。80-120px、字重 700-900 的标题不属于 Swiss；“字号越大，字重越轻”是硬性规则。
- 不要交付只有平坦纸张背景、每一行都使用等宽标签且缺少氛围层的 Editorial 海报。运行 `references/style-system.md` 中的 Editorial Identity Test——仅有衬线标题并不能使海报成为 Editorial。
- 不要伪造数据、发布详情或百分比。
- 除非用户明确接受，否则不要裁掉人脸、关键 UI 文字或硬件/产品细节。
- 不要通过盲目裁剪 `21:9` 封面来复用为 `1:1`。每种比例必须分别构图。
- **3:4 卡必须吃满画布**。内容（文字 + 图片 + 数据）必须覆盖 ≥75% 画布高度。任何 >15% 画布高度的纯空白带都需要“留白理由”：(a) hero image 自带呼吸、(b) 单句宣言式 hero statement、(c) 段落顶/底 leading & trailing whitespace（前后总和 ≤15%）。**禁止用 `<div style="flex: 1"></div>` 上下夹击把内容塞到中段**——杂志页留白逻辑不适用于社交卡（杂志靠对开页吸收留白，社交卡逐张独立刷，欠填看着像 PPT 漏排）。各个 Recipe 的最小密度见 `references/layout-recipes.md` 中每条 recipe 的「Minimum density」段。渲染后必须执行 `qa-checklist.md` 中的四横带密度检查。

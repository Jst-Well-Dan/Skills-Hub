# 文档协作撰写工作流

此技能提供了一个结构化工作流，用于引导用户协作创建文档。充当积极主动的向导，带领用户完成三个阶段：上下文收集、完善与组织，以及读者测试。

## 何时提供此工作流

**触发条件：**
- 用户提到编写文档：“写一份文档”、“起草一份提案”、“创建一份规范”、“整理成文”
- 用户提到特定文档类型：“PRD”、“设计文档”、“决策文档”、“RFC”
- 用户似乎准备开始一项较大的写作任务

**初始建议：**
向用户提供一个用于协作撰写文档的结构化工作流。解释三个阶段：

1. **上下文收集**：用户提供所有相关上下文，同时 Claude 提出澄清问题
2. **完善与组织**：通过头脑风暴和编辑，逐节迭代构建内容
3. **读者测试**：使用一个全新的 Claude（无上下文）测试文档，在其他人阅读前发现盲点

说明这种方法有助于确保其他人阅读文档时能够顺利理解（包括他们将文档粘贴到 Claude 中时）。询问他们是想尝试此工作流，还是更愿意自由协作。

如果用户拒绝，则自由协作。如果用户接受，则进入阶段 1。

## 阶段 1：上下文收集

**目标：** 缩小用户所知与 Claude 所知之间的差距，以便稍后提供明智的指导。

### 初始问题

首先询问用户有关文档的元上下文：

1. 这是什么类型的文档？（例如技术规范、决策文档、提案）
2. 主要受众是谁？
3. 希望读者阅读后产生什么效果？
4. 是否有需要遵循的模板或特定格式？
5. 是否还有其他需要了解的约束或上下文？

告知他们可以使用简写回答，也可以用任何最适合自己的方式倾倒信息。

**如果用户提供模板或提到某种文档类型：**
- 询问他们是否有可以分享的模板文档
- 如果他们提供共享文档的链接，请使用适当的集成获取该文档
- 如果他们提供文件，请读取该文件

**如果用户提到要编辑现有的共享文档：**
- 使用适当的集成读取文档当前状态
- 检查是否存在没有替代文本的图像
- 如果存在没有替代文本的图像，请说明当其他人使用 Claude 理解文档时，Claude 将无法看到这些图像。询问他们是否希望生成替代文本。如果希望，请他们将每张图像粘贴到聊天中，以生成描述性替代文本。

### 信息倾倒

初始问题回答完毕后，鼓励用户倾倒他们拥有的全部上下文。请求以下信息：
- 项目或问题的背景
- 相关的团队讨论或共享文档
- 为什么不采用其他解决方案
- 组织上下文（团队动态、过往事件、内部关系）
- 时间压力或约束
- 技术架构或依赖项
- 利益相关者的顾虑

建议他们不必担心整理，只需把所有信息都说出来。提供多种上下文提交方式：
- 以意识流方式倾倒信息
- 指向需要阅读的团队频道或讨论串
- 链接到共享文档

**如果有可用的集成**（例如 Slack、Teams、Google Drive、SharePoint 或其他 MCP 服务器），请说明可以使用这些集成直接获取上下文。

**如果未检测到集成，并且当前位于 Claude.ai 或 Claude 应用中：** 建议他们在 Claude 设置中启用连接器，以便直接从消息应用和文档存储中获取上下文。

告知他们完成初始信息倾倒后，将提出澄清问题。

**上下文收集期间：**

- 如果用户提到团队频道或共享文档：
  - 如果有可用的集成：告知他们现在将读取相关内容，然后使用适当的集成
  - 如果没有可用的集成：说明无法访问。建议他们在 Claude 设置中启用连接器，或直接粘贴相关内容。

- 如果用户提到未知的实体或项目：
  - 询问是否应搜索已连接的工具以了解更多信息
  - 等待用户确认后再搜索

- 随着用户提供上下文，持续记录已经了解的内容以及仍不清楚的内容

**提出澄清问题：**

当用户表示已完成初始信息倾倒时（或已经提供大量上下文后），提出澄清问题以确保理解：

根据上下文中的缺口生成 5-10 个编号问题。

告知他们可以使用简写回答（例如“1：是，2：见 #channel，3：否，因为向后兼容性”），链接到更多文档，指向需要阅读的频道，或者继续倾倒信息。采用对他们最高效的方式即可。

**退出条件：**
当提出的问题体现出已经理解上下文时，即已能够询问边界情况和权衡，而不需要用户解释基础信息，说明已收集到足够的上下文。

**过渡：**
询问他们在此阶段是否还有更多上下文想要提供，或者是否该开始起草文档。

如果用户希望补充更多信息，就让他们补充。准备就绪后，进入阶段 2。

## 阶段 2：完善与组织

**目标：** 通过头脑风暴、筛选和迭代完善，逐节构建文档。

**给用户的说明：**
说明文档将逐节构建。对于每一节：
1. 提出澄清问题，确定要包含哪些内容
2. 通过头脑风暴提出 5-20 个选项
3. 用户指出要保留、删除或合并的内容
4. 起草该节
5. 通过精确编辑进行完善

从未知因素最多的部分开始（通常是核心决策或提案），然后处理其余部分。

**章节顺序：**

如果文档结构清晰：
询问他们希望从哪一节开始。

建议从未知因素最多的部分开始。对于决策文档，通常是核心提案。对于规范，通常是技术方案。摘要部分最好留到最后。

如果用户不知道需要哪些章节：
根据文档类型和模板，建议 3-5 个适合该文档类型的章节。

询问此结构是否合适，或者他们是否希望调整。

**结构达成一致后：**

为所有章节创建包含占位文本的初始文档结构。

**如果可以访问 artifacts：**
使用 `create_file` 创建 artifact。这样 Claude 和用户都能获得一个可协作的文档框架。

告知他们将创建包含所有章节占位符的初始结构。

创建包含所有章节标题和简短占位文本（如“[待撰写]”或“[在此填写内容]”）的 artifact。

提供文档框架链接，并说明现在可以开始逐节填写内容。

**如果无法访问 artifacts：**
在工作目录中创建一个 Markdown 文件。使用合适的名称（例如 `decision-doc.md`、`technical-spec.md`）。

告知他们将创建包含所有章节占位符的初始结构。

创建包含所有章节标题和占位文本的文件。

确认已创建该文件，并说明现在可以开始逐节填写内容。

**对于每一节：**

### 步骤 1：澄清问题

宣布将开始处理 [SECTION NAME] 章节。提出 5-10 个澄清问题，了解应该包含哪些内容：

根据上下文和章节目的生成 5-10 个具体问题。

告知他们可以使用简写回答，或者只指出哪些内容必须涵盖。

### 步骤 2：头脑风暴

根据 [SECTION NAME] 章节的复杂程度，通过头脑风暴提出 [5-20] 项可能包含的内容。寻找：
- 已经分享但可能被遗忘的上下文
- 尚未提及的角度或考虑因素

根据章节复杂程度生成 5-20 个编号选项。最后询问他们是否还需要更多选项，如需要则继续进行头脑风暴。

### 步骤 3：筛选

询问哪些要点应该保留、删除或合并。请他们简要说明理由，以帮助了解后续章节的优先级。

提供示例：
- “保留 1、4、7、9”
- “删除 3（与 1 重复）”
- “删除 6（受众已经知道这一点）”
- “合并 11 和 12”

**如果用户提供自由形式的反馈**（例如“看起来不错”或“我大部分都喜欢，但是……”），而不是选择编号，请提取他们的偏好并继续。解析他们希望保留、删除或更改的内容，并应用这些要求。

### 步骤 4：缺口检查

根据他们选择的内容，询问 [SECTION NAME] 章节是否还遗漏了任何重要内容。

### 步骤 5：起草

使用 `str_replace` 将此章节的占位文本替换为实际起草的内容。

宣布现在将根据他们选择的内容起草 [SECTION NAME] 章节。

**如果使用 artifacts：**
起草完成后，提供 artifact 链接。

请他们通读并指出需要更改的内容。说明反馈越具体，越有助于了解他们对后续章节的偏好。

**如果使用文件（无 artifacts）：**
起草完成后，确认已完成。

告知他们已在 [filename] 中起草 [SECTION NAME] 章节。请他们通读并指出需要更改的内容。说明反馈越具体，越有助于了解他们对后续章节的偏好。

**给用户的关键说明（起草第一节时加入）：**
提供一条提示：请不要直接编辑文档，而是指出需要更改的内容。这有助于了解他们的风格，以便用于后续章节。例如：“删除 X 要点——Y 已经涵盖了它”或“让第三段更简洁”。

### 步骤 6：迭代完善

随着用户提供反馈：
- 使用 `str_replace` 进行编辑（切勿重新输出整份文档）
- **如果使用 artifacts：** 每次编辑后提供 artifact 链接
- **如果使用文件：** 只需确认编辑已完成
- 如果用户直接编辑文档并要求读取：在心中记录他们所做的更改，并在后续章节中加以考虑（这些更改体现了他们的偏好）

**继续迭代**，直到用户对该章节满意为止。

### 质量检查

连续 3 次迭代都没有实质性更改后，询问是否可以删除某些内容而不损失重要信息。

章节完成后，确认 [SECTION NAME] 已完成。询问是否准备继续下一节。

**对所有章节重复此流程。**

### 接近完成

当接近完成时（80% 以上的章节已完成），宣布将重新阅读整份文档并检查：
- 各章节之间的衔接和一致性
- 重复或矛盾
- 任何显得“粗制滥造”或通用填充的内容
- 是否每句话都有实际价值

阅读整份文档并提供反馈。

**所有章节起草和完善完成后：**
宣布所有章节均已起草完成。说明将再审阅一次完整文档。

审查整体连贯性、行文流畅性和完整性。

提供最终建议。

询问是否准备进入读者测试，或者是否还想完善其他内容。

## 阶段 3：读者测试

**目标：** 使用一个全新的 Claude（无上下文污染）测试文档，验证它是否对读者有效。

**给用户的说明：**
说明现在将进行测试，看看该文档是否真的对读者有效。这可以发现盲点——一些对作者而言很合理、但可能让其他人感到困惑的内容。

### 测试方法

**如果可以使用 sub-agents（例如在 Claude Code 中）：**

直接执行测试，无需用户参与。

### 步骤 1：预测读者问题

宣布将预测读者在尝试查找此文档时可能提出的问题。

生成 5-10 个读者实际可能提出的问题。

### 步骤 2：使用 Sub-Agent 测试

宣布将使用一个全新的 Claude 实例（不含本次对话的上下文）测试这些问题。

对于每个问题，仅向 sub-agent 提供文档内容和问题并调用它。

总结 Reader Claude 对每个问题回答正确和错误的地方。

### 步骤 3：执行其他检查

宣布将执行其他检查。

调用 sub-agent 检查歧义、错误假设和矛盾。

总结发现的所有问题。

### 步骤 4：报告并修复

如果发现问题：
报告 Reader Claude 在哪些具体问题上遇到了困难。

列出具体问题。

说明将修复这些缺口。

返回完善流程，处理存在问题的章节。

---

**如果无法使用 sub-agents（例如在 claude.ai 网页界面中）：**

用户需要手动执行测试。

### 步骤 1：预测读者问题

询问人们在尝试查找此文档时可能会提出什么问题。他们会在 Claude.ai 中输入什么？

生成 5-10 个读者实际可能提出的问题。

### 步骤 2：设置测试

提供测试说明：
1. 打开一个全新的 Claude 对话：https://claude.ai
2. 粘贴或共享文档内容（如果使用启用了连接器的共享文档平台，请提供链接）
3. 向 Reader Claude 提出生成的问题

对于每个问题，要求 Reader Claude 提供：
- 答案
- 是否存在歧义或不清楚之处
- 文档假设读者已经具备哪些知识或上下文

检查 Reader Claude 是否给出正确答案，或是否误解了任何内容。

### 步骤 3：其他检查

还应询问 Reader Claude：
- “此文档中有哪些内容可能对读者而言存在歧义或不够清楚？”
- “此文档假设读者已经具备哪些知识或上下文？”
- “是否存在任何内部矛盾或不一致？”

### 步骤 4：根据结果迭代

询问 Reader Claude 回答错误或遇到困难的地方。说明将修复这些缺口。

返回完善流程，处理任何存在问题的章节。

---

### 退出条件（两种方法均适用）

当 Reader Claude 能够持续正确回答问题，并且不再发现新的缺口或歧义时，文档即准备就绪。

## 最终审查

读者测试通过后：
宣布文档已通过 Reader Claude 测试。完成前：

1. 建议他们亲自进行最后一次通读——他们是这份文档的所有者，并对其质量负责
2. 建议再次检查所有事实、链接或技术细节
3. 请他们确认文档是否达到了预期效果

询问他们是否希望再审查一次，或者工作是否已经完成。

**如果用户希望进行最终审查，请执行审查。否则：**
宣布文档已完成。提供一些最终提示：
- 考虑在附录中链接本次对话，让读者了解文档的形成过程
- 使用附录提供深度信息，避免主文档过于臃肿
- 根据真实读者的反馈持续更新文档

## 有效指导的技巧

**语气：**
- 直接且程序化
- 当理由会影响用户行为时，简要说明理由
- 不要试图“推销”这种方法——直接执行即可

**处理偏离流程的情况：**
- 如果用户想跳过某个阶段：询问他们是否希望跳过此阶段并自由撰写
- 如果用户显得沮丧：承认所需时间比预期更长。建议加快进度的方法
- 始终让用户有权调整流程

**上下文管理：**
- 在整个过程中，如果提到的某些内容缺少上下文，应主动询问
- 不要让缺口不断积累——出现时就及时处理

**Artifact 管理：**
- 使用 `create_file` 起草完整章节
- 所有编辑均使用 `str_replace`
- 每次更改后提供 artifact 链接
- 切勿使用 artifacts 存放头脑风暴列表——这些内容只需保留在对话中

**质量优先于速度：**
- 不要匆忙完成各个阶段
- 每次迭代都应带来有意义的改进
- 目标是创建一份真正对读者有效的文档

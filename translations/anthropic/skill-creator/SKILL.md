# 技能创建器

一个用于创建新技能并对其进行迭代改进的技能。

从高层次来看，创建技能的流程如下：

- 确定你希望技能完成什么，以及它大致应该如何完成
- 编写技能草稿
- 创建几个测试提示，并让可访问该技能的 Claude 运行这些提示
- 帮助用户从定性和定量两个方面评估结果
  - 在运行任务于后台执行期间，如果还没有定量 evals，就起草一些（如果已经有了，可以直接使用，或者在你认为需要修改时进行调整）。然后向用户解释这些 evals（如果它们已经存在，就解释现有的 evals）
  - 使用 `eval-viewer/generate_review.py` 脚本向用户展示结果供其查看，同时让他们查看定量指标
- 根据用户对结果的评估反馈重写技能（如果定量基准测试暴露出任何明显缺陷，也应据此修改）
- 重复以上过程，直到你满意为止
- 扩展测试集，并以更大规模再次尝试

使用此技能时，你的任务是判断用户目前处于这个流程的哪个阶段，然后加入并帮助他们推进后续阶段。例如，他们可能会说“我想为 X 制作一个技能”。你可以帮助他们明确具体需求、编写草稿、编写测试用例、确定评估方式、运行所有提示，并不断重复。

另一方面，他们也可能已经有了技能草稿。在这种情况下，你可以直接进入 eval/迭代环节。

当然，你应始终保持灵活。如果用户说“我不需要运行一大堆评估，直接凭感觉和我一起做就行”，你也可以按这种方式进行。

技能完成后（不过，流程顺序仍然可以灵活调整），你还可以运行技能描述改进器。我们为此准备了一个单独的完整脚本，用于优化技能触发效果。

明白了吗？很好。

## 与用户沟通

技能创建器可能会被熟悉程度各不相同的用户使用，他们对编程术语的了解可能差异很大。如果你还没听说过（你当然可能没听说，因为这种趋势最近才出现），现在出现了一种趋势：Claude 的能力正在鼓舞水管工打开终端，也让父母和祖父母开始搜索“如何安装 npm”。不过，大多数用户可能还是具备相当程度的计算机素养。

因此，请留意上下文线索，以判断应该如何措辞！作为默认参考：

- “评估”和“基准测试”处于临界位置，但通常可以直接使用
- 对于“JSON”和“断言”，你最好先从用户那里看到明确迹象，确认他们知道这些概念，再在不加解释的情况下使用

如果你不确定，可以简要解释术语；如果不确定用户能否理解，也可以用一句简短的定义澄清。

## 创建技能

### 捕获意图

首先理解用户的意图。当前对话中可能已经包含用户想要固化的工作流（例如，他们说“把这个变成一个技能”）。如果是这样，先从对话历史中提取答案——使用过的工具、步骤顺序、用户做出的纠正，以及观察到的输入/输出格式。用户可能需要补充其中的空缺，并应在进入下一步前进行确认。

1. 此技能应该让 Claude 能够完成什么？
2. 此技能应在什么时候触发？（哪些用户措辞/上下文）
3. 预期的输出格式是什么？
4. 是否应设置测试用例来验证技能是否有效？具有客观可验证输出的技能（文件转换、数据提取、代码生成、固定工作流步骤）适合使用测试用例。具有主观输出的技能（写作风格、艺术创作）通常不需要。根据技能类型建议合适的默认选项，但让用户做最终决定。

### 访谈与研究

主动询问边缘情况、输入/输出格式、示例文件、成功标准和依赖项。在彻底理清这些内容之前，不要编写测试提示。

检查可用的 MCP——如果它们有助于研究（搜索文档、查找类似技能、查询最佳实践），且有可用的子代理，就通过子代理并行研究；否则直接进行研究。提前准备好上下文，以减轻用户的负担。

### 编写 SKILL.md

根据用户访谈填写以下组成部分：

- **name**：技能标识符
- **description**：何时触发以及它做什么。这是主要的触发机制——既要包含技能的功能，也要包含应在何种具体上下文中使用它。所有“何时使用”的信息都应放在这里，而不是正文中。注意：Claude 目前有一种“不充分触发”技能的倾向——即使技能有用，也可能不使用。为应对这一点，请让技能描述稍微“积极主动”一些。例如，不要写“如何构建一个简单、快速的仪表板来显示 Anthropic 内部数据。”，而可以写成“如何构建一个简单、快速的仪表板来显示 Anthropic 内部数据。每当用户提到仪表板、数据可视化、内部指标，或想展示任何类型的公司数据时，都务必使用此技能，即使他们没有明确要求创建‘仪表板’。”
- **compatibility**：所需工具、依赖项（可选，很少需要）
- **技能的其余部分 :)**

### 技能编写指南

#### 技能的结构

```
skill-name/
├── SKILL.md (必需)
│   ├── YAML frontmatter (name, description 必需)
│   └── Markdown 指令
└── 捆绑资源 (可选)
    ├── scripts/    - 用于确定性/重复性任务的可执行代码
    ├── references/ - 根据需要加载到上下文中的文档
    └── assets/     - 输出中使用的文件（模板、图标、字体）
```

#### 渐进式披露

技能使用三级加载系统：
1. **元数据**（name + description）- 始终位于上下文中（约 100 个词）
2. **SKILL.md 正文** - 每当技能触发时加载到上下文中（理想情况下少于 500 行）
3. **捆绑资源** - 按需使用（不限大小，脚本无需加载即可执行）

这些字数只是大致参考，如有需要，可以适当增加。

**关键模式：**
- 将 SKILL.md 控制在 500 行以内；如果接近此限制，请增加一层层级，并明确指出使用该技能的模型接下来应到哪里继续查阅。
- 在 SKILL.md 中清楚引用文件，并说明何时阅读它们
- 对于大型参考文件（超过 300 行），应包含目录

**领域组织方式**：当技能支持多个领域/框架时，按变体组织：
```
cloud-deploy/
├── SKILL.md (工作流 + 选择)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claude 只读取相关的参考文件。

#### 无意外原则

这本应是不言自明的，但技能不得包含恶意软件、漏洞利用代码或任何可能危害系统安全的内容。如果一个技能已被如实描述，其内容和意图就不应让用户感到意外。不要配合创建误导性技能，也不要创建旨在协助未经授权的访问、数据外泄或其他恶意活动的技能。不过，类似“扮演某个 XYZ”这样的请求是可以的。

#### 编写模式

指令应优先使用祈使句。

**定义输出格式**——可以像这样编写：
```markdown
## 报告结构
始终使用以下确切模板：
# [标题]
## 执行摘要
## 主要发现
## 建议
```

**示例模式**——包含示例会很有帮助。可以像这样设置格式（不过，如果示例中包含“输入”和“输出”，你可能需要稍作调整）：
```markdown
## 提交消息格式
**示例 1：**
输入：使用 JWT 令牌添加了用户身份验证
输出：feat(auth): implement JWT-based authentication
```

### 写作风格

与其大量使用生硬、陈旧的 MUST，不如尝试向模型解释事情为什么重要。运用心智理论，并尽量让技能具有通用性，不要过度局限于特定示例。先写一份草稿，然后以新的视角重新审视并改进它。

### 测试用例

编写技能草稿后，构思 2-3 个真实的测试提示——也就是现实用户真正可能说出的内容。与用户分享这些提示：[不必使用完全相同的措辞]“这里有几个我想尝试的测试用例。它们看起来合适吗？还是你想再添加一些？”然后运行它们。

将测试用例保存到 `evals/evals.json`。暂时不要编写断言——只保存提示。在下一步运行任务进行期间，你会起草断言。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "用户的任务提示",
      "expected_output": "预期结果的描述",
      "files": []
    }
  ]
}
```

完整模式请参阅 `references/schemas.md`（包括稍后要添加的 `assertions` 字段）。

## 运行和评估测试用例

本节是一个连续流程——不要中途停止。不要使用 `/skill-test` 或任何其他测试技能。

将结果放入 `<skill-name>-workspace/`，使其与技能目录互为同级目录。在工作区内，按迭代组织结果（`iteration-1/`、`iteration-2/` 等），并在每次迭代中为每个测试用例创建一个目录（`eval-0/`、`eval-1/` 等）。不要预先创建所有目录——随着流程推进逐个创建即可。

### 第 1 步：在同一轮中启动所有运行任务（使用技能和基线）

对于每个测试用例，在同一轮中启动两个子代理——一个使用技能，一个不使用。这一点很重要：不要先启动使用技能的运行任务，然后稍后再回来启动基线。一次性启动所有任务，让它们大致同时完成。

**使用技能的运行任务：**

```
执行此任务：
- 技能路径：<path-to-skill>
- 任务：<eval prompt>
- 输入文件：<eval files if any, or "none">
- 将输出保存到：<workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- 要保存的输出：<what the user cares about — e.g., "the .docx file", "the final CSV">
```

**基线运行任务**（使用相同提示，但基线取决于上下文）：
- **创建新技能**：完全不使用技能。使用相同提示，不提供技能路径，并保存到 `without_skill/outputs/`。
- **改进现有技能**：使用旧版本。编辑前先为技能创建快照（`cp -r <skill-path> <workspace>/skill-snapshot/`），然后让基线子代理使用该快照。保存到 `old_skill/outputs/`。

为每个测试用例编写一个 `eval_metadata.json`（断言暂时可以为空）。根据测试内容为每个 eval 起一个描述性名称——不要只使用“eval-0”。目录也使用这个名称。如果本次迭代使用了新增或修改过的 eval 提示，请为每个新的 eval 目录创建这些文件——不要假设它们会从之前的迭代中自动继承。

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "用户的任务提示",
  "assertions": []
}
```

### 第 2 步：在运行任务进行期间起草断言

不要只是等待运行任务完成——可以有效利用这段时间。为每个测试用例起草定量断言，并向用户解释它们。如果 `evals/evals.json` 中已经存在断言，请审查并解释它们检查的内容。

好的断言应当可以客观验证，并具有描述性名称——它们应该能在基准查看器中清晰呈现，让浏览结果的人一眼就能明白每个断言检查什么。主观技能（写作风格、设计质量）更适合进行定性评估——不要强行给需要人工判断的内容添加断言。

断言起草完成后，更新各个 `eval_metadata.json` 文件和 `evals/evals.json`。同时向用户解释他们将在查看器中看到什么——包括定性输出和定量基准测试。

### 第 3 步：运行任务完成时记录计时数据

当每个子代理任务完成时，你会收到包含 `total_tokens` 和 `duration_ms` 的通知。立即将这些数据保存到该运行目录中的 `timing.json`：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这是捕获这些数据的唯一机会——它们通过任务通知传递，不会持久保存到其他位置。每条通知到达时就处理，不要试图批量处理。

### 第 4 步：评分、汇总并启动查看器

所有运行任务完成后：

1. **为每次运行评分**——启动一个评分子代理（或直接评分），让其读取 `agents/grader.md`，并根据输出评估每项断言。将结果保存到每个运行目录的 `grading.json` 中。grading.json 的 expectations 数组必须使用字段 `text`、`passed` 和 `evidence`（不能使用 `name`/`met`/`details` 或其他变体）——查看器依赖这些确切的字段名。对于能够通过程序检查的断言，应编写并运行脚本，而不是靠肉眼判断——脚本更快、更可靠，并且可以在多次迭代中复用。

2. **汇总为基准测试**——运行 skill-creator 目录中的汇总脚本：
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   这会生成 `benchmark.json` 和 `benchmark.md`，其中包含每种配置的 pass_rate、时间和令牌数，并提供平均值 ± 标准差及差值。如果手动生成 benchmark.json，请参阅 `references/schemas.md`，了解查看器所需的确切模式。
将每个 with_skill 版本放在其对应的基线版本之前。

3. **进行分析审查**——读取基准数据，并找出汇总统计数据可能掩盖的模式。有关需要关注的内容，请参阅 `agents/analyzer.md`（“Analyzing Benchmark Results”部分）——例如，无论是否使用技能都总是通过的断言（缺乏区分度）、方差较高的 evals（可能不稳定），以及时间/令牌方面的权衡。

4. **启动查看器**，同时提供定性输出和定量数据：
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   对于第 2 次及之后的迭代，还要传递 `--previous-workspace <workspace>/iteration-<N-1>`。

   **Cowork / 无界面环境：**如果 `webbrowser.open()` 不可用或环境没有显示设备，请使用 `--static <output_path>` 写入独立 HTML 文件，而不是启动服务器。用户点击“Submit All Reviews”后，反馈将作为 `feedback.json` 文件下载。下载后，将 `feedback.json` 复制到工作区目录，供下一次迭代读取。

注意：请使用 generate_review.py 创建查看器；无需编写自定义 HTML。

5. **告知用户**，可以这样说：“我已经在你的浏览器中打开了结果。里面有两个标签页——‘Outputs’让你逐个查看测试用例并留下反馈，‘Benchmark’显示定量对比。查看完成后，请回到这里告诉我。”

### 用户在查看器中看到的内容

“Outputs”标签页一次显示一个测试用例：
- **Prompt**：交给系统的任务
- **Output**：技能生成的文件；在可能的情况下以内嵌方式呈现
- **Previous Output**（第 2 次及之后的迭代）：显示上一次迭代输出的折叠区域
- **Formal Grades**（如果运行了评分）：显示断言通过/失败情况的折叠区域
- **Feedback**：一个文本框，输入内容会自动保存
- **Previous Feedback**（第 2 次及之后的迭代）：上一次的评论，显示在文本框下方

“Benchmark”标签页显示统计摘要：各配置的通过率、计时和令牌使用情况，以及每个 eval 的明细和分析观察结果。

可以使用上一项/下一项按钮或方向键进行导航。完成后，用户点击“Submit All Reviews”，所有反馈会保存到 `feedback.json`。

### 第 5 步：读取反馈

当用户告诉你他们已经完成审查时，读取 `feedback.json`：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "图表缺少坐标轴标签", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "非常完美，我很喜欢", "timestamp": "..."}
  ],
  "status": "complete"
}
```

空白反馈表示用户认为结果没有问题。重点改进用户明确提出意见的测试用例。

完成后终止查看器服务器：

```bash
kill $VIEWER_PID 2>/dev/null
```

## 改进技能

这是整个循环的核心。你已经运行了测试用例，用户也审查了结果，现在需要根据他们的反馈改进技能。

### 如何思考改进方向

1. **从反馈中概括普遍规律。** 这里发生的事情，从全局来看，是我们试图创建可以被使用一百万次（也许真的是一百万次，甚至可能更多，谁知道呢）的技能，让它们适用于各种不同的提示。你和用户之所以只围绕少量示例反复迭代，是因为这样推进得更快。用户对这些示例了如指掌，可以迅速评估新的输出。但如果你和用户共同开发的技能只能用于这些示例，那它就毫无用处。不要进行琐碎且过度拟合的修改，也不要堆砌压迫性、限制过度的 MUST。遇到顽固问题时，可以尝试换用不同的比喻，或者推荐不同的工作模式。尝试的成本相对较低，而且你也许会找到非常好的方案。

2. **保持提示精简。** 删除没有发挥作用的内容。务必阅读执行记录，而不只是最终输出——如果技能似乎让模型浪费大量时间执行没有成效的操作，可以尝试删除技能中导致这些行为的部分，然后观察效果。

3. **解释原因。** 尽最大努力解释要求模型执行每项操作背后的**原因**。如今的 LLM 非常*聪明*。它们具有良好的心智理论，在获得合适的框架后，能够超越机械指令并真正把事情做好。即使用户的反馈很简短或带有挫败感，也要尝试真正理解任务，理解用户为什么写下这些内容、他们实际写了什么，然后将这种理解传递到指令中。如果你发现自己正在使用全大写的 ALWAYS 或 NEVER，或者使用极其僵化的结构，这就是一个警示信号——如果可能，请重新表述并解释原因，让模型理解你所要求的事情为什么重要。这是一种更人性化、更强大且更有效的方法。

4. **寻找测试用例之间的重复工作。** 阅读测试运行记录，注意各个子代理是否都独立编写了相似的辅助脚本，或采用了相同的多步骤方法。如果 3 个测试用例都导致子代理编写 `create_docx.py` 或 `build_chart.py`，这强烈表明技能应捆绑该脚本。只需编写一次，将它放入 `scripts/`，并指示技能使用它。这样可以避免未来每次调用都重复造轮子。

这项任务非常重要（毕竟我们正试图每年创造数十亿的经济价值！），而你的思考时间并不是瓶颈；请慢慢来，认真琢磨。我建议先写一份修订草稿，然后重新审视并进一步改进。尽最大努力站在用户的角度，真正理解他们想要什么、需要什么。

### 迭代循环

改进技能后：

1. 将改进应用到技能
2. 将所有测试用例重新运行到新的 `iteration-<N+1>/` 目录中，包括基线运行。如果正在创建新技能，基线始终为 `without_skill`（不使用技能）——在所有迭代中保持不变。如果正在改进现有技能，请根据实际情况判断应使用用户最初提供的原始版本，还是上一次迭代作为基线。
3. 启动审查器，并让 `--previous-workspace` 指向上一次迭代
4. 等待用户审查并告诉你他们已经完成
5. 读取新的反馈，再次改进，并重复流程

持续进行，直到：
- 用户表示满意
- 所有反馈都为空（所有内容都没有问题）
- 已经无法取得有意义的进展

## 高级：盲测对比

如果希望更严格地比较技能的两个版本（例如，用户询问“新版本真的更好吗？”），可以使用盲测对比系统。有关详细信息，请阅读 `agents/comparator.md` 和 `agents/analyzer.md`。基本思路是：将两个输出交给一个独立代理，不告诉它们分别来自哪个版本，让它判断质量。然后分析胜出者为何胜出。

这是可选功能，需要子代理，大多数用户不需要它。人工审查循环通常已经足够。

## 描述优化

SKILL.md frontmatter 中的 description 字段，是决定 Claude 是否调用某个技能的主要机制。创建或改进技能后，应主动提出优化描述，以提高触发准确率。

### 第 1 步：生成触发 eval 查询

创建 20 条 eval 查询——混合应触发和不应触发的情况。保存为 JSON：

```json
[
  {"query": "用户提示", "should_trigger": true},
  {"query": "另一个提示", "should_trigger": false}
]
```

查询必须真实，应是 Claude Code 或 Claude.ai 用户实际可能输入的内容。不要使用抽象请求，而要使用具体、明确并包含充分细节的请求。例如，文件路径、用户工作或情境的个人背景、列名和值、公司名称、URL。可以加入一些背景说明。有些查询可以全部小写，或者包含缩写、拼写错误或随意的口吻。混合使用不同长度，并重点关注边缘情况，而不是让它们过于容易判断（用户之后会有机会确认）。

差：`"格式化这些数据"`、`"从 PDF 中提取文本"`、`"创建图表"`

好：`"好的，我老板刚给我发了这个 xlsx 文件（在我的下载目录里，文件名大概是 'Q4 sales final FINAL v2.xlsx'），她想让我加一列，用百分比显示利润率。收入好像在 C 列，成本在 D 列"`

对于**应触发**查询（8-10 条），应考虑覆盖范围。使用表达同一意图的不同措辞——有些正式，有些随意。包含用户未明确说出技能或文件类型、但显然需要该技能的情况。加入一些不常见的用例，以及此技能与其他技能竞争但应该胜出的情况。

对于**不应触发**查询（8-10 条），最有价值的是那些近似但不匹配的情况——它们与技能共享关键词或概念，但实际上需要不同的能力。考虑相邻领域、朴素关键词匹配会错误触发的模糊措辞，以及查询虽然涉及此技能所做的事情，但在该上下文中使用其他工具更合适的情况。

需要避免的关键问题：不要让不应触发的查询明显无关。对于 PDF 技能，把“编写一个 fibonacci 函数”作为负面测试太简单了——它没有测试任何实质内容。负面用例应该真正具有迷惑性。

### 第 2 步：与用户审查

使用 HTML 模板向用户展示 eval 集供其审查：

1. 从 `assets/eval_review.html` 读取模板
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → eval 项目的 JSON 数组（外面不要加引号——它是一个 JS 变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → 技能名称
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → 技能当前的描述
3. 写入临时文件（例如 `/tmp/eval_review_<skill-name>.html`）并打开：`open /tmp/eval_review_<skill-name>.html`
4. 用户可以编辑查询、切换 should-trigger、添加/删除条目，然后点击“Export Eval Set”
5. 文件会下载到 `~/Downloads/eval_set.json`——检查 Downloads 文件夹中最新的版本，以防存在多个文件（例如 `eval_set (1).json`）

这一步很重要——糟糕的 eval 查询会产生糟糕的描述。

### 第 3 步：运行优化循环

告诉用户：“这需要一些时间——我会在后台运行优化循环，并定期检查进度。”

将 eval 集保存到工作区，然后在后台运行：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

使用系统提示中标明的模型 ID（即当前会话所使用的模型），这样触发测试才能匹配用户的实际体验。

运行期间，定期查看输出末尾，向用户更新当前迭代进度和得分情况。

此命令会自动处理完整的优化循环。它会将 eval 集拆分为 60% 的训练集和 40% 的保留测试集，评估当前描述（每条查询运行 3 次，以获得可靠的触发率），然后调用 Claude，根据失败情况提出改进建议。它会在训练集和测试集上重新评估每个新描述，最多迭代 5 次。完成后，它会在浏览器中打开一份 HTML 报告，展示每次迭代的结果，并返回包含 `best_description` 的 JSON——该描述根据测试得分而不是训练得分进行选择，以避免过拟合。

### 技能触发机制

了解触发机制有助于设计更好的 eval 查询。技能会以名称和描述的形式出现在 Claude 的 `available_skills` 列表中，Claude 根据描述决定是否查阅某个技能。需要注意的是，Claude 只会为那些无法轻松自行处理的任务查阅技能——像“读取这个 PDF”这样的简单单步查询，即使描述完全匹配，也可能不会触发技能，因为 Claude 可以使用基础工具直接处理。复杂、多步骤或专业化的查询，在描述匹配时会更可靠地触发技能。

这意味着 eval 查询应该足够充实，让 Claude 确实能从查阅技能中获益。“读取文件 X”之类的简单查询是糟糕的测试用例——无论描述质量如何，它们都不会触发技能。

### 第 4 步：应用结果

从 JSON 输出中获取 `best_description`，并更新技能 SKILL.md 的 frontmatter。向用户展示修改前后的内容，并报告得分。

### 打包并呈现（仅当 `present_files` 工具可用时）

检查你是否可以访问 `present_files` 工具。如果不能，则跳过此步骤。如果可以，请打包技能，并向用户提供 .skill 文件：

```bash
python -m scripts.package_skill <path/to/skill-folder>
```

打包完成后，将用户引导到生成的 `.skill` 文件路径，以便他们安装。

## Claude.ai 专用指令

在 Claude.ai 中，核心工作流保持不变（草拟 → 测试 → 审查 → 改进 → 重复），但由于 Claude.ai 没有子代理，一些具体机制需要调整。应作如下适配：

**运行测试用例**：没有子代理意味着无法并行执行。对于每个测试用例，读取技能的 SKILL.md，然后自行按照其中的指令完成测试提示。一次执行一个。这不如独立子代理严格（因为你编写了技能，同时又在运行它，所以掌握全部上下文），但仍然是有用的健全性检查——人工审查步骤可以弥补这一点。跳过基线运行——只需使用技能完成所请求的任务。

**审查结果**：如果无法打开浏览器（例如 Claude.ai 的 VM 没有显示设备，或你正在远程服务器上），请完全跳过浏览器审查器。改为直接在对话中展示结果。对于每个测试用例，显示提示和输出。如果输出是用户需要查看的文件（例如 .docx 或 .xlsx），请将它保存到文件系统并告知用户路径，以便他们下载和检查。直接在对话中询问反馈：“看起来怎么样？有什么想修改的吗？”

**基准测试**：跳过定量基准测试——它依赖基线对比，而在没有子代理的情况下，这种对比没有意义。专注于用户的定性反馈。

**迭代循环**：与之前相同——改进技能、重新运行测试用例、询问反馈——只是不在中间使用浏览器审查器。如果环境提供文件系统，仍然可以将结果组织到迭代目录中。

**描述优化**：本节需要 `claude` CLI 工具（具体来说是 `claude -p`），而它仅在 Claude Code 中可用。如果你在 Claude.ai 中，请跳过本节。

**盲测对比**：需要子代理。跳过。

**打包**：`package_skill.py` 脚本可以在任何提供 Python 和文件系统的环境中运行。在 Claude.ai 中，你可以运行该脚本，然后让用户下载生成的 `.skill` 文件。

**更新现有技能**：用户可能要求更新现有技能，而不是创建新技能。在这种情况下：
- **保留原始名称。** 记录技能目录名称和 frontmatter 中的 `name` 字段——不要修改它们。例如，如果安装的技能是 `research-helper`，则输出 `research-helper.skill`（而不是 `research-helper-v2`）。
- **编辑前复制到可写位置。** 已安装的技能路径可能是只读的。将其复制到 `/tmp/skill-name/`，在那里进行编辑，并从该副本打包。
- **如果手动打包，请先在 `/tmp/` 中暂存**，然后复制到输出目录——直接写入可能因权限问题而失败。

## Cowork 专用指令

如果你在 Cowork 中，需要了解的主要事项如下：

- 你可以使用子代理，因此主要工作流（并行启动测试用例、运行基线、评分等）都能正常工作。（不过，如果遇到严重的超时问题，也可以串行运行测试提示，而不是并行运行。）
- 你没有浏览器或显示设备，因此生成 eval 查看器时，应使用 `--static <output_path>` 写入独立 HTML 文件，而不是启动服务器。然后提供一个用户可以点击的链接，让他们在浏览器中打开该 HTML。
- 不知为何，Cowork 环境似乎会让 Claude 在运行测试后不太愿意生成 eval 查看器，所以再次强调：无论你在 Cowork 还是 Claude Code 中，运行测试后，在你自行评估输入、修改技能并尝试纠正之前，都应始终使用 `generate_review.py` 生成 eval 查看器（不要自己编写花哨的 html 代码），让人工先查看示例。提前抱歉，我要用全大写强调：在自行评估输入之前，先生成 EVAL 查看器！你需要尽快让人工看到结果！
- 反馈的工作方式不同：由于没有运行中的服务器，查看器的“Submit All Reviews”按钮会将 `feedback.json` 下载为文件。然后你可以从那里读取它（可能需要先请求访问权限）。
- 打包功能可用——`package_skill.py` 只需要 Python 和文件系统。
- 描述优化（`run_loop.py` / `run_eval.py`）在 Cowork 中应该可以正常工作，因为它通过子进程使用 `claude -p`，而不是依赖浏览器。不过，请等到技能已经完全完成且用户确认效果良好后，再进行描述优化。
- **更新现有技能**：用户可能要求更新现有技能，而不是创建新技能。请遵循上面 claude.ai 部分中的更新指导。

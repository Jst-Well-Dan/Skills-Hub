# 诊断错误

一套用于处理疑难错误的严谨方法。只有在明确说明理由时才能跳过阶段。

探索代码库时，阅读 `CONTEXT.md`（如果存在）以清晰理解相关模块，并检查所涉及区域的 ADR。

## 阶段 1——建立反馈循环

**这就是本技能的核心。** 其他一切都是机械操作。如果你对该错误有一个**紧密的**通过/失败信号——一个会因_这个_错误而变红的信号——你就能找到原因；二分查找、假设检验和插桩都只是在使用这个信号。如果没有，再怎么盯着代码看也救不了你。

在这里投入格外多的精力。**要积极。要有创造力。拒绝放弃。**

### 构建反馈循环的方法——大致按此顺序尝试

1. 在任何能触达该错误的接缝处编写**失败测试**——单元测试、集成测试或 e2e 测试。
2. 针对正在运行的开发服务器编写 **Curl / HTTP 脚本**。
3. 使用固定输入执行 **CLI 调用**，并将 stdout 与已知正确的快照进行 diff。
4. 编写**无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，并对 DOM/控制台/网络进行断言。
5. **重放捕获的追踪记录。** 将真实的网络请求、负载或事件日志保存到磁盘；在隔离环境中通过相应代码路径重放。
6. **一次性测试工具。** 启动系统的最小子集（一个服务、模拟的依赖项），通过一次函数调用来执行错误代码路径。
7. **属性测试 / 模糊测试循环。** 如果错误是“有时输出错误”，运行 1000 个随机输入并寻找失败模式。
8. **二分测试工具。** 如果错误出现在两个已知状态（提交、数据集、版本）之间，自动执行“在状态 X 启动、检查、重复”，以便使用 `git bisect run`。
9. **差异比较循环。** 让相同输入分别通过旧版本与新版本（或两种配置）运行，并对输出进行 diff。
10. **HITL bash 脚本。** 最后的手段。如果必须由人点击，就用 `scripts/hitl-loop.template.sh` 引导_他们_，使循环仍然结构化。捕获的输出会反馈给你。

建立正确的反馈循环后，这个错误就已经解决了 90%。

### 收紧循环

把循环当作一个产品。一旦有了_一个_循环，就要**收紧**它：

- 能否让它更快？（缓存初始化、跳过无关的初始化、缩小测试范围。）
- 能否让信号更明确？（针对具体症状进行断言，而不是只检查“没有崩溃”。）
- 能否让它更具确定性？（固定时间、设置 RNG 种子、隔离文件系统、冻结网络。）

一个耗时 30 秒且不稳定的循环只比没有循环好一点；一个耗时 2 秒且具有确定性的循环才算紧密——这是调试的超能力。

### 非确定性错误

目标不是获得一次干净的复现，而是实现**更高的复现率**。将触发操作循环 100 次、并行执行、增加压力、缩小时间窗口、注入 sleep。复现率为 50% 的不稳定错误是可调试的；复现率为 1% 的则不是——不断提高复现率，直到它可以被调试。

### 当你确实无法建立循环时

停下来并明确说明。列出你尝试过的方法。向用户请求：(a) 访问能够复现问题的环境，(b) 捕获的工件（HAR 文件、日志转储、核心转储、带时间戳的屏幕录像），或 (c) 添加临时生产环境插桩的许可。**不要**在没有循环的情况下继续提出假设。

### 完成标准——一个能够变红的紧密循环

当循环足够**紧密**且**能够变红**时，阶段 1 才算完成：你可以给出**一条命令**——脚本路径、测试调用或 curl——并且你已经**至少运行过一次**（粘贴调用及其输出），同时它满足：

- [ ] **能够变红**——它会执行实际的错误代码路径，并对**用户描述的确切症状**进行断言，因此能因这个错误而变红，并在修复后变绿。不能只是“运行时没有报错”——它必须能够_捕获这个特定错误_。
- [ ] **具有确定性**——每次运行都得到相同结论（对于不稳定错误：按照上述方法，固定一个较高的复现率）。
- [ ] **快速**——耗时数秒，而不是数分钟。
- [ ] **智能体可运行**——你可以无人值守地运行它；只有通过 `scripts/hitl-loop.template.sh` 才能让人参与循环。

如果你发现在这条命令存在之前，自己已经开始阅读代码来构建理论，**立即停下——直接跳到假设正是本技能要防止的失败。** 没有能够变红的命令，就不能进入阶段 2。

## 阶段 2——复现并最小化

运行循环。观察它变红——错误出现。

确认：

- [ ] 循环产生的是**用户**所描述的失败模式，而不是恰好发生在附近的另一个失败。错误的问题 = 错误的修复。
- [ ] 该失败能够在多次运行中复现（对于非确定性错误，则应以足够高的频率复现，以便据此进行调试）。
- [ ] 你已经捕获了确切症状（错误消息、错误输出、缓慢的耗时），以便后续阶段验证修复是否确实解决了问题。

### 最小化

循环变红后，将复现缩减为**仍然会变红的最小场景**。每次只删除一项输入、调用方、配置、数据或步骤，并在每次删除后重新运行循环——只保留对失败起关键作用的内容。

为什么值得这样做：最小复现会缩小阶段 3 中的假设空间（剩下需要怀疑的可变因素更少），并会成为阶段 5 中清晰的回归测试。

当**剩余的每个元素都不可或缺**时才算完成——删除其中任何一个元素都会使循环变绿。

在完成复现**并且**最小化之前，不要继续。

## 阶段 3——提出假设

在测试任何假设之前，先生成 **3–5 个按优先级排序的假设**。只生成一个假设会让你锚定在第一个看似合理的想法上。

每个假设都必须是**可证伪的**：说明它会做出什么预测。

> 格式：“如果 <X> 是原因，那么 <改变 Y> 会使错误消失 / <改变 Z> 会使错误加重。”

如果无法说明预测，那么这个假设只是一种感觉——丢弃它或使它更明确。

**在测试之前向用户展示排序后的列表。** 他们通常拥有能立刻改变排序的领域知识（“我们刚刚部署了与第 3 项有关的变更”），或者知道哪些假设已经被排除。这是成本低、节省时间多的检查点。不要因此阻塞——如果用户暂时不在，就按照你的排序继续。

## 阶段 4——插桩

每个探针都必须对应阶段 3 中的一个具体预测。**每次只改变一个变量。**

工具偏好顺序：

1. 如果环境支持，使用**调试器 / REPL 检查**。一个断点胜过十条日志。
2. 在能够区分各项假设的边界处添加**有针对性的日志**。
3. 绝不要“记录所有内容然后 grep”。

为**每条调试日志添加标签**，使用唯一前缀，例如 `[DEBUG-a4f2]`。结束时只需 grep 一次即可完成清理。无标签日志会留存；有标签日志必须删除。

**性能分支。** 对于性能回退，日志通常是错误的工具。应先建立基线测量（计时工具、`performance.now()`、分析器、查询计划），然后进行二分查找。先测量，再修复。

## 阶段 5——修复并添加回归测试

在修复之前编写回归测试——但前提是存在一个**正确的接缝**。

正确的接缝是指测试能够按照错误在调用点实际发生的方式，执行**真实的错误模式**。如果唯一可用的接缝过浅（错误需要多个调用方，但测试只有单个调用方；单元测试无法复现触发错误的调用链），那么在那里添加回归测试只会产生虚假的信心。

**如果不存在正确的接缝，这本身就是一项发现。** 将其记录下来。代码库架构正在阻碍对此错误建立可靠防护。为下一阶段标记此问题。

如果存在正确的接缝：

1. 将最小化复现转换为该接缝处的失败测试。
2. 观察它失败。
3. 应用修复。
4. 观察它通过。
5. 针对原始的（未最小化的）场景重新运行阶段 1 的反馈循环。

## 阶段 6——清理并进行事后分析

在宣布完成之前，必须满足：

- [ ] 原始复现不再复现问题（重新运行阶段 1 的循环）
- [ ] 回归测试通过（或已记录不存在接缝）
- [ ] 所有 `[DEBUG-...]` 插桩均已删除（`grep` 该前缀）
- [ ] 一次性原型已删除（或移至有明确标记的调试位置）
- [ ] 在提交 / PR 消息中说明最终被证明正确的假设——让下一位调试者能够从中学习

**然后问：怎样才能预防这个错误？** 如果答案涉及架构变更（没有良好的测试接缝、调用方纠缠不清、存在隐藏耦合），请将具体信息移交给 `/improve-codebase-architecture` 技能。在修复完成**之后**再提出建议，而不是之前——现在掌握的信息比刚开始时更多。

# 原型

原型是**用于回答一个问题的用完即弃代码**。问题决定其形态。

## 选择一个分支

确定要回答的是哪个问题——根据用户的提示、周围的代码，或者在用户在线时直接询问：

- **“这个逻辑 / 状态模型合理吗？”** → [LOGIC.md](LOGIC.md)。构建一个微型交互式终端应用，推动状态机经历那些难以在纸面上推理的情况。
- **“这个界面应该是什么样子？”** → [UI.md](UI.md)。在单个路由上生成多个截然不同的 UI 变体，并可通过 URL 搜索参数和悬浮底栏进行切换。

这两个分支会产出截然不同的成果——选错分支会让整个原型白费。如果问题确实含糊不清且无法联系用户，则默认选择更符合周围代码的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部说明这一假设。

## 两个分支都适用的规则

1. **从第一天起就是用完即弃的，并明确标示这一点。** 将原型代码放在靠近其实际使用位置的地方（紧挨着它所针对的模块或页面），让上下文一目了然——但命名必须让普通读者看出它是原型，而不是生产代码。对于用完即弃的 UI 路由，请遵循项目已有的路由约定；不要发明新的顶层结构。
2. **一条命令即可运行。** 使用项目现有任务运行器支持的方式——`pnpm <name>`、`python <path>`、`bun <path>` 等。用户必须能够不假思索地启动它。
3. **默认不持久化。** 状态保存在内存中。持久化是原型要_验证_的内容，而不应成为原型的依赖。如果问题明确涉及数据库，请使用临时数据库或本地文件，并为其取一个明确包含“PROTOTYPE — wipe me”的名称。
4. **跳过打磨。** 不写测试，不添加超出让原型_能够运行_所需的错误处理，也不做抽象。重点是快速了解情况，然后将其删除。
5. **展示状态。** 每次操作后（逻辑）或每次切换变体时（UI），打印或渲染完整的相关状态，让用户能够看到发生了什么变化。
6. **完成后删除或吸收。** 当原型回答了它的问题后，要么删除它，要么将经过验证的决策整合进真实代码——不要任由它在仓库里腐烂。

## 完成时

原型中唯一值得保留的是_答案_。将答案及其所回答的问题记录在某个持久的位置（提交消息、ADR、议题，或原型旁边的 `NOTES.md`）中。如果用户在线，这项记录可以通过一次简短交流完成；如果用户不在线，则保留占位内容，以便他们（或下一轮处理时的你）在删除原型前填写最终结论。

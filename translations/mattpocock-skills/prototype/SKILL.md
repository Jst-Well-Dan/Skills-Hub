# 原型

原型是**用于回答问题的用完即弃代码**。问题决定原型的形式。

## 选择分支

从用户的提示、周边代码中确定要回答的问题；如果用户在线，也可以直接询问：

- **“这个逻辑 / 状态模型合理吗？”** → [LOGIC.md](LOGIC.md)。构建一个微型交互式终端应用，让状态机经历那些难以在纸面上推演的情况。
- **“它应该是什么样子？”** → [UI.md](UI.md)。在单个路由上生成几种截然不同的 UI 变体，并可通过 URL 查询参数和底部悬浮栏切换。

两个分支会产出截然不同的成果——选错分支会让整个原型白费。如果问题确实含糊不清且联系不上用户，默认选择更符合周边代码的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部说明这一假设。

## 两个分支都适用的规则

1. **从第一天起就是用完即弃的，并明确标注这一点。** 将原型代码放在靠近它实际使用位置的地方（紧邻它所针对的模块或页面），让上下文一目了然——但命名必须让普通读者一眼看出这是原型，而不是生产代码。对于用完即弃的 UI 路由，遵循项目现有的路由约定；不要自创新的顶层结构。
2. **一条命令即可运行。** 使用项目现有任务运行器支持的任何形式——`pnpm <name>`、`python <path>`、`bun <path>` 等。用户必须无需思考就能启动它。
3. **默认不持久化。** 状态保存在内存中。持久化是原型要_验证_的内容，而不是原型应依赖的东西。如果问题明确涉及数据库，则使用临时数据库或本地文件，并赋予一个清晰包含“PROTOTYPE — wipe me”的名称。
4. **跳过打磨。** 不写测试，不做超出让原型_可运行_所需范围的错误处理，也不做抽象。重点是快速获得认知。
5. **呈现状态。** 每次操作后（逻辑分支）或每次切换变体时（UI 分支），打印或渲染全部相关状态，让用户能够看到发生了什么变化。
6. **完成后留存。** 将所有经过验证的决策整合进真实代码，然后把原型本身作为**一手资料**留存：将它提交到主分支之外的一个用完即弃分支，并在实现议题中留下指向该分支的上下文链接。同时也要留存答案——结论以及它所解决的问题——记录在议题或提交中。主分支仅保留经过验证的决策。

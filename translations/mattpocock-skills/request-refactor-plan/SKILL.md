name: request-refactor-plan
description: 通过用户访谈创建一份由微小提交组成的详细重构计划，然后将其提交为 GitHub issue。当用户希望规划重构、创建重构 RFC 或将重构拆分为安全的增量步骤时使用。
---

当用户希望创建重构请求时，将调用此 skill。你应该执行以下步骤。如果你认为某些步骤没有必要，可以跳过。

1. 请用户详细描述他们想要解决的问题，并提供任何潜在的解决思路。

2. 探索仓库，以验证他们的陈述并了解代码库的当前状态。

3. 询问他们是否考虑过其他方案，并向他们提出其他可选方案。

4. 就实现细节访谈用户。务必极其细致、全面。

5. 明确实现的确切范围。确定计划更改的内容以及计划不更改的内容。

6. 查看代码库，检查代码库中该区域的测试覆盖率。如果测试覆盖不足，询问用户的测试计划。

7. 将实现拆分为由微小提交组成的计划。请记住 Martin Fowler 的建议：“让每个重构步骤尽可能小，这样你就始终可以看到程序正常运行。”

8. 创建一个包含重构计划的 GitHub issue。使用以下模板作为 issue 描述：

<refactor-plan-template>

## 问题陈述

从开发者的角度描述其面临的问题。

## 解决方案

从开发者的角度描述问题的解决方案。

## 提交

一份篇幅长、细节丰富的实现计划。使用通俗的语言编写计划，将实现拆分为尽可能小的提交。每个提交都应使代码库保持可工作状态。

## 决策文档

列出已经作出的实现决策。这可以包括：

- 将要构建/修改的模块
- 将要修改的这些模块的接口
- 开发者提供的技术说明
- 架构决策
- Schema 变更
- API 契约
- 具体交互

不要包含具体的文件路径或代码片段。它们可能很快就会过时。

## 测试决策

列出已经作出的测试决策。包括：

- 描述什么样的测试才是好测试（只测试外部行为，不测试实现细节）
- 将测试哪些模块
- 测试的先例（即代码库中类似类型的测试）

## 范围之外

描述本次重构范围之外的事项。

## 补充说明（可选）

关于本次重构的任何其他说明。

</refactor-plan-template>

对用户提供的固定点与 `HEAD` 之间的差异进行双维度审查：

- **规范**——代码是否符合此仓库记录的编码规范？
- **需求**——代码是否忠实实现了原始 issue / PRD / 规格说明？

两个维度都作为**并行子代理**运行，避免相互污染上下文，之后由此技能汇总其发现。

issue 跟踪器本应已提供给你——如果缺少 `docs/agents/issue-tracker.md`，请运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 固定基准点

用户所说的内容就是固定点——可以是提交 SHA、分支名称、标签、`main`、`HEAD~5` 等。如果用户未指定，请询问。

只记录一次差异命令：`git diff <fixed-point>...HEAD`（三个点，因此会与合并基准进行比较）。同时通过 `git log <fixed-point>..HEAD --oneline` 记录提交列表。

继续之前，确认固定点可以解析（`git rev-parse <fixed-point>`），且差异非空。无效引用或空差异应在此处失败，而不是在两个并行子代理内部失败。

### 2. 确定需求来源

按以下顺序查找原始需求：

1. 提交消息中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等）——通过 `docs/agents/issue-tracker.md` 中的工作流获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名称或功能匹配的 PRD/规格说明文件。
4. 如果什么都没找到，询问用户需求在哪里。如果用户说没有需求文档，**需求**子代理将跳过审查并报告“没有可用的需求文档”。

### 3. 确定规范来源

仓库中任何说明代码应如何编写的内容，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除仓库记录的内容外，规范维度始终包含下方的**代码异味基线**——这是一组固定的 Fowler 代码异味（《_Refactoring_》第 3 章），即使仓库未记录任何规范也适用。它受两条规则约束：

- **以仓库为准。** 仓库中记录的规范始终优先；如果其明确认可基线会标记的做法，则不报告该异味。
- **始终需要判断。** 每种异味都是带标签的启发式判断（“可能存在 Feature Envy”），绝不是硬性违规——并且与此处的任何规范一样，跳过工具已经强制执行的内容。

每种异味都按照*它是什么* → *如何修复*的形式描述；将其与差异进行比对：

- **Mysterious Name（神秘命名）**——函数、变量或类型的名称无法揭示其用途或所保存的内容。→ 重命名；如果无法找到诚实准确的名称，说明设计含混不清。
- **Duplicated Code（重复代码）**——相同的逻辑结构出现在变更中的多个差异块或文件里。→ 提取共享结构，并从两处调用。
- **Feature Envy（依恋情结）**——某个方法访问另一个对象的数据多于访问自身数据。→ 将该方法移到它所依恋的数据上。
- **Data Clumps（数据泥团）**——相同的几个字段或参数总是一起传递（意味着一个类型正等待诞生）。→ 将它们组合为一个类型并传递该类型。
- **Primitive Obsession（基本类型偏执）**——使用基本类型或字符串代替本应拥有独立类型的领域概念。→ 为该概念创建自己的小型类型。
- **Repeated Switches（重复的条件逻辑）**——针对相同类型的同一 `switch`/`if` 级联在变更中反复出现。→ 使用多态替代，或让两处共享同一个映射。
- **Shotgun Surgery（霰弹式修改）**——一个逻辑变更迫使差异中许多文件出现分散修改。→ 将一起变化的内容集中到一个模块中。
- **Divergent Change（发散式变化）**——一个文件或模块因多个互不相关的原因而被修改。→ 拆分，使每个模块只因一个原因而变化。
- **Speculative Generality（夸夸其谈的通用性）**——为需求中不存在的需要添加抽象、参数或钩子。→ 删除它；内联回去，直到出现真实需求。
- **Message Chains（过长消息链）**——调用方不应依赖的长串 `a.b().c().d()` 导航。→ 将这段遍历隐藏在第一个对象的一个方法之后。
- **Middle Man（中间人）**——主要只是继续委托给其他对象的类或函数。→ 删除它，直接调用真正的目标。
- **Refused Bequest（被拒绝的遗赠）**——子类或实现者忽略或重写了所继承的大部分内容。→ 去掉继承，使用组合。

### 4. 并行启动两个子代理

发送一条包含两个 `Agent` 工具调用的消息。两个调用都使用 `general-purpose` 子代理。

**规范子代理提示词**——包含：

- 完整的差异命令和提交列表。
- 你在第 3 步找到的规范来源文件列表，**以及第 3 步中的代码异味基线**，完整粘贴——子代理无法通过其他方式访问它。
- 任务说明：“按文件/差异块报告相关内容——(a) 差异中每一处违反已记录规范的地方：引用该规范（文件 + 规则）；以及 (b) 发现的任何基线异味：指出异味名称并引用差异块。区分硬性违规和判断性结论——违反已记录规范可以是硬性违规，但基线异味始终是判断性结论，并且仓库中记录的规范优先于基线。跳过工具已经强制执行的内容。少于 400 字。”

**需求子代理提示词**——包含：

- 差异命令和提交列表。
- 需求文档的路径或获取到的内容。
- 任务说明：“报告：(a) 需求中要求但缺失或仅部分实现的内容；(b) 差异中未被要求的行为（范围蔓延）；(c) 看似已实现，但实现方式可能有误的需求。每项发现都引用对应的需求原文。少于 400 字。”

如果缺少需求文档，跳过需求子代理，并在最终报告中注明。

### 5. 汇总

在 `## Standards` 和 `## Spec` 标题下展示两份报告，可以原样呈现或稍作清理。**不要**合并发现或重新排序——两个维度是刻意分开的（参见*为何采用两个维度*）。

最后用一行总结：每个维度的发现总数，以及每个维度中最严重的问题（如有）。不要在两个维度之间选出唯一最严重的问题——这种重新排序正是将二者分开的目的所在。

## 为何采用两个维度

一项变更可能通过一个维度，却无法通过另一个维度：

- 代码遵循所有规范，却实现了错误的内容 → **规范通过，需求失败。**
- 代码完全实现了 issue 的要求，却破坏了项目约定 → **需求通过，规范失败。**

分开报告可以防止一个维度掩盖另一个维度。

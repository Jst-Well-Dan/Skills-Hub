# 转换为工单

将计划、规范或对话拆分为一组 **工单**——追踪弹式垂直切片，每个工单都声明会 **阻塞** 它的其他工单。

问题跟踪器和分流标签词汇应当已经提供给你——如果尚未提供，请运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

基于对话上下文中已有的全部内容开展工作。如果用户通过参数传入了引用（规范路径、问题编号或 URL），请获取它并完整阅读其正文和评论。

### 2. 探索代码库（可选）

如果你尚未探索代码库，请进行探索，以了解代码的当前状态。工单标题和描述应使用项目领域术语表中的词汇，并遵循你所涉及区域的 ADR。

寻找预先重构代码的机会，让实现变得更容易。“先让变更变得容易，再完成这个容易的变更。”

### 3. 起草垂直切片

将工作拆分为 **追踪弹** 工单。

<vertical-slice-rules>

- 每个切片都应沿着每一层（schema、API、UI、tests）切出一条狭窄但完整的路径——它必须是垂直切片，而不是某一层的水平切片
- 每个已完成的切片都能够独立演示或验证
- 每个切片的规模都应能放入一个全新的上下文窗口中
- 任何预先重构都应首先完成

</vertical-slice-rules>

为每个工单指定其 **阻塞边**——在它开始之前必须完成的其他工单。没有阻塞项的工单可以立即开始。

**大范围重构是垂直切片原则的例外。** **大范围重构**是指一种机械式变更——例如重命名列、重新定义共享符号的类型——其 **影响半径** 扩散到整个代码库，导致一次编辑同时破坏数千个调用点，任何垂直切片都无法在保持绿色状态的情况下落地。不要强行将其拆成追踪弹；应按照 **扩展–收缩** 的方式安排顺序。首先扩展：在旧形式旁添加新形式，确保任何内容都不会损坏。然后根据影响半径将调用点分批迁移（按 package、按 directory），每批作为一个独立工单，并由扩展工单阻塞；由于旧形式仍然存在，因此从一批到下一批都能保持 CI 绿色。最后收缩：在不再有任何调用方后删除旧形式，将其作为一个由所有迁移批次阻塞的工单。当连各个批次都无法独立保持绿色时，仍保留此顺序，但允许它们共享一个集成分支，并让它们全部阻塞最终的集成与验证工单——只承诺在该工单中恢复绿色状态。

### 4. 询问用户

以编号列表的形式展示建议的拆分方案。对于每个工单，展示：

- **标题**：简短的描述性名称
- **阻塞项**：必须先完成的其他工单（如有）
- **交付内容**：此工单将实现的端到端行为

询问用户：

- 粒度是否合适？（太粗 / 太细）
- 阻塞边是否正确——每个工单是否只依赖真正构成其启动门槛的工单？
- 是否应合并某些工单，或进一步拆分？

持续迭代，直到用户批准拆分方案。

### 5. 将工单发布到已配置的跟踪器

发布已批准的工单。具体 **方式** 取决于 `/setup-matt-pocock-skills` 配置的跟踪器——无论哪种方式，工单内容都相同，只有阻塞边的表现形式不同：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下为每个工单写入一个文件，按照依赖顺序（阻塞项优先）从 `01` 开始编号。每个文件的“阻塞项”列出它依赖的编号/标题。使用下面的单工单文件模板——每个文件只包含一个工单，绝不能合并到单个文件中。
- **真实问题跟踪器（GitHub、Linear、……）** → 按照依赖顺序（阻塞项优先）为每个工单发布一个问题，以便每个工单的阻塞边能够引用真实标识符。如果平台提供原生阻塞 / 子问题关系，请使用它；否则，将每个工单的“阻塞项”设为对应的阻塞问题。除非另有指示，否则应用 `ready-for-agent` 分流标签——这些工单在构造上即可由代理领取。

处理 **前沿**：即所有阻塞项均已完成的任意工单。对于纯线性链，这意味着从上到下依次处理。

不要关闭或修改任何父问题。

无论采用哪种形式，都应避免具体文件路径或代码片段——它们很快就会过时。例外：如果原型生成的片段能够比文字更准确地表达某项决策（state machine、reducer、schema、type shape），则可将其内联，并简要注明它来自原型。只保留富含决策信息的部分——不要提供可运行的演示，只保留重要内容。

使用 `/implement` 每次处理一个前沿工单，并在工单之间清除上下文。

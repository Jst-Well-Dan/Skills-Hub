# 代码库设计

设计**深模块**：在小型接口背后封装大量行为，将其置于清晰的接缝处，并可通过该接口进行测试。凡是设计或重构代码，都应使用这套语言和原则。目标是为调用者提供杠杆效应，为维护者提供局部性，并让所有人都能方便地进行测试。

## 术语表

请严格使用这些术语——不要替换为“组件”“服务”“API”或“边界”。统一语言正是这里的核心目的。

**模块** — 任何具有接口和实现的事物。刻意不限定规模：它可以是函数、类、包，也可以是跨层切片。_避免使用_：单元、组件、服务。

**接口** — 调用者为了正确使用模块而必须了解的一切：类型签名，以及不变量、顺序约束、错误模式、必需配置和性能特征。_避免使用_：API、签名（范围过窄——它们仅指类型层面的表面）。

**实现** — 模块内部的内容，即其代码主体。它不同于**适配器**：一个事物可以是具有大型实现的小型适配器（例如 Postgres 仓库），也可以是具有小型实现的大型适配器（例如内存假实现）。讨论接缝时使用“适配器”；其他情况下使用“实现”。

**深度** — 接口所提供的杠杆效应：调用者（或测试）每学习一个单位的接口，就能使用多少行为。当大量行为隐藏在小型接口背后时，模块是**深的**；当接口几乎与实现同样复杂时，模块是**浅的**。

**接缝** _(Michael Feathers)_ — 无需在该位置编辑代码便能改变行为的地方；模块接口所在的*位置*。接缝放在哪里本身就是一项设计决策，与接缝背后放什么是两回事。_避免使用_：边界（该词与 DDD 的限界上下文含义重叠）。

**适配器** — 在接缝处满足某个接口的具体事物。它描述的是*角色*（填补哪个位置），而不是实质（内部是什么）。

**杠杆效应** — 调用者从深度中获得的收益：每学习一个单位的接口，就能获得更多能力。一个实现可以在 N 个调用点和 M 个测试中持续产生回报。

**局部性** — 维护者从深度中获得的收益：变更、缺陷、知识和验证集中在一处，而不是分散到各个调用者中。修复一次，处处修复。

## 深与浅

**深模块** = 小型接口 + 大量实现：

```
┌─────────────────────┐
│      小型接口       │  ← 方法少，参数简单
├─────────────────────┤
│                     │
│      深层实现       │  ← 隐藏复杂逻辑
│                     │
└─────────────────────┘
```

**浅模块** = 大型接口 + 少量实现（应避免）：

```
┌─────────────────────────────────┐
│            大型接口             │  ← 方法多，参数复杂
├─────────────────────────────────┤
│            单薄实现             │  ← 仅仅透传
└─────────────────────────────────┘
```

设计接口时，请问：

- 我能减少方法数量吗？
- 我能简化参数吗？
- 我能在内部隐藏更多复杂性吗？

## 原则

- **深度是接口的属性，而不是实现的属性。** 深模块在内部可以由小型、可模拟、可替换的部分组成——只是这些部分不属于接口。模块既可以拥有**内部接缝**（由实现私有，供自身测试使用），也可以在接口处拥有**外部接缝**。
- **删除测试。** 想象一下删除该模块。如果复杂性随之消失，它只是一个透传层。如果复杂性重新出现在 N 个调用者中，它便发挥了应有的价值。
- **接口就是测试表面。** 调用者和测试跨越同一个接缝。如果你想越过接口测试其内部，模块的形状很可能不正确。
- **一个适配器意味着假想的接缝。两个适配器意味着真实的接缝。** 除非接缝两侧确实存在变化，否则不要引入接缝。

## 为可测试性而设计

良好的接口会让测试自然而然：

1. **接收依赖，不要创建依赖。**

   ```typescript
   // 可测试
   function processOrder(order, paymentGateway) {}

   // 难以测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // 可测试
   function calculateDiscount(cart): Discount {}

   // 难以测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **较小的表面积。** 方法越少，需要的测试越少。参数越少，测试设置越简单。

## 关系

- 一个**模块**恰好拥有一个**接口**（它呈现给调用者和测试的表面）。
- **深度**是**模块**的属性，相对于其**接口**进行衡量。
- **接缝**是**模块**的**接口**所在的位置。
- **适配器**位于**接缝**处，并满足该**接口**。
- **深度**为调用者带来**杠杆效应**，为维护者带来**局部性**。

## 不采用的表述方式

- **将深度视为实现代码行数与接口代码行数之比**（Ousterhout）：这种方式会奖励向实现中填充代码。我们改用“深度即杠杆效应”。
- **将“接口”理解为 TypeScript 的 `interface` 关键字或类的公共方法**：范围过窄——这里的接口包括调用者必须了解的每一项事实。
- **“边界”**：该词与 DDD 的限界上下文含义重叠。请使用**接缝**或**接口**。

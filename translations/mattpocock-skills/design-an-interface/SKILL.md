# 设计接口

基于《软件设计的哲学》中的“设计两次”：你的第一个想法不太可能是最好的。生成多个截然不同的设计，然后进行比较。

## 工作流程

### 1. 收集需求

在设计之前，先了解：

- [ ] 这个模块解决什么问题？
- [ ] 调用者是谁？（其他模块、外部用户、测试）
- [ ] 关键操作有哪些？
- [ ] 是否有任何约束？（性能、兼容性、现有模式）
- [ ] 哪些内容应该隐藏在内部，哪些应该暴露？

询问：“这个模块需要做什么？谁会使用它？”

### 2. 生成设计（并行子代理）

使用 Task 工具同时启动 3 个以上的子代理。每个子代理都必须提出一种**截然不同**的方案。

```
每个子代理的提示词模板：

为以下内容设计一个接口：[module description]

需求：[gathered requirements]

此设计的约束：[assign a different constraint to each agent]
- 代理 1：“尽量减少方法数量——最多以 1-3 个方法为目标”
- 代理 2：“最大限度提高灵活性——支持多种使用场景”
- 代理 3：“针对最常见的场景进行优化”
- 代理 4：“借鉴 [specific paradigm/library]”

输出格式：
1. 接口签名（类型/方法）
2. 使用示例（调用者如何使用它）
3. 此设计在内部隐藏了什么
4. 此方案的权衡
```

### 3. 展示设计

展示每个设计时包括：

1. **接口签名**——类型、方法、参数
2. **使用示例**——调用者在实践中实际如何使用它
3. **它隐藏了什么**——保留在内部的复杂性

依次展示各个设计，以便用户在比较之前充分理解每种方案。

### 4. 比较设计

展示所有设计后，从以下方面进行比较：

- **接口简洁性**：方法更少、参数更简单
- **通用与专用**：灵活性与专注度
- **实现效率**：这种接口形态是否允许高效的内部实现？
- **深度**：用小型接口隐藏大量复杂性（好），还是用大型接口搭配单薄实现（差）
- **易于正确使用**与**易于误用**

使用文字而非表格讨论权衡。重点指出各个设计差异最大的地方。

### 5. 综合

最佳设计通常会结合多个方案中的优点。询问：

- “哪种设计最适合你的主要使用场景？”
- “其他设计中是否有值得纳入的元素？”

## 评估标准

源自《软件设计的哲学》：

**接口简洁性**：方法更少、参数更简单 = 更容易学习并正确使用。

**通用性**：无需修改即可处理未来的使用场景。但要警惕过度泛化。

**实现效率**：接口形态是否允许高效实现？还是会迫使内部实现变得别扭？

**深度**：用小型接口隐藏大量复杂性 = 深层模块（好）。用大型接口搭配单薄实现 = 浅层模块（应避免）。

## 反模式

- 不要让子代理生成相似的设计——必须确保设计截然不同
- 不要跳过比较——价值在于对比
- 不要实现——这里只关注接口形态
- 不要根据实现工作量进行评估

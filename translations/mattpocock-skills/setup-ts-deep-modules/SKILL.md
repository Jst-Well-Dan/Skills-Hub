# 设置 TypeScript 深模块

让此仓库中的每个包都成为一个**深模块**：用小型接口封装大量行为。包的公共表面是它的**入口点**——位于包根目录的文件——而子文件夹中的所有内容均被隐藏。此技能会安装 [dependency-cruiser](https://github.com/sverweij/dependency-cruiser)，配置确保入口点是唯一访问方式的规则，然后证明这些规则确实会生效。

有关相关术语（深模块、接口、接缝、深度），请运行 `/codebase-design` 技能——并在整个过程中使用其中的语言。

## 此配置强制执行的结构

```
src/packages/
  <name>/
    index.ts        ← 一个入口点（公共）。从包外部导入此文件。
    client.ts       ← 另一个入口点。包可以暴露多个入口点。
    lib/            ← 实现：对外隐藏，内部文件可自由相互导入。
    tests/          ← 就地放置的测试和固件（属于子文件夹，因此是私有的）。
```

公共表面是包的**根目录文件**——并非某个指定的 `index.ts`。按照约定，实现位于 `lib/`，测试位于 `tests/`，从而让每个包都采用相同的双文件夹结构。不过，规则本身是通用的：*任何*子文件夹中的*任何*内容都是私有的，因此永远不需要为新增文件夹扩展配置。

四条规则，全部为 `error`：

1. **入口点边界**——包外部的代码（应用代码或另一个包）只能导入该包的入口点（即根目录文件），绝不能导入其子文件夹中的任何内容。
2. **包内自由访问**——包自身的文件可以自由相互导入。
3. **测试通过入口点访问**——`<pkg>/tests/` 下的文件可以导入任何包的入口点以及自身 `tests/` 中的固件，但绝不能导入任何包子文件夹中的内部内容（即使是自身包也不行）。允许跨包集成测试，但不允许深层导入。
4. **禁止循环依赖**——不得存在依赖循环。

**使用入口点，而不是桶文件。** 因为公共表面是*每个*根目录文件，所以包可以暴露多个小型入口点（`index.ts`、`client.ts`、`server.ts`），而不必将所有内容汇集到一个巨大的 `index.ts` 中。不建议使用重新导出整个子树的桶文件——保持入口点精简，并将实现隐藏在子文件夹中。

分层（哪些包可以依赖哪些包）是一个*不同的*问题，配置中会保留一个注释掉的存根，供此仓库自行填写。

## 步骤

### 1. 检测环境

- **包管理器**——存在 `pnpm-lock.yaml` → pnpm，存在 `yarn.lock` → yarn，存在 `bun.lockb` → bun，否则使用 npm。下面的每条命令都使用检测到的包管理器（`pnpm`/`yarn`/`npm run`/`bunx`）。
- **包根目录**——如果存在 `src/`，则使用 `src/packages`，否则使用 `packages`。如果仓库已经明显采用其他约定，请向用户确认选择。
- **现有配置**——检查是否存在 `.dependency-cruiser.*` 文件。如果存在，**不要**覆盖它：将这四条规则和相关选项合并进去，并告诉用户添加了哪些内容。

**完成标准：** 已确定包管理器、包根目录和现有配置状态。

### 2. 安装 dependency-cruiser

使用检测到的包管理器，将 `dependency-cruiser` 安装为 devDependency。

**完成标准：** `dependency-cruiser` 已列入 `devDependencies`。

### 3. 编写配置

将 [`dependency-cruiser.config.cjs`](./dependency-cruiser.config.cjs) 复制到仓库根目录，并命名为 `.dependency-cruiser.cjs`。将 `PACKAGES_ROOT` 设置为步骤 1 中检测到的根目录。这些规则基于路径深度且与扩展名无关，因此无需调整其他内容。

**完成标准：** `.dependency-cruiser.cjs` 已存在，其中包含正确的 `PACKAGES_ROOT`，并且四条禁止规则均已配置。

### 4. 接入检查流程

- 添加 `lint:boundaries` 脚本：`depcruise <packages-root>`（或 `depcruise src`）。
- 将它并入仓库的总检查命令——即已经运行类型检查的命令（例如 `check` / `ci` / `validate` 脚本）。**不要**修改 `tsconfig`，也不要添加路径别名。
- 如果没有总检查脚本，则添加 `lint:boundaries`，并告诉用户将其纳入 CI。

**完成标准：** `lint:boundaries` 已存在，并且会与类型检查通过同一条命令运行。

### 5. 搭建示例包

创建并提交 `<packages-root>/example/`，将其作为可复制的模板：

- `index.ts`——一个入口点。导出一个委托给内部文件的函数（让该包明显是*深模块*，而非简单的透传层）。
- `lib/impl.ts`——位于**子文件夹**中的内部文件，由 `index.ts` 导入，无法从外部访问。
- `tests/example.test.ts`——**仅**导入 `../index`（入口点），并对公共函数进行断言。

告诉用户这是一个可以复制或删除的起始模板。

**完成标准：** 示例包已存在，通过根目录入口点暴露其行为，并将 `impl` 隐藏在子文件夹中。

### 6. 证明规则确实会生效

这是整个技能的完成标准——无法在违规时失败的配置毫无价值。

1. 运行 `lint:boundaries`。它必须在干净的示例上**通过**。
2. 临时向 `tests/example.test.ts` 添加一个深层导入（例如 `import { thing } from "../lib/impl"`）。再次运行 `lint:boundaries`——它必须**失败**，并报告 `tests-through-entrypoints`。
3. 撤销该深层导入。再次运行——它必须**通过**。

**完成标准：** 已观察到先通过、因深层导入而失败、再恢复通过的完整过程。如果步骤 2 没有失败，说明规则没有正确接入——完成前必须修复。

### 7. 记录约定

在包文件夹中编写 `README.md`（`<packages-root>/README.md`）——将它放在所约束的包旁边——内容包括：`src/packages/<name>/` 布局（根目录中的入口点、用于实现的 `lib/`、用于测试的 `tests/`）、“仅通过包的入口点（即其根目录文件）导入”，以及如何运行 `lint:boundaries`。明确**不建议使用桶文件**——应暴露多个小型入口点，而不是通过一个索引文件重新导出整个子树。内容保持精简，仅包含可复制的片段，以及分别用一个段落说明的四条规则。

然后从仓库的智能体指令文件中添加一个指向它的**上下文链接**——如果存在 `CLAUDE.md`，则使用它，否则使用 `AGENTS.md`（如果两者都不存在，则创建 `AGENTS.md`）。一行即可，例如：`包是深模块——在添加或导入包之前，请参阅 [src/packages/README.md](./src/packages/README.md)。` 这样智能体就能发现边界规则，而不是在违反规则后才意识到它的存在。

**完成标准：** `<packages-root>/README.md` 已存在且明确不建议使用桶文件，并且仓库的 `CLAUDE.md`/`AGENTS.md` 已链接到该文件。

## 注意事项

- 配置中的 `$1` 反向引用（dependency-cruiser 的分组匹配）使包能够访问自身内部内容，同时阻止外部访问——不要将其展开为每个包各自独立的规则。
- 公共和私有由**深度**决定：包的根目录文件是入口点；子文件夹中的任何内容都是私有的。约定的子文件夹是 `lib/`（实现）和 `tests/`，但规则并未硬编码它们——任何子文件夹都是私有的，因此新增文件夹永远不需要修改配置。添加入口点只需添加一个根目录文件——无需桶文件。
- 包是**扁平的**：根目录下只有一层直接子级。包的内部结构可以任意深度嵌套，但包内不能包含另一个包。
- 使用 `.cjs`（而不是 `.js`），这样即使仓库配置了 `"type": "module"`，配置中的 `module.exports` 也能正常工作。

# 改进代码库架构

揭示架构摩擦并提出**深化机会**——将浅层模块重构为深层模块。目标是提高可测试性和 AI 可导航性。

此命令以项目的领域模型为依据，并建立在一套共享的设计词汇之上：

- 运行 `/codebase-design` skill，以获取架构词汇（**module**、**interface**、**depth**、**seam**、**adapter**、**leverage**、**locality**）及其原则（删除测试、“interface 就是测试表面”、“一个 adapter = 假想 seam，两个 = 真实 seam”）。在每条建议中严格使用这些术语——不要偏移为 “component”、“service”、“API” 或 “boundary”。
- `CONTEXT.md` 中的领域语言为良好的 seam 命名；`docs/adr/` 中的 ADR 记录了此命令不应重新争论的决策。

## 流程

### 1. 探索

**扫描前先确定范围——YAGNI。** 深化一个 module 的收益在于让未来对它的修改变得更容易，因此应重点关注代码库中近期频繁变动的部分。先决定要查看*哪里*，然后再开始查看：

- 如果用户指定了方向——某个 module、子系统或痛点——就按该方向进行，并跳过下面的推断。
- 否则，向前回溯一段足够长的提交历史（`git log --oneline`），找出代码库中的热点——那些反复出现的文件和区域——并优先让这些路径引导你的注意力。如果变更较为分散，没有明确热点，则扩大搜索范围。

首先阅读项目的领域术语表（`CONTEXT.md`），以及与你将要处理的区域相关的所有 ADR。

然后使用 Agent 工具并设置 `subagent_type=Explore` 来遍历代码库。不要遵循僵化的启发式规则——自然地探索，并记录你感受到摩擦的地方：

- 理解一个概念时，是否需要在许多小 module 之间来回跳转？
- 哪些 module 是**浅层的**——interface 几乎与实现一样复杂？
- 哪些纯函数仅仅为了可测试性而被提取出来，但真正的缺陷却隐藏在它们的调用方式中（缺乏 **locality**）？
- 哪些紧密耦合的 module 会跨越其 seam 泄漏？
- 代码库中的哪些部分未经测试，或者很难通过其当前 interface 进行测试？

对任何疑似浅层的对象应用**删除测试**：删除它会集中复杂性，还是只会转移复杂性？你需要寻找的信号是“是的，会集中复杂性”。

### 2. 以 HTML 报告呈现候选项

将一个自包含的 HTML 文件写入操作系统临时目录，确保不会有任何内容落入仓库。通过 `$TMPDIR` 解析临时目录，若不可用则回退到 `/tmp`（Windows 上使用 `%TEMP%`），并写入 `<tmpdir>/architecture-review-<timestamp>.html`，确保每次运行都会生成新文件。为用户打开该文件——Linux 上使用 `xdg-open <path>`，macOS 上使用 `open <path>`，Windows 上使用 `start <path>`——并告知用户其绝对路径。

报告使用通过 CDN 加载的 **Tailwind** 进行布局和样式设计，并在图形、流程或时序能够可靠表达结构时，使用通过 CDN 加载的 **Mermaid** 绘制图表。将 Mermaid 与手工制作的 CSS/SVG 视觉效果结合使用——当关系呈图结构时（调用图、依赖关系、时序）使用 Mermaid；当你想要更具编辑感的效果时（质量图、剖面图、折叠动画），使用手工构建的 div/SVG。每个候选项都应包含一个**前后对比可视化**。要突出视觉表达。

为每个候选项渲染一张卡片，其中包含：

- **文件**——涉及哪些文件/module
- **问题**——当前架构为何会造成摩擦
- **解决方案**——用通俗语言描述将发生哪些变化
- **收益**——从 locality 和 leverage 的角度进行说明，并解释测试会如何改善
- **之前／之后图示**——并排展示、自定义绘制，用于说明浅层状态及深化后的状态
- **推荐强度**——`Strong`、`Worth exploring`、`Speculative` 之一，并以徽章形式呈现

报告结尾应包含一个**首要推荐**部分：说明你会优先处理哪个候选项，以及原因。

**使用 `CONTEXT.md` 的词汇描述领域，并使用 `/codebase-design` 的词汇描述架构。** 如果 `CONTEXT.md` 定义了 “Order”，就称其为 “Order intake module”——而不是 “FooBarHandler”，也不是 “Order service”。

**ADR 冲突**：如果某个候选项与现有 ADR 相冲突，只有在实际摩擦严重到值得重新审视该 ADR 时才将其提出。在卡片中清楚标记这一点（例如使用警告提示：_*“与 ADR-0007 冲突——但值得重新讨论，因为……”*_）。不要列出 ADR 所禁止的每一种理论重构。

完整的 HTML 脚手架、图示模式和样式指南请参阅 [HTML-REPORT.md](HTML-REPORT.md)。

此时不要提出 interface。文件写入完成后，询问用户：“你想探索其中哪一项？”

### 3. 深入追问循环

用户选择候选项后，运行 `/grilling` skill，与用户一起梳理决策树——约束、依赖关系、深化后 module 的形态、seam 背后包含什么，以及哪些测试会保留下来。

随着决策逐渐明确，副作用应当即时发生——在此过程中运行 `/domain-modeling` skill，使领域模型始终保持最新：

- **以 `CONTEXT.md` 中尚不存在的概念命名深化后的 module？** 将该术语添加到 `CONTEXT.md`。如果文件不存在，则按需创建。
- **在对话中使某个模糊术语变得更加精确？** 当场更新 `CONTEXT.md`。
- **用户以一个关键性理由否决候选项？** 提议创建 ADR，措辞为：_*“要我将此记录为 ADR 吗？这样未来的架构审查就不会再次建议它。”*_ 只有当未来的探索者确实需要知道这个理由，才能避免再次提出同一建议时，才进行此提议——跳过短期理由（“现在不值得做”）和不言自明的理由。
- **想探索深化后 module 的其他 interface？** 运行 `/codebase-design` skill，并使用其 design-it-twice 并行 sub-agent 模式。

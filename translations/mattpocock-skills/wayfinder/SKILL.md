一个尚显松散的想法出现了——它对单个智能体会话而言过于庞大，而且笼罩在迷雾之中：从这里通往**目的地**的道路尚不可见。寻路的重点是找到这条路，而不是直接冲向目的地。此技能会在仓库的问题跟踪器上将路线绘制成一张**共享地图**，然后逐一处理其中的**决策工单**——这些工单所要解决的是需要形成决策的问题，而不是待执行的构建工作切片——直到路线清晰可见。

每项工作的目的地各不相同，而为其命名就是绘图的第一步——它会塑造每一张工单。目的地可能是一份需要交接并迭代的规范、一个必须在规划开始前敲定的决策，或一项直接实施的变更，例如数据结构迁移。这张地图与领域无关——工程工作、课程内容，任何符合这种形式的工作都适用。

## 规划，而非执行

Wayfinder 默认用于**规划**：每张工单解决一个决策；当路线已经清晰——在有人着手执行之前不再有任何待决定事项——地图便告完成。想要直接动手执行，通常意味着你已经到达地图边缘，该进行交接了。某项工作可以在其 **Notes** 中覆盖这一默认行为——将执行也纳入地图本身——但若无此说明，应产出决策，而非交付物。

## 用名称引用

每张地图和工单都是一个问题，因此都有一个**名称**——即其标题。在所有供人阅读的内容中——叙述以及地图的 Decisions-so-far——都应使用该名称引用它，绝不能只使用裸 id、编号或 slug。满墙的 `#42, #43, #44` 难以辨认；名称则能让人一眼看懂。id 和 URL 并不会消失——名称会包裹其链接——但它们应置于名称*内部*，绝不能替代名称。

## 地图

地图是此仓库问题跟踪器上的单个问题，带有 `wayfinder:map` 标签——它是规范工件。地图的工单是它的子问题。

地图是**索引**，而非存储库。它列出已经作出的决策，并指向保存其详细内容的工单；一个决策只存在于一个位置——它的工单——因此地图绝不复述决策，只提供其要旨和链接。

**地图、其子工单、阻塞关系和前沿查询在物理上位于何处，取决于具体的跟踪器。** 问题跟踪器本应已经提供给你——如果没有，请运行 `/setup-matt-pocock-skills`。查阅跟踪器文档的“Wayfinding operations”部分，了解此仓库如何表达这些内容。如果未提供跟踪器，默认使用 local-markdown 跟踪器。

### 地图正文

这是整张地图的低分辨率视图，每个会话只加载一次。开放工单**不会**列在其中——它们是开放的子问题，通过查询找到。

```markdown
## Destination

<抵达这张地图终点时应呈现的状态——这项工作正在寻找通往何种规范、决策或变更的道路。一两行即可；每个会话在选择工单前都据此确定方向。>

## Notes

<领域；每个会话都应查阅的技能；这项工作的长期偏好>

## Decisions so far

- [<已关闭工单的标题>](link) — <答案的一行要旨>

## Not yet specified

<!-- 参见“战争迷雾”：尚无法创建工单的范围内迷雾；随着前沿推进而转化 -->
```

### 工单

每张工单都是地图的一个**子问题**；跟踪器的问题 id 就是它的身份标识。其正文是待解决的问题，规模应适合单个 100K token 的智能体会话：

```markdown
## Question

<此工单要解决的决策或调查>
```

每张工单都带有一个 `wayfinder:<type>` 标签——取值为 `research`、`prototype`、`grilling`、`task` 之一（参见[工单类型](#ticket-types)）。

会话必须在开展任何工作之前，**首先**将工单分配给负责推进地图的开发者，以此**认领**该工单，使并发会话跳过它。该受理人本身就是认领标记：开放且未分配的工单即为未认领。

阻塞关系使用跟踪器的**原生**依赖关系——这一点至关重要，因为它会在跟踪器自身的 UI 中以*可视化*方式呈现前沿，让人无需打开地图便能看到哪些工单可以处理。只有缺乏原生阻塞功能的跟踪器才退回使用正文约定。当一张工单的所有阻塞工单都已关闭时，它就是**未受阻塞的**；**前沿**则是所有开放、未受阻塞且未认领的子工单——即已知范围的边缘。

答案不属于正文——它会在解决工单时记录（参见[推进地图](#work-through-the-map)）。解决工单期间创建的资产应通过问题中的链接引用，而不是直接粘贴进去。

## 工单类型

每张工单都属于 **HITL** 或 **AFK**：HITL 表示人类参与其中，与能够代表自己表达意见的人类*共同*处理；AFK 则由智能体独立推进。HITL 工单只能通过这种实时交流解决；智能体绝不能代替人类完成交流中的人类一方（一个自行回答自己问题的 grilling 智能体已经破坏了此规则）。

- **Research**（AFK）：阅读文档、第三方 API 或知识库等本地资源，以找出某项决策正在等待的事实。由一个 `/research` **subagent** 解决。当需要当前工作目录之外的知识时使用。
- **Prototype**（HITL）：制作一个廉价、粗糙而具体的工件供人反馈，从而提高讨论的保真度——可以是大纲、粗略方案、存根，或通过 /prototype 技能制作的 UI/逻辑代码。将原型作为资产链接。关键问题是“它应该是什么样子”或“它应该如何表现”时使用。
- **Grilling**（HITL）：通过 /grilling 和 /domain-modeling 技能进行对话，每次提出一个问题。这是默认类型。
- **Task**（HITL 或 AFK）：在作出某个*决策*之前必须完成的人工工作——没有需要决定、制作原型或研究的内容，但在工作完成前讨论无法继续。例如注册某项服务以便评估其 API、配置访问权限，或移动数据以查看其结构。这是唯一一种重在*执行*而非决策的类型——它之所以有资格出现在地图中，是因为它能解除某个决策的阻塞，而不是因为它交付了目的地。智能体能够独立推进时便自行推进（AFK）；否则向人类提供精确的检查清单（HITL）。工作完成时即视为解决；答案应记录已完成的工作，以及后续工单所依赖的任何结果事实（凭据位置、新 URL、行数）。

## 战争迷雾

地图是*有意*不完整的：不要绘制你目前还看不见的内容。在现有工单之外是**战争迷雾**——你能隐约看出即将出现的决策和调查，却因它们依赖仍未解决的问题而无法准确界定。解决一张工单会驱散其前方的迷雾，将此时已经能够明确描述的内容逐一转化为新工单，直到通往目的地的路线清晰可见且没有任何工单剩余。

地图的 **Not yet specified** 部分用于记录这种模糊视图：疑似会出现的问题、以后需要重新审视的领域。它是通往目的地的尚未发现的前沿——这里的一切都在范围内，只是尚不够清晰，无法创建工单。视野允许多详细，就可以写得多详细或多宽泛；它同时也是路标，让阅读地图的协作者了解这项工作正朝哪里前进。

**迷雾还是工单？** 判断标准是你现在能否准确陈述问题——而*不是*你现在能否回答它。

- **创建工单的情况**：问题已经足够清晰——即使它受到阻塞，你暂时还无法采取行动。
- **放入 Not yet specified 的情况**：你还无法如此清晰地表达问题。不要预先将迷雾切成工单大小的片段：迷雾比工单更粗略；当前沿抵达时，同一片迷雾可能转化为多张工单，也可能一张都没有。

**Not yet specified** 不包含已经决定的事项（Decisions so far）、已有现行工单的事项，以及范围之外的事项（下一节）。

## 范围之外

迷雾只会聚集在*通往*目的地的方向上。目的地确定了范围，因此超出目的地的工作属于**范围之外**——它不是迷雾，也不应放入 **Not yet specified**。它在地图上拥有自己的 **Out of scope** 部分：记录你有意识地排除在*本次*工作之外的事项。决定某项内容放在这里的是范围，而非清晰程度。

范围之外的工作绝不会转化——前沿止于目的地——因此，只有重新划定目的地时它才会重新出现，而且应作为一项全新的工作，而非原工作的恢复。

将某项内容判定为范围之外是一项范围界定行为，而不是路线上的一步。如果一张已经存在的工单后来被发现位于目的地之外——可能是在绘图时错误纳入范围，或由某次解决结果揭示——应**关闭它**（关闭的工单明确不在前沿），并在 **Out of scope** 部分留下一行：概述其要旨以及被排除的原因，并链接到已关闭的工单。它不应出现在 **Decisions so far** 中；后者记录的是实际走过的路线——范围边界并不是路线上的一步。

## 调用

有两种模式。无论采用哪种模式，**每个会话都绝不能解决超过一张工单**——research 工单除外。

### 绘制地图

用户以一个松散想法调用。

1. **为目的地命名。** 运行一次 `/grilling` 和 `/domain-modeling` 会话，明确这张地图正在寻找通往何处的道路——规范、决策或变更。目的地决定范围，因此必须最先确定。
2. **绘制前沿。** 再次进行 grilling，但这次采用**广度优先**：横向展开整个空间，而不是深入任何一条线索，找出尚待解决的决策和当前即可采取的第一步。**如果没有发现任何迷雾**——通往目的地的道路已经清晰，整个旅程小到单个会话便能完成——则不需要地图。停下来询问用户希望如何继续。
3. **创建地图**（标签为 `wayfinder:map`）：填写 Destination 和 Notes，将 Decisions-so-far 留空，并在 **Not yet specified** 中勾勒迷雾。
4. **将目前能够明确描述的内容创建为工单**，作为地图的子问题——随后在**第二轮**连接阻塞边（问题必须先拥有 id 才能互相引用）。连接操作会将它们划分为前沿工单和受阻塞工单；所有尚无法明确描述的内容都留在迷雾中——即 **Not yet specified** 部分。
5. **启动 research 子智能体。** 针对刚创建的每一张 `research` 工单，启动一个 `/research` 子智能体并行解决；将其发现记录在一个用完即弃的 `research/<name>` 分支上，并在工单中提供上下文指针。
6. 停止——绘制地图就是一个会话的全部工作；该会话本身不解决任何工单。

### 推进地图

用户使用一张地图（URL 或编号）调用。工单是**可选的**——如果没有指定，则由你选择下一个决策，而不是让用户选择。

1. 加载**地图**——只加载低分辨率视图，而不是每张工单的正文。
2. 选择工单。如果用户指定了一张，就使用它；否则按顺序选择第一张前沿工单。**认领它**：在开展任何工作之前将其分配给自己。
3. 解决它——**按需放大查看**：仅在需要时获取任何相关工单或已关闭工单的完整正文；调用 `## Notes` 块中指定的技能。如有疑问，使用 `/grilling` 和 `/domain-modeling`。
4. 记录解决结果：将答案作为一条**解决评论**发布，**关闭**问题，并向地图的 Decisions-so-far **追加上下文指针**。
5. 添加新发现的工单（先创建，再连接）；将答案所明确化的任何迷雾转化为工单，并从 **Not yet specified** 中清除每一片已转化的迷雾，使其只存在于新工单中。如果答案揭示某张工单——当前工单或其他工单——位于目的地之外，应将其**判定为范围之外**，而不是作为路线的一部分予以解决。如果该决策使地图的其他部分失效，则更新或删除相应工单。

用户可能会并行处理未受阻塞的工单，因此应预期其他会话也在并发编辑跟踪器。

# 分诊

通过一套小型的分诊角色状态机处理项目议题跟踪器中的议题。

如果此仓库将外部拉取请求视为一种请求入口（请参阅议题跟踪器配置），分诊也涵盖这些请求：**PR 是附带代码的议题**——角色相同、状态相同、状态机相同，只有少数差异会在下文标注为“对于 PR”。根据跟踪器配置，将单独的 `#42` 解析为议题或 PR。

分诊期间发布到议题跟踪器的每条评论或议题都**必须**以以下免责声明开头：

```
> *这是由 AI 在分诊期间生成的。*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — 如何编写持久有效的代理简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) — `.out-of-scope/` 知识库的工作方式

## 角色

两个**类别**角色：

- `bug` — 某些功能已损坏
- `enhancement` — 新功能或改进

五个**状态**角色：

- `needs-triage` — 需要维护者评估
- `needs-info` — 正在等待报告者提供更多信息
- `ready-for-agent` — 规格已完全明确，可交由 AFK 代理处理
- `ready-for-human` — 需要由人类实现
- `wontfix` — 不会采取行动

对于 PR，相同状态应结合其附带代码来理解：`ready-for-agent` 表示已附上简报，代理应对该差异执行下一步操作；`ready-for-human` 表示已准备好由人类合并。

每个已分诊的议题都应恰好带有一个类别角色和一个状态角色。如果状态角色冲突，请指出冲突并先询问维护者，再执行任何其他操作。

这些是规范角色名称——议题跟踪器中实际使用的标签字符串可能不同。相关映射应当已经提供给你；如果没有，请运行 `/setup-matt-pocock-skills`。

状态转换：未标记的议题通常先进入 `needs-triage`；随后从该状态转为 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 会返回 `needs-triage`。维护者可以随时覆盖状态——如果状态转换看起来异常，请指出并在继续之前询问维护者。

## 调用方式

维护者调用 `/triage`，并使用自然语言描述他们的需求。解释请求并采取行动。示例：

- “向我展示所有需要我关注的内容”
- “我们看看 #42”（议题或 PR）
- “将 #42 移至 ready-for-agent”
- “有哪些内容已准备好供代理接手？”

## 显示需要关注的内容

查询议题跟踪器并按从旧到新的顺序展示三个分组：

1. **未标记** — 从未分诊。
2. **`needs-triage`** — 正在评估。
3. **自上次分诊备注以来报告者有新活动的 `needs-info`** — 需要重新评估。

当 PR 在范围内时，将外部 PR 纳入这些分组，并在每一行标注 `[PR]` 或 `[issue]`。发现流程只展示*外部* PR（跟踪器配置定义了哪些人属于外部人员）——协作者正在处理的 PR 不属于分诊工作。此筛选仅适用于发现流程；无论作者是谁，明确指定的 PR 始终都要进行分诊。

显示数量，并为每一项提供一行摘要。让维护者选择。

## 分诊特定议题或 PR

1. **收集上下文。** 阅读完整的议题或 PR（正文、评论、标签、作者、日期；对于 PR，还要阅读差异）。解析所有先前的分诊备注，以免再次询问已解决的问题。使用项目的领域术语表探索代码库，并遵守相关区域中的 ADR。针对代码库执行两项检查：(a) **冗余性**——按领域概念（而不只是请求中的措辞）搜索是否已有所请求行为的实现，并报告搜索过的位置。如果找到，则属于已实现的 `wontfix`（第 5 步）。(b) **先前拒绝记录**——阅读 `.out-of-scope/*.md`，并指出其中与此请求相似的内容。

2. **提出建议。** 向维护者说明你建议的类别和状态及其理由，并简要总结与该请求相关的代码库情况——包括它是否已经实现。等待指示。

3. **验证主张。** 在进行任何深入盘问之前，检查相关主张是否成立。对于 bug，根据报告者提供的步骤进行复现。对于 PR，确认差异确实实现了其声称的功能——检出该 PR，并运行相关测试或命令。报告结果：已确认（附代码路径）、失败，或细节不足（强烈表明应设为 `needs-info`）。经过确认的验证可以形成质量高得多的代理简报。

4. **深入盘问（如果需要）。** 如果请求需要进一步充实，请同时运行 `/grilling` 和 `/domain-modeling` 技能——每次提出一个问题，通过深入盘问使其成形，同时完善领域术语，并在决策确定时同步更新 `CONTEXT.md`/ADR。

5. **应用结果：**
   - `ready-for-agent` — 发布代理简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human` — 使用与代理简报相同的结构，但注明无法委派的原因（需要判断、外部访问、设计决策、手动测试）。
   - `needs-info` — 发布分诊备注（模板见下文）。
   - `wontfix` — 关闭，并根据*原因*发布相应评论：
     - **已经实现** — 该变更已经存在于代码库中。指出其所在位置；**不要**写入 `.out-of-scope/`（该知识库用于记录*被拒绝*的请求，而不是已构建的功能）。
     - **已拒绝（bug）** — 礼貌说明原因，然后关闭。
     - **已拒绝（enhancement）** — 写入 `.out-of-scope/`，在评论中链接到该内容，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage` — 应用该角色。如果已有部分进展，可以选择添加评论。

## 快速状态覆盖

如果维护者说“将 #42 移至 ready-for-agent”，请信任他们并直接应用该角色。确认你即将执行的操作（角色变更、评论、关闭），然后执行。跳过深入盘问。如果在未进行深入盘问会话的情况下移至 `ready-for-agent`，请询问他们是否希望编写代理简报。

## Needs-info 模板

```markdown
## 分诊备注

**目前已确定的内容：**

- 要点 1
- 要点 2

**我们仍需要你（@reporter）提供的内容：**

- 问题 1
- 问题 2
```

将在深入盘问期间解决的所有内容记录在“目前已确定的内容”下，以免工作成果丢失。问题必须具体且可操作，不能只是“请提供更多信息”。

## 恢复之前的会话

如果议题或 PR 中存在先前的分诊备注，请阅读这些备注，检查报告者是否已回答任何尚未解决的问题，并在继续之前展示更新后的情况。不要再次询问已解决的问题。

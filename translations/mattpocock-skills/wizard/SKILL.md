# 向导

**向导**是一个 bash 脚本，它逐步引导用户完成某个手动流程；这种流程手工执行很繁琐，每次都重新向 AI 解释也同样麻烦。它会打开每个 URL，准确说明要点击什么、复制什么，收集相应的值，将其写入正确的位置（`.env`、GitHub 密钥），在每个阶段进行确认，并显示剩余进度。它可以配置第三方服务、执行一次性迁移，或将项目从一种状态转换为另一种状态。

出色的用户体验已经由 [template.sh](template.sh) 实现——包括带剩余时间的进度显示、确认关卡、跨平台 URL 打开（包括 WSL）、隐藏式密钥输入、幂等的 `.env` 更新插入、`gh secret`/`gh variable` 写入以及结束摘要。**你的工作只是明确流程范围并编写各个阶段。** `STAGES` 标记上方的库代码在每个向导中都完全相同；这种一致性正是设计目的——绝不要手动编辑它。

默认情况下，向导是临时性的——为一次运行而构建，保存到临时路径或 `scripts/` 路径，任务完成后删除。只有当用户希望在仓库中保留一条可重复执行的配置路径时，才提交它。

## 流程

### 1. 明确流程范围

梳理用户必须执行的每个手动步骤，以及过程中需要收集的每个值。先阅读仓库——不要在毫无背景的情况下直接询问：

- 对于配置：检查 `.env`、`.env.example`、`.env.*`、`README`、`docker-compose*`、框架配置和 `.github/workflows/*`（每个 `secrets.*` / `vars.*` 引用都是向导必须生成的值）。
- 对于迁移或转换：检查当前状态、目标状态以及两者之间不可逆的操作。

然后向用户展示按顺序排列的阶段列表，以及每个阶段产生的值，并请求确认——用户可能会添加、删除或重新排序阶段。

**完成标准：** 每个阶段都已按顺序命名，并且对于每个收集的值，你都知道：(a) 用户从哪里获取它；(b) 它会被写到哪里（`.env`、GitHub 密钥、两者，或不写入任何位置——某些阶段仅执行操作）；以及 (c) 它是否为密钥（隐藏式输入）或公开值。

### 2. 规划每个阶段的操作路径

对于每个阶段，写出用户需要遵循的准确路径：要打开哪个 URL、在那里执行什么操作、值显示在哪里、它会填入哪个变量——例如“控制面板 → 开发者 → API 密钥 → 显示测试密钥 → 复制”。如果你并不真正了解当前界面或确切命令，请如实说明并询问用户或查阅文档——绝不要虚构可能并不存在的步骤。

**完成标准：** 每个阶段都能落实为具体说明，让一个完全不了解情况的人也可以照着完成。

### 3. 编写向导

将 `template.sh` 复制到目标路径。按照依赖顺序，将示例阶段替换为每个步骤对应的一个 `stage`。使用库提供的辅助函数——`stage`、`say`/`step`、`open_url`、`ask`/`ask_secret`、`write_env`、`set_secret`/`set_var`、`pause`/`confirm`——并为 `TOTAL_STAGES` 和 `TOTAL_MINUTES` 设置诚实的估算值（这些值用于驱动剩余时间显示）。

保持模板设定的标准：在请求用户输入值之前先打开相应 URL；任何密钥都使用 `ask_secret`；每个需要持久化的值都使用 `write_env`；仅对 CI 实际需要的值使用 `set_secret`；执行任何不可逆操作前都使用 `confirm`。每个 `stage` 都会清屏，因此屏幕上只显示当前步骤——每个阶段只应聚焦一项任务，以免用户需要的信息滚出屏幕。不要修改标记上方的库代码。

### 4. 验证并交付

- 执行 `bash -n <script>`；如果 `shellcheck` 可用，也运行它。
- 执行 `chmod +x <script>`。
- 不要亲自端到端运行脚本——它会打开浏览器并阻塞等待用户输入。改为进行静态追踪：确认步骤 1 中的每个值都已被收集，并写入步骤 1 指定的位置；确认每个 `set_secret` 名称都与 CI 中的某个 `secrets.*` 引用完全一致。
- 告诉用户如何运行它。如果它是一条可重复执行的配置路径，请提交它，并从 README 链接到该脚本，让下一个人直接运行脚本，而不是询问 AI。

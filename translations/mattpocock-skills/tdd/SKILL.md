# 测试驱动开发

TDD 是红 → 绿循环。本技能是一份参考指南，旨在让该循环产出值得保留的测试：什么是好的测试、测试应放在哪里、反模式，以及循环的规则。每一节都适用于每一次循环——应在循环之前和过程中查阅，而不是事后查阅。

探索代码库时，请阅读 `CONTEXT.md`（如果存在），以确保测试名称和接口词汇与项目的领域语言一致，并遵循所涉及区域中的 ADR。

## 什么是好的测试

测试应通过公共接口验证行为，而不是实现细节。代码可以彻底改变，测试不应随之改变。好的测试读起来就像规格说明——“用户可以使用有效购物车结账”能准确说明具备什么能力——并且能经受重构，因为它不关心内部结构。

有关示例，请参阅 [tests.md](tests.md)；有关模拟指南，请参阅 [mocking.md](mocking.md)。

## 接缝——测试应放在哪里

**接缝**是进行测试的公共边界：你可以在不触及内部实现的情况下观察行为的接口。测试应位于接缝处，绝不能针对内部实现。

**仅在预先商定的接缝处进行测试。** 在编写任何测试之前，先写下要测试的接缝，并与用户确认。不得在未经确认的接缝处编写测试。你无法测试一切——预先就接缝达成一致，才能让测试工作集中在关键路径和复杂逻辑上，而不是每个边缘情况上。

请询问：“公共接口是什么，我们应该测试哪些接缝？”

## 反模式

- **与实现耦合**——模拟内部协作者、测试私有方法，或通过旁路进行验证（绕过接口直接查询数据库）。其明显特征是：重构时行为并未改变，测试却失败了。
- **同义反复**——断言以与代码相同的方式重新计算预期值（`expect(add(a, b)).toBe(a + b)`、以相同方式手工推导的快照、断言某个常量等于其自身），因此它必然通过，永远无法与代码产生分歧。预期值必须来自独立的事实来源——已知正确的字面值、完整演算过的示例或规格说明。
- **水平切片**——先编写所有测试，再编写所有实现。批量测试验证的是_想象中_的行为：你测试的是事物的_形状_，而不是面向用户的行为；测试会对真实变化变得不敏感；而且在理解实现之前，你就已经受制于测试结构。应改用**垂直切片**——一个测试 → 一个实现 → 重复；每个测试都是一枚**曳光弹**，根据上一个循环带来的认识作出响应。

## 循环规则

- **先红后绿。** 先编写失败的测试，然后只编写足以使其通过的代码。不要预判未来的测试，也不要添加推测性的功能。
- **一次一个切片。** 每个循环只处理一个接缝、一个测试和一个最小实现。
- **重构不属于该循环。** 它属于审查阶段（参见 `code-review` 技能），而不是红 → 绿实现循环。

# 测试驱动开发

TDD 是红 → 绿循环。本技能是让该循环产出值得保留的测试的参考指南：什么是好的测试、测试应放在哪里、反模式以及循环规则。每次循环都应应用每一节的内容——在循环之前和期间查阅，而不是在循环之后。

探索代码库时，请阅读 `CONTEXT.md`（如果存在），使测试名称和接口术语与项目的领域语言保持一致，并遵循所修改区域中的 ADR。

## 什么是好的测试

测试应通过公共接口验证行为，而非实现细节。代码可以彻底改变，但测试不应随之改变。好的测试读起来像规范——“用户可以使用有效的购物车结账”准确说明了具备什么能力——并且能够经受重构，因为它不关心内部结构。

示例请参阅 [tests.md](tests.md)，模拟指南请参阅 [mocking.md](mocking.md)。

## 接缝——测试应放在哪里

**接缝**是进行测试的公共边界：你可以在不深入内部的情况下观察行为的接口。测试应位于接缝处，绝不针对内部实现。

**仅在预先约定的接缝处进行测试。** 在编写任何测试之前，先写下要测试的接缝并与用户确认。不得在未经确认的接缝处编写测试。你无法测试一切——预先约定接缝，才能让测试工作集中在关键路径和复杂逻辑上，而不是每个边缘情况。

请问：“公共接口是什么，我们应该测试哪些接缝？”

## 反模式

- **与实现耦合**——模拟内部协作者、测试私有方法，或通过旁路进行验证（例如查询数据库，而不是使用接口）。其典型表现是：行为没有改变，但重构会导致测试失败。
- **同义反复**——断言使用与代码相同的方式重新计算期望值（`expect(add(a, b)).toBe(a + b)`、以相同方式手工推导出的快照、断言某个常量等于自身），因此测试从构造上就必然通过，永远无法与代码产生分歧。期望值必须来自独立的事实来源——已知正确的字面值、经过推演的示例或规范。
- **水平切片**——先编写所有测试，再编写所有实现。批量测试验证的是_想象出来的_行为：你测试的是事物的_形状_，而不是面向用户的行为；测试会对真实变化变得不敏感；而且你会在理解实现之前就确定测试结构。应改用**垂直切片**——一个测试 → 一个实现 → 重复；每个测试都是一枚**曳光弹**，根据上一个循环带来的认知作出响应。

## 循环规则

- **先红后绿。** 先编写失败的测试，然后只编写足以使其通过的代码。不要预判未来的测试，也不要添加推测性的功能。
- **每次只完成一个切片。** 每个循环只处理一个接缝、一个测试和一个最小实现。
- **重构不属于该循环。** 它属于审查阶段（参阅 `review` 技能），而非红 → 绿实现循环。

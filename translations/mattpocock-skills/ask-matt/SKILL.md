# 问 Matt

你不可能记住每一个技能，所以问问吧。

**流程（flow）**是一条贯穿多个技能的路径。大多数路径沿着一条**主流程**前进，并有两个**入口匝道**汇入其中。其余技能要么独立运行，要么作为底层的词汇体系。

## 主流程：想法 → 交付

这是大多数工作的必经路线。你有一个想法，并希望把它构建出来。

1. **`/grill-with-docs`** — 通过访谈打磨想法。当你**已有代码库**时从这里开始：它是有状态的，会将了解到的内容保存在 `CONTEXT.md` 和 ADR 中。（没有代码库？使用 `/grill-me` — 参见“独立技能”。两者都运行相同的 `/grilling` 基础能力；`grill-with-docs` 会留下书面记录。）
2. **分支 — 能否在对话中解决所有问题？** 如果某个问题需要通过可运行的内容来回答（状态、业务逻辑，或必须亲眼看到的 UI），就绕道制作原型，并在往返两个方向上都使用 **`/handoff`** 衔接（参见“跨会话”）：
   - 用 **`/handoff`** 导出，然后针对该文件开启一个全新会话，
   - 用 **`/prototype`** 通过一次性代码回答问题，
   - 用 **`/handoff`** 将了解到的内容传回，并在原始想法线程中引用它。
3. **分支 — 这是一个需要多个会话完成的构建吗？**
   - **是** → 使用 **`/to-spec`**（将线程转换为规格说明），然后使用 **`/to-tickets`** 将其拆分为示踪弹式工单，每个工单都声明自己的**阻塞边**。在本地跟踪器中，每个工单对应 `.scratch/<feature>/issues/` 下的一个文件，由人工按阻塞项优先的顺序处理；在真正的跟踪器中，这些边会变成原生阻塞链接，因此只要某个工单的阻塞项全部完成，就可以领取它 — 为每个工单启动 **`/implement`**，并且**在每个工单之间清除上下文**。
   - **否** → 就在这里、同一个上下文窗口中运行 **`/implement`**。

   无论哪种情况，**`/implement`** 都会在内部驱动 **`/tdd`** 来构建每个问题 — 每次完成一个红灯到绿灯的切片 — 然后在提交之前运行 **`/code-review`** 收尾，对差异进行双轴审查（标准 + 规格）。如果你只想以测试优先的方式构建一个具体行为，而不需要完整规格，请单独使用 **`/tdd`**；每当你想以某个固定基准审查分支或 PR 时，请单独使用 **`/code-review`**。

### 上下文卫生

将步骤 1–3 保持在**一个不中断的上下文窗口**中 — 在 `/to-tickets` 完成之前不要压缩或清除上下文 — 这样访谈、规格和工单都会建立在同一套思路之上。之后，每次 `/implement` 都从全新上下文开始，依据工单开展工作。

这里的限制是 **[智能区间](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能保持敏锐推理能力的窗口范围（在最先进的模型上约为 120k tokens）。如果一个会话在到达 `/to-tickets` 之前就接近这个限制，不要在能力下降的情况下强行继续 — 使用 `/handoff`，然后在新线程中继续。

## 入口匝道

一种会产生工作、随后汇入主流程的起始情境。

- **Bug 和请求不断堆积** → **`/triage`**。它让问题依次经过各个分诊角色，并产出可供代理直接处理的问题，之后由 **`/implement`** 接手。

  分诊只适用于**并非由你创建**的问题 — Bug 报告、传入的功能请求，以及任何未经整理而到达的内容。由 `/to-tickets` 生成的工单已经可以供代理直接处理，因此**不要对它们进行分诊**。

- **某些东西坏了** → **`/diagnosing-bugs`**。用于处理棘手问题：乍看之下无法解决的 Bug、间歇性出现的不稳定故障，或潜入两个已知正常状态之间的回归问题。在建立**紧密反馈循环**之前，它拒绝进行理论推测 — 即先找到一条能够在*这个* Bug 上稳定报错的命令 — 然后通过回归测试完成修复。当真正的发现是缺少一个适合锁定该 Bug 的良好接缝时，它会在事后分析中移交给 **`/improve-codebase-architecture`**。

- **庞大而模糊的工作 — 一个绿地项目或大型功能构建，大到无法在一个会话中完成** → **`/wayfinder`**，这是这里对认知要求最高的流程。当从当前位置通往目标的道路尚不可见时，它会在问题跟踪器上绘制由**决策工单**组成的**共享地图**，并逐一解决它们 — 产出的是**决策，而非交付物** — 直到迷雾退去、道路清晰。**`/grill-with-docs`** 用于打磨你能在一个会话中掌握的想法，而 wayfinder 则用于处理你无法在一个会话中掌握的想法 — 它更慢、密度也更高，因此只应在确实需要时使用，绝不要用于范围明确的功能。

  当地图变得清晰时，**它会移交，而不会构建**：在 **`/to-spec`** 处汇入主流程，将地图中相互链接的决策收束为可构建的计划，然后照常运行 `/to-tickets` 和 `/implement`。将地图直接送入 `/implement` 会跳过这一收束过程，并丢弃相互链接的细节 — 只有当这项工作最终确实很小时，才直接进入 `/implement`。

## 代码库健康

这不是功能开发 — 而是维护工作。

- **`/improve-codebase-architecture`** — 每当有空闲时间时运行它，以保持代码库适合代理操作。它会发现**深化机会**；选中其中一个就会*生成一个想法*，你可以将其带入主流程中的 `/grill-with-docs`。它是寻找候选项的勘察工具；**`/codebase-design`**（见下文）则是用于设计选中候选项的工作台。

## 底层词汇体系

两个由模型调用、运行在其他技能*底层*的参考体系 — 每个体系都是其词汇的唯一事实来源。当问题出在**措辞**而非流程时，可以直接调用它们；也可以让上面的技能自行引入它们。

- **`/domain-modeling`** — 打磨项目的*领域*语言：质疑模糊术语，解决一词多义的问题（例如 "account" 同时承担三种职责），并将难以逆转的决策记录为 ADR。这是 `/grill-with-docs` 为保持 `CONTEXT.md` 作为整洁术语表而推动实施的主动纪律。
- **`/codebase-design`** — 用于设计模块*形态*的深模块词汇体系（模块、接口、深度、接缝、适配器、杠杆效应、局部性）：在清晰的接缝处，通过小型接口封装大量行为。`/tdd` 和 `/improve-codebase-architecture` 都使用这套语言。

## 跨会话

- **`/handoff`** — 当线程已满，或你需要分出一条支线时（例如进入一个 `/prototype` 会话），它会将对话压缩到一个 Markdown 文件中。你不会在原处继续 — 而是**开启一个新会话并引用该文件**，以便跨会话携带上下文。它是上下文窗口之间双向通行的桥梁。当你想要一个**全新会话**，但又需要**保留当前对话**时使用它。
- **`/compact`**（内置）— 留在**同一个对话**中，同时让之前的轮次得到摘要。在**阶段之间的有意停顿处**使用它，前提是你不介意丢失逐字历史记录。不要在阶段中途压缩 — 代理可能会迷失方向。`/handoff` 创建分支；`/compact` 延续当前对话。

## 独立技能

完全位于主流程之外。

- **`/grill-me`** — 与 `/grill-with-docs` 相同的不懈访谈，但适用于你**没有代码库**的情况。它是无状态的：不会在本地保存任何内容，也不会构建 `CONTEXT.md`。用它来打磨任何不属于某个仓库的计划或设计。
- **`/prototype`** — 一个小型的一次性程序，用于回答单个设计问题：这种状态模型感觉是否合适，或者这个 UI 应该是什么样子。从第一天起就是一次性的 — 保留答案，删除代码。它是主流程步骤 2 中的绕行路线，但只要某个设计问题难以在纸面上确定，都可以使用它。
- **`/research`** — 将阅读资料的工作委派给一个**后台代理**：它依据**一手来源**调查问题，然后在仓库中留下一个带引用的 Markdown 文件。在它阅读时，你可以继续工作。它产出的文件可以带入主流程中的 `/grill-with-docs` — 研究为思考提供素材，但不能取代思考。
- **`/teach`** — 使用当前目录作为有状态工作区，跨多个会话学习一个概念。
- **`/writing-great-skills`** — 用于出色编写和编辑技能的参考资料。

## 前置条件

**`/setup-matt-pocock-skills`** — 在第一次运行工程流程之前执行，用于配置其他技能所依赖的问题跟踪器、分诊标签和文档布局。也支持自定义问题跟踪器。

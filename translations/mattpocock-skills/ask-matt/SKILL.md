# 询问 Matt

你不可能记住每项技能，所以问一问。

**流程**是贯穿多项技能的一条路径。大多数路径沿着一条**主流程**运行，另有两个**入口匝道**汇入其中。其他内容要么是独立技能，要么是运行在底层的词汇层。

## 主流程：想法 → 交付

大多数工作的必经之路。你有一个想法，并希望将它构建出来。

1. **`/grill-with-docs`** — 通过访谈打磨想法。当你**已有代码库**时从这里开始：它是有状态的，会将学到的内容保存在 `CONTEXT.md` 和 ADR 中。（没有代码库？使用 `/grill-me` — 参见“独立技能”。两者都运行相同的 `/grilling` 基础能力；`grill-with-docs` 会留下书面记录。）
2. **分支 — 能否在对话中解决所有问题？** 如果某个问题需要通过可运行的内容来回答（状态、业务逻辑，或必须亲眼看到的 UI），则绕道构建原型，并在两个方向上都通过 **`/handoff`** 衔接（参见“跨会话衔接”）：
   - 使用 **`/handoff`** 导出，然后基于该文件开启一个新会话，
   - 使用 **`/prototype`** 通过一次性代码回答问题，
   - 使用 **`/handoff`** 将学到的内容传回，并在原始想法线程中引用它。
3. **分支 — 这是一个跨多个会话的构建任务吗？**
   - **是** → **`/to-prd`**（将线程转化为 PRD）→ **`/to-issues`**（将 PRD 拆分为可独立领取的问题）。由于这些问题彼此独立，因此应在每个问题之间**清除上下文**：为每个问题开启一个新会话，并将 PRD 和当前要处理的单个问题传给 **`/implement`**，以启动实现。
   - **否** → 就在这里、在同一个上下文窗口中运行 **`/implement`**。

   无论采用哪条路径，**`/implement`** 都会在内部驱动 **`/tdd`** 来构建每个问题 — 每次完成一个红灯—绿灯切片 — 然后在提交前运行 **`/code-review`** 收尾，对差异进行双轴审查（标准 + 规格）。当你只想以测试优先的方式构建一个具体行为，而不需要完整规格时，可以单独使用 **`/tdd`**；当你想基于某个固定基准审查分支或 PR 时，可以单独使用 **`/code-review`**。

### 上下文卫生

让步骤 1–3 始终处于**同一个不间断的上下文窗口**中 — 在 `/to-issues` 完成之前不要压缩或清除上下文 — 这样访谈、PRD 和问题都能建立在同一套思考之上。随后，每次 `/implement` 都从全新上下文开始，依据对应问题开展工作。

这里的限制是**[智能区间](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能保持敏锐推理能力的窗口（在最先进的模型上约为 120k tokens）。如果会话在执行 `/to-issues` 之前就接近这一上限，不要在能力退化的状态下强行继续 — 使用 `/handoff`，然后在新线程中继续。

## 入口匝道

一种先产生工作、再汇入主流程的起始情境。

- **错误和请求不断积压** → **`/triage`**。它让问题经过各个分诊角色，并生成可供智能体直接处理的问题，之后由 **`/implement`** 接手。

  分诊仅用于**并非由你创建**的问题 — 错误报告、传入的功能请求，以及任何以原始状态到达的内容。由 `/to-issues` 生成的问题已经可以供智能体直接处理，因此**不要对它们进行分诊**。

- **有东西坏了** → **`/diagnosing-bugs`**。用于棘手的问题：乍看之下难以解决的错误、间歇性失败，以及在两个已知良好状态之间悄然引入的回归。它拒绝在建立**紧密反馈循环**之前提出理论 — 即用一条命令就能让*这个*错误稳定变红 — 然后通过回归测试完成修复。如果事后分析发现真正的问题在于缺少一个能够可靠锁定该错误的良好接缝，它会将任务移交给 **`/improve-codebase-architecture`**。

## 代码库健康状况

这不是功能开发 — 而是维护。

- **`/improve-codebase-architecture`** — 只要有空闲时间，就运行它来保持代码库适合智能体操作。它会发现**深化机会**；选择其中一个，就会_生成一个想法_，你可以从 `/grill-with-docs` 开始将其带入主流程。它是寻找候选项的勘察工具；**`/codebase-design`**（见下文）则是设计所选候选项的工作台。

## 底层词汇

两个由模型调用、运行在其他技能*底层*的参考技能 — 每个都是其词汇体系的唯一事实来源。当问题出在**用词**而非流程时，可以直接使用它们；也可以让上面的技能自行引入它们。

- **`/domain-modeling`** — 打磨项目的*领域*语言：质疑模糊术语、解决含义过载的词语（例如让“account”承担三种职责），并将难以逆转的决策记录为 ADR。这是 `/grill-with-docs` 用来保持 `CONTEXT.md` 作为清晰术语表的主动实践。
- **`/codebase-design`** — 用于设计模块*形态*的深模块词汇体系（模块、接口、深度、接缝、适配器、杠杆效应、局部性）：在一个清晰接缝处，通过一个小型接口隐藏大量行为。`/tdd` 和 `/improve-codebase-architecture` 都使用这套语言。

## 跨会话衔接

- **`/handoff`** — 当一个线程已满，或你需要分支出去（例如进入一个 `/prototype` 会话）时，它会将对话压缩到一个 markdown 文件中。你不会在原处继续 — 而是**开启一个新会话并引用该文件**，以便跨上下文窗口传递上下文。它是上下文窗口之间的双向桥梁。当你需要一个**全新会话**，同时又要**保留当前对话**时使用它。
- **`/compact`**（内置）— 留在**同一段对话**中，同时让早期轮次被总结。在**阶段之间有意安排的停顿点**使用它，前提是你不介意丢失逐字历史。不要在阶段中途压缩 — 智能体可能会迷失方向。`/handoff` 创建分支；`/compact` 延续当前对话。

## 独立技能

完全位于主流程之外。

- **`/grill-me`** — 与 `/grill-with-docs` 相同的不懈访谈，但用于你**没有代码库**的情况。它是无状态的：不会在本地保存任何内容，也不会构建 `CONTEXT.md`。使用它来打磨任何不依附于仓库的计划或设计。
- **`/prototype`** — 一个小型的一次性程序，用于回答单个设计问题：这个状态模型是否合适，或者这个 UI 应该是什么样子。从第一天起就把它当作一次性内容 — 保留答案，删除代码。它是主流程步骤 2 中的绕行路径，但只要某个设计问题难以在纸面上解决，都可以使用它。
- **`/teach`** — 使用当前目录作为有状态工作区，跨多个会话学习一个概念。
- **`/writing-great-skills`** — 用于良好编写和编辑技能的参考资料。

## 前置条件

**`/setup-matt-pocock-skills`** — 在首次运行工程流程之前执行它，以配置其他技能所依赖的问题跟踪器、分诊标签和文档布局。自定义问题跟踪器同样适用。

# 代码库去低质化

使用此技能，在基本保持当前产品原样的同时，将仓库从“能用但令人痛苦”转变为由小型、类型明确、经过测试且易于维护的模块组成、具备产品形态的集合。将其视为第一次可维护性/产品化改造，而不是更广泛的生产就绪计划。

## 边界

此技能用于结构性可维护性：代码组织、类型化边界、测试、功能文件夹、API 整合、文件规模缩减、样式清理和审计证据。

不要将范围扩展为完整的生产就绪计划。可观测性/日志计划、安全审查、合规、事件响应、SLO、运行手册、密钥管理状况、渗透测试和深度可靠性工程应由后续独立技能负责，除非用户明确要求加入一项小型的支持性变更。

## 操作原则

- 首先保留行为。以小而可逆的切片改进架构。
- 每项决策都应基于仓库事实：文件大小、依赖关系图、测试、运行时形态、API 表面、用户工作流、部署限制和当前脏工作树。
- 保持文件便于 AI 编辑：优先采用大约 300-500 行以内的聚焦模块、明确的功能文件夹、稳定的兼容性桶文件以及范围窄的测试。
- 未经许可，绝不重写用户正在维护的区域。如果其他代理/用户正在编辑某个表面，则对其进行审计或绕开它开展工作。
- 条件允许时，对独立分析或隔离的编辑切片使用并发子代理，但应由一名负责人合并并验证整个代码树。
- 在状态正常的检查点提交。不要让迁移变成一个无法审查的巨型差异。
- 以证据收尾：在本地提供迁移审计微型网站，其中包含可视化内容、指标、风险和前后对比解读。

## 工作流

### 1. 确立产品形态

在制定计划前，快速执行一次非修改式探索：

- 查找包脚本、应用入口点、API 路由、部署配置、测试工具、类型配置和当前 git 状态。
- 测量最大的文件和顶层目录。
- 仅在影响安全重构的范围内，识别用户关键工作流、部署约束、数据持久化、身份验证、提供商集成和高成本操作。
- 阅读近期提交和文档，以免撤销正在进行的工作。

如果仓库已上线或面向用户，默认采用保留兼容性的迁移和回滚路径。

有关更深入的探索提示和命令，请参阅 [analysis-checklist.md](references/analysis-checklist.md)。

### 2. 编写决策完备的迁移计划

生成一份可持续演进、但足够完整以供另一个代理执行的计划：

- 目标、成功标准、明确的非目标、当前禁止触碰的区域和风险态度。
- 按影响范围和验证可信度排序的分阶段切片。
- 公共接口和兼容性承诺。
- 测试计划：当前基线、需要新增的测试、e2e/视觉检查、部署冒烟测试。
- 并发图：哪些工作者可以独立编辑，以及哪些文件必须由单一负责人维护。
- 检查点策略：何时提交、推送、部署和审计。

仅对无法从仓库中发现的产品权衡使用 `request_user_input`。

### 3. 建立基线安全网

在进行大范围编辑前：

- 在可行的情况下，运行现有的类型检查、单元测试、构建和 e2e。
- 如果缺少测试，在重构行为之前添加或规划最小但高价值的特征测试。
- 仅添加保障重构安全所需的最低限度诊断或可恢复错误处理；将全面的日志/可观测性计划推迟到独立的生产就绪技能中。
- 为核心 UX 表面截取屏幕截图；对于浏览器 e2e，在可行的情况下目视检查移动端、桌面端、平板端和超宽屏输出。

### 4. 以状态正常的小切片执行

有条不紊地推进迁移：

- 首先拆分最大、变更最频繁的文件，并通过桶文件/外观接口保留旧的导入表面。
- 在 UI 外壳之前提取纯模型/辅助函数。
- 当 API/提供商数据跨越信任边界时，将无类型或临时拼凑的边界转换为共享领域类型和运行时验证。
- 只有在测试固定响应形态后，才能整合重复的服务器/API 函数。
- 逐个表面迁移样式；仅在屏幕截图检查后移除旧选择器。
- 保持每个切片足够小，以便测试、审查和回滚。

并发数量不得超过用户批准的子代理数量。将工作者分配到测试、CSS、服务器辅助函数、前端功能提取、类型边界和审计工具等独立表面。不要让子代理并发编辑相同的热点文件。

有关执行规则和工作者提示，请参阅 [execution-playbook.md](references/execution-playbook.md)。

### 5. 验证、提交、部署

在每个检查点：

- 运行针对已触及表面的窄范围测试。
- 提交前运行更广泛的类型检查/构建/单元测试。
- 当 UI 或生产流程发生变化时，在部署前运行 e2e/视觉冒烟测试。
- 仅提交预期文件；保留用户不相关的脏工作。
- 仅在约定的发布门禁全部通过时部署，或者明确标记已知风险发布。

### 6. 以迁移审计微型网站收尾

迁移稳定后，生成一个静态 HTML 审计微型网站，回答以下问题：

- 可维护性是否有所改善？
- 增加/删除了多少 LOC/文件？
- 哪些文件的大小显著缩减？
- 结构如何演变？
- 测试、类型、API 函数、部署风险和 UX 覆盖发生了哪些变化？
- 还存在哪些成本和风险？

在本地提供该微型网站，并返回可点击的 `localhost` 或 `127.0.0.1` URL。用户更喜欢直接在 Codex 中打开微型网站制品，而不是只收到文件路径。

有关指标、结构和验证，请使用 [audit-microsite.md](references/audit-microsite.md)。

## 质量标准

一次成功的代码库去低质化迁移应具备：

- 热点路径中不存在无人负责的巨型文件。
- 清晰的功能/提供商/领域文件夹。
- 前端/后端/API/提供商数据之间具有类型化模块边界。
- 测试物有所值，并且可以窄范围运行。
- 具备生产形态的本地/开发部署检查。
- 最终审计制品如实说明收益、成本和残余风险。

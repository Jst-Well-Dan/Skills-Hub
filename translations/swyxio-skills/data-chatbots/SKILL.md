# 数据聊天机器人

基于**权威结构化状态**（日程、CRM、配置）的副驾驶应先**起草**变更，且仅在人工明确批准后才**应用**。把模型视为规划器，而不是写入器。

## 血泪教训（生产事故——发布前必读）

以下是让 aiebot 操作真实数据时发生过的实际故障。每一个都曾上线、坑过我们，如今已成为下方测试矩阵和快速检查清单中的永久检查项。如果你构建草稿→应用型副驾驶，你**一定**会遇到这些问题——请在事故发生前接好护栏，而不是事后补救。

1. **应用时静默覆盖（TOCTOU）——在生产环境中发现，差点丢掉一场真实演讲。** 人工批准了一个普通的 `assignment_create`（“把这场演讲放进 11:10 的**空闲**时段”）。从起草（时段为空）到约 7 分钟后点击 Apply 之间，该时段已被另一场演讲占用。应用路径**根据实时状态重新推导占用情况，并静默地把放置操作降解成 `batch[cancel occupant, place new]`**，取消了一场**无人批准取消**的真实演讲。只有不可变审计日志揭示了此事。**护栏：实际 APPLY 的内容必须等于人工 REVIEWED 的内容——绝不能在应用时合成破坏性更强的操作。** 参见下方的*应用 == 审核*及测试 §5.10。版本护栏**救不了你**（版本是匹配的）。
2. **唯一外部/导入 id → 无法插入，必须重新激活。** 一个 `*_create` 尝试重新关联已使用的 `cfp_proposal_id`，在应用时因 `UNIQUE constraint failed` 失败——包括仍持有该键的*软删除*行。试运行模拟了占用情况，却没有模拟外部 id 唯一性，因此它“通过审核、应用失败”。**护栏：试运行每一个数据库不变量；在应用瓶颈处设置确定性的 create→move/reactivate 护栏。** 参见*外部/导入 ID 唯一性*。
3. **应用失败没有反馈闭环（缺失的第 4 种结果）。** 被拒绝的应用让提案保持 `draft`，未写入会话记录，规划器再次读取时把它当成“待处理”，并重新提出完全相同、注定失败的变更。**护栏：重新抛出异常前记录权威的 `[Apply FAILED …]` 行；告诉规划器这是终态。** 参见*会话/后续上下文*。
4. **审计/历史运行在无服务器环境中被静默终止。** 最慢的路径（选择性预取 + 大量 token + 容易让人选最强模型 + 多轮交互）耗尽后台执行预算，在中途被终止——没有回复、没有错误、没有遥测记录。**护栏：每次调用设置硬超时、审计默认使用中档模型、限制轮数、在 `finally` 中写入终态、按次记录遥测。** 参见 [audit-log.md](audit-log.md)。
5. **UI 中的“空闲”≠ 索引中的“空闲”。** 预置的占位持有行会让时段看起来为空，但数据库中仍存在有效安排；`open_slot` 查询会漏掉它们，指标也会少算。**护栏：支持两类可放置时段（open + placeholder）；提供 `placeableSlotsByDayRoom`；排除 HOLD/reserved。** 参见*日程数据*。
6. **批量应用向所有操作分发同一个固定 `expectedVersion`。** 使用相同起始版本应用 N 个草稿，会导致第 2 到第 N 个全部抛出 `version_conflict`。**护栏：把每次应用返回的版本串接到下一次；最后只刷新一次。** 参见*批量审核/批量批准*。
7. **第二次覆盖——一场真实演讲被误判为空占位符（并非 TOCTOU）。** 在第 1 次事故数月后，我们通过一条*不同*路径又丢掉了一场演讲。一场标题为 `"TBD — <speaker> on <topic>"` 的**已确认**演讲，其演讲者只写在标题里（`speakers` 数组为空）。占位符启发式规则是“没有关联演讲者 ⇒ 空持有项”，于是它被列为可放置项，并被一次**看似无害的 `assignment` 更新**原地覆盖了内容——时段没有变化、版本没有偏差，第 1 项的应用时护栏也完全没有监测到。生产查询显示，*数十场*演讲者尚待确认的真实演讲都处于危险之中。**两道护栏：(a) 不要根据单一脆弱信号推断“空”——真实演讲也可能没有关联演讲者；应根据内容分类（描述性标题 ⇒ 真实预订），并把模糊情况视为真实内容（默认拒绝）。(b) REPLACEMENT 同样具有破坏性——在*写入层*（reducer）强制执行“未经明确选择不得销毁”，并以目标的实际内容为依据，使其无论规划器如何分类该行，都能捕获每一种路径。** 参见下方*破坏性操作必须明确*及测试 §5.11。

> **低成本取证检查：** 使用只读脚本遍历审计日志，查找**已审核提案并未批准取消，却实际执行了取消的记录**（执行的操作取消了演讲，但存储的提案只是放置/移动，而不是明确的取消或包含可见取消操作的批次），便可在事后找出所有静默覆盖。定期运行它；应用时护栏上线后，它应始终返回零。

## 架构（不可妥协项）

| 层 | 职责 |
|-------|----------------|
| **规划器** | 读取紧凑索引及可选查询；返回答案和结构化提案 |
| **验证器** | 补丁键白名单、真实实体 ID、领域规则（冲突、占用） |
| **试运行** | 在内存快照上累计模拟提案；在人类看到前丢弃无效草稿 |
| **持久化草稿** | 在数据库中保存 `draft` / `applied` / `ignored` 状态，与规范状态分离 |
| **应用路径** | 使用与手动 UI 相同的变更管线（`expectedVersion` + 审计日志） |
| **数据库不变量** | 在 SQLite 中强制互斥，而非仅在 TS 中（部分 UNIQUE + CHECK） |

每种产品界面（Web、Slack、电子邮件）只使用一个编排函数，以保持行为一致。

### 审计/变更日志（不可变）

审计/变更日志是**不可变的（仅追加）**，并在规范状态的每次变更中**记录操作者（哪位用户）及所执行的操作**。理想情况下，它还应支持规范状态的**快照/回滚/恢复**。每条应用路径都通过它写入（参见上方*应用路径*）。有关审计模式访问、预取/轮数上限和无服务器执行预算的运维详解，请参阅 [audit-log.md](audit-log.md)。

### 可观测性/追踪（与审计日志分离）

审计日志是*规范状态变更的不可变记录*；**LLM 追踪则是一条独立且可能丢失的可观测性数据流**，记录智能体每轮执行的内容（span、token、成本、工具调用），并通过 OpenInference + OTLP 发送到 Arize AX / Phoenix 等后端。不要混淆二者。那些不明显的陷阱——使用 **`session.id`** 对多轮追踪分组（每轮本来就正确地拥有独立 trace；没有 `session.id` 时，它只是*看起来*像只捕获了单轮）、无服务器环境中的 **“spans without root spans”** 孤立问题（刷新时根 span 丢失），以及**人工 👍/👎 反馈捕获**（以自有数据库为事实来源 + 尽力写入供应商注释，span id 在服务端解析）——详见 [observability.md](observability.md)。

### 时段占用（排程类产品）

在 **SQLite** 中强制执行，而非仅依靠应用代码：

- 对 `assignments(slot_id)` 建立**部分 UNIQUE**，条件为 `status != 'cancelled'`——每个时段最多只能有一个有效占用者。
- 使用 **CHECK** `(status != 'cancelled' OR slot_id IS NULL)`——已取消行不能保留 `slot_id`（防止“NO PROGRAMMING”幽灵项遮蔽真实演讲）。
- **应用层**映射数据库规则：更新时执行 `releaseSlotWhenCancelled`；网格仅使用有效的 `assignmentsBySlot`；将 `UNIQUE`/`CHECK` 失败映射为 `409 slot_occupied`。

### 破坏性操作必须明确（应用 == 审核，替换也算）

**任何会抹除现有真实内容的写入——覆盖、替换或取消——都具有破坏性，必须 (1) 明确展示给人工，且 (2) 在写入层强制执行。** 我们从两个不同角度的两次事故中吸取了这一教训：

- **血泪教训 #1（应用时扩大范围/TOCTOU）：***应用*路径重新推导出比已审核草稿破坏性更强的操作。（见下文。）
- **血泪教训 #7（起草时错误分类）：** 一场真实演讲被误判为空占位符，因此一次*看似无害的原地更新*将其销毁——时段未变、版本无偏差，第 1 项的护栏完全没有监测到。（案例见下文。）

统一的教训是：**不要依赖规划器/启发式规则决定哪些内容可安全销毁。** 把不变量放入 reducer——所有写入都会流经的唯一瓶颈——并以*写入时目标的实际当前内容*为依据：除非调用方明确选择加入（`allowReplace`），否则拒绝覆盖/替换真实预订的身份；同时拒绝合成人工未批准的取消。无论分类器是否准确，也无论问题发生在起草还是应用阶段，写入层护栏都能捕获这两种路径。

> **案例研究——血泪教训 #7（占位符误分类）。** “空占位符”是根据一个脆弱信号推断的：空 `speakers` 数组。但真实演讲也可能尚未确定演讲者，或演讲者仅写在标题中（`"TBD — Charlie Holtz on Conductor for coding agents"`，状态为 `confirmed`）。它因此被暴露为可放置项，并被一次 `assignment` 更新原地覆盖。**修复：** (a) 根据*内容*分类——描述性标题即使没有关联演讲者也表示真实预订；只有简短/空白、类似标签的标题（`Keynote`、`M1`、赞助商占位项）才可填充；模糊情况视为真实内容（**默认拒绝**）。(b) 将占用者分类移入规划器索引和 reducer 共用的**单一共享模块**，使两层永远不会产生分歧。(c) 添加写入层 `isDestructiveReplace` 护栏：如果原地更新把已预订行的标题+演讲者（或不同的外部/CFP id）替换成另一场演讲，除非设置 `allowReplace`，否则拒绝操作。合法编辑（重命名、关联演讲者、填充真实占位符）不受影响。

**实际 APPLY 的操作范围必须与人工 REVIEWED 的草稿完全一致。** 危险间隙来自*检查时刻与使用时刻之间的差异*：草稿基于一个快照审核，却基于稍后的另一个快照应用。如果应用路径根据实时状态**重新推导**操作，它可能悄悄变得比已批准内容**更具破坏性**。

真实生产事故（血泪教训 #1）：一个已审核的 `assignment_create`（“放进一个**空闲**时段”）在约 7 分钟后应用，而此时该时段已被另一场演讲占用。应用路径发现时段已占用，于是**将放置操作降解成 `batch[cancel occupant, place new]`**——执行了对真实演讲的取消，而该操作**从未出现在已审核草稿中**。之所以能够恢复，完全是因为审计日志显示了合成的取消操作。

常见护栏无法捕获它的原因：

- **`expectedVersion` 必不可少，但并不充分。** 它能检测世界*发生了变化*，却无法判断*此草稿的具体前置条件是否仍成立*。即使**版本匹配**，该缺陷仍会触发，因为操作范围是在应用时根据实时占用情况重新计算的。（更糟的是，客户端经常发送点击时的*当前*版本，而不是草稿生成时的版本——因此检查必然轻易通过。）
- **试运行验证的是无害版本。** 起草时该时段为空，因此模拟操作只是普通放置。破坏性降解在稍后的应用阶段发生，而那里没有根据人工看到的内容重新验证。

护栏（全部执行）：

1. **在 DRAFT 阶段决定破坏性降解，并以可见卡片展示。** 如果放置目标是已被真实预订占用的时段，*存储的草稿*应成为明确替换（`batch[cancel X, place Y]`），让审核者看到并单独批准取消操作。风险分析器应将含取消操作的批次标记为破坏性（默认不勾选）。
2. **在 APPLY 阶段拒绝扩大范围。** 如果存储的*普通放置*所针对的时段现已被占用，则必须抛出异常（`409 slot_occupied` → “重新起草”）；绝不能合成取消。只有明确审核过的替换批次才能取消——如果占用者再次变化，reducer 的占用检查仍会提供保护。
3. **同一规则适用于所有破坏性合成，而不只是取消**——例如把 create→move 变成重新安置现有演讲，或产生级联操作的删除等。如果应用会执行卡片未展示的事情，就应失败并重新起草。

这与 cfp 去重教训互为镜像：在那里，应用路径必须把 create *收敛*成 move；而在这里，应用路径必须*拒绝*把 placement 发散成 cancel。统一不变量是：**应用要么执行已审核意图，要么失败——绝不能创造新的破坏性范围。**（按模式拆分降解函数：`preview` 模式把对已占用时段的放置降解成可见替换供起草使用，而 `apply` 模式则抛出异常而非合成——这样两条路径永远不会发生偏离。）

### 外部/导入 ID 唯一性——重新激活，不要重新创建（`cfp_proposal_id` 教训）

当行包含**唯一外部/导入键**（CFP 提案 id、Airtable 记录 id、源行哈希）时，尝试重新关联已使用键的 `*_create` **无法插入**——数据库唯一索引会拒绝它。实际意图几乎总是**复用现有行**（移动/更新/重新激活），而不是创建重复项。真实生产故障：`db_write_failed: UNIQUE constraint failed: assignments.cfp_proposal_id`。

同一个缺陷踩中了三个陷阱：

1. **试运行/验证器模拟了占用，却没有模拟外部 id 唯一性。** 提案通过所有内存检查，仅在应用时失败。**教训：试运行必须模拟其能够模拟的*每一个*数据库不变量——唯一外部 id、外键、CHECK——而不只是时段占用。** 当两个验证层（领域试运行与数据库约束）不一致时，它们之间的空隙正是“通过审核、应用失败”滋生之处。智能体自己的验证修复重试也捕获不了它：该循环只是重新运行*同一个*领域验证器，因此验证器不可见的约束对自我修复同样不可见。
2. **软删除行仍持有唯一键——护栏谓词必须与索引谓词匹配。** 占用唯一性是部分索引（`WHERE status != 'cancelled'`）；外部 id 唯一性通常**不是**（`WHERE cfp_proposal_id IS NOT NULL`）。一个 `cancelled`、未排程的行仍拥有其 `cfp_proposal_id`，并会阻止新插入。如果 create→move 护栏过滤 `status != 'cancelled'`（对占用来说正确），就会**完全漏掉已取消行的情况。** 应逐键决定已取消行是否计入。
3. **无法搜索的键也无法用于去重。** 没有查询索引 `cfp_proposal_id`（assignment 查询匹配标题/轨道/演讲者；bash 虚拟文件系统也不输出 cfp id），因此 `grep <cfpId>` 什么也找不到，智能体于是“合理地”选择了 create。**教训：智能体需要用来去重的每个标识符，都必须存在于至少一个查询/索引中**——否则应优先采用确定性的服务端护栏，而不是依赖提示指令。

**纵深防御（至少采用多种）：**

- **确定性写回护栏（最可靠）。** 在唯一的应用瓶颈处、构建语句之前：如果 `*_create` 携带的外部 id 已关联某行，就把它改写为对该现有行的**更新/移动**（若已软删除则重新激活：设置目标时段，并将状态从 `cancelled` 改回）。无论模型输出什么，它都覆盖所有界面（提案应用、直接操作、导入）。查询谓词必须与*索引*谓词匹配。
- **验证时转换。** 在起草阶段将 `create`→`move`，让人工看到移动卡片，而不是注定失败的创建。
- **提示指引（单独使用时最弱）。** 告诉规划器查询该演讲是否已存在（使用可搜索字段——如果 id 未被索引，则用标题 + 演讲者）并输出 move。仅当去重键确实可搜索时才可靠。
- **紧急数据修复：** 运维修复应与护栏一致——将**现有的（通常已软删除的）行重新激活**到目标位置，而不是插入第二行，从而保留唯一关联。

## 分层操作框架（次要——MVP 后采用）

上述去重教训只是更广泛陷阱的一个实例：写入界面会针对每种措辞不断增长出**一个定制操作 + 修复强制转换**（`create`、`move`、`multi_move`、`cancel`、`swap`、`rotate`、`create-on-placeholder`……），而“通过审核、应用失败”的缺陷就潜伏在*它们之间的缝隙*中。经过验证的修复方法，是将副驾驶界面收敛为基于**一个选择器**的**三个层级**（高频路径 → 可组合原语 → 审计），并通过每个请求的 `mode` 进行控制。**不要第一天就采用它**——先运行更简单的定制操作 MVP，了解真实用例后再升级。完整重构计划（层级、`upsert`/`rebind`/`batch` 原语集、单一选择器解析器、高频路径 → saga 降解、模式控制，以及“收敛副驾驶界面，保留人工/旧版词汇”的迁移）见 [tiered-operation-harness.md](tiered-operation-harness.md)。

## 提示

### 语气：已起草，而非已完成

- **绝不**使用过去时假装数据库已发生变更：避免“我移动了”“我放置了”“我创建了”。
- 推荐使用：“我起草了……”“提议……”“已准备好供你审核……”
- 系统提示必须声明：**提案仅在人工点击 Apply 后才会应用**（或同等措辞）。

### 基于事实，避免臆造 ID

- 提供**紧凑索引**（计数、带真实 ID 的可放置时段、目录），而不是完整表。
- **智能体循环**：`need_more` + 定向查询；`final` + 提案，不再查询。
- 明确规则：放置 ID **位于索引中**——不要向用户询问索引已包含的时段 ID。
- 定量陈述 → 使用确定性报告或查询，绝不捏造数字。
- **智能体需要据以去重/重新关联的任何键都必须可搜索。** 如果数据库强制唯一的外部/导入 id（cfp id、record id、hash）不存在于任何查询或虚拟文件系统中，智能体便无法发现现有关联，并会创建重复项。应将其加入查询索引，*或*在服务端确定性地执行去重——不要依赖提示指令去避免模型根本看不到的冲突。

### 日程数据：UI 中的“空闲”≠ 索引中的“空闲”（AIEWF / aiebot 教训）

许多日程会在每个时段预置**结构性占位行**（例如通用标题 `Keynote` / `Talk`，没有真实演讲者）。网格看起来为空，但数据库中仍存在有效 assignment。副驾驶需要支持**两类可放置项**，且绝不能混淆：

| 人类看到的内容 | 索引字段 | 如何预订 |
|-----------------|-------------|-------------|
| 真正空闲的时段（没有行） | `placeableSlotsByDayRoom` 中的 `openSlots` / `state: "open"` | `assignment_create` → `targetId = slot_*` |
| 空的**占位符**持有项 | `placeableSlotsByDayRoom` 中的 `state: "placeholder"` + `assignmentId` | 对该 `asn_*` 执行 `assignment` **更新**（title/speakers/status）——**不是**在时段上 create |

**数据提供陷阱（真实生产缺陷）：**

1. **只搜索 `openSlots` 的 `open_slot` 查询**会漏掉用户称为“空闲”的所有占位符（例如“下午 5:10 Main Stage 是空的”）。应优先在紧凑索引中提供 `placeableSlotsByDayRoom`，或添加包含时钟时间 + `assignmentId` 的 `placeable_slot` 查询。
2. **`openSlots` / “N 个空闲”指标**会少算有场次的日期——占位符可放置，却不计为空闲。当占位符存在时，不要告诉用户“Main Stage 有 0 个空闲时段”。
3. **虚拟文件系统/bash `grep OPEN SLOT`** 只标记**没有** assignment 的时段；占位 keynote 会显示为普通场次文件，而不是 `OPEN SLOT`。
4. **移动与填充：** 向已被占位符占用的时段执行 `assignment` 补丁 `{ slotId }`，试运行结果会是 `slot_occupied`（持有项仍占用该时段）。要将现有演讲重新安排到该时间，应与占用项**交换**、**填充占位符行**并清除/移动源演讲，或对 3 个以上项目执行**轮换**——不能直接移动到该 slot id。
5. **时间消歧：** 一个“keynote 时间窗”（例如 4:30–5:30）通常包含**多个** slot id（4:30、4:50、5:10）。“闭幕 keynote”可能指**最后一个**区块，而不是索引中的最早样本。当用户明确说出时钟时间时，应匹配该样本——不要自动选择组中最早的可放置项。
6. **HOLD / reserved 行不是占位符：** `status: "hold"` 或标题为 `HOLD`/`Reserved` 的行即使没有演讲者，也是**有意阻塞**的。必须将它们从 `placeableSlotsByDayRoom` 中**排除**。验证必须**丢弃**填充 hold 行，或通过 `assignment_create` / `slotId` 移动到已被预订或 hold 占用时段的提案——绝不能静默覆盖。当用户说“替换 X 的时段”时，应解析 **X 的** `asn_*`，而不是轨道中最早的占位符。这是一个**起草时**护栏；它**无法**覆盖空时段草稿获批后，该时段才被占用的情况——对此请参见*应用 == 审核*（应用路径必须拒绝，而不是静默合成取消）。

**提示 + 验证器习惯：** 系统提示必须说明 `open` 和 `placeholder` 两种状态；将占位符上的 `assignment_create` 强制转换为 `assignment` 更新；试运行应丢弃进入真实预订项的移动，并在原因中包含占用者 id；从可放置索引中排除 hold 行；应用阶段拒绝把空时段草稿扩大为取消操作（TOCTOU）。参见 [test-cases.md](test-cases.md) §5.6–5.10。

### 信息不足的请求

- 保持**宽容**：立即使用 TBD 占位符（标题、演讲者、时段）起草，而不是拒绝。
- 在答案中指出占位符和自动选择的时段，让人工可以逐个字段修正。

### 多步骤/复合请求（一条消息，多个操作）

用户经常在一个提示中塞入一次**名单刷新**——范围 + 多个删除 + 一个带粘贴 JSON 的添加：

> *“在 Inference 轨道中，删除 Perplexity 的演讲和 Denis Yarats，并添加……”* + `{ "proposal_id": "…", "speaker": "…", "session": "…", "description": "…" }`

应将其视为**一次规划轮次 → 多个提案**，而不是一个模糊变更。

**拆分为原子草稿**（每个草稿都有自己的摘要及 Apply/Ignore 卡片）：

| 用户意图 | 典型提案 |
|-------------|---------------------|
| 删除/移除/清除已预订演讲 | 对解析出的 `asn_*` 执行 `assignment` 更新：`{ "status": "cancelled" }` 或 `{ "slotId": null }` |
| 删除多场演讲 | **每场演讲一个提案**——绝不把无关实体合并进同一补丁 |
| 添加/放置新演讲 | `assignment_create` 或占位符 `assignment` 更新；若为新人员，再加 `speaker_create` |
| 用 C 替换 A 和 B | 取消 A、取消 B、放置 C（一次响应中包含 3 个以上提案） |

**解析阶梯**（持续查询直至 ID 已知——不要猜测 `asn_*`）：

1. **范围**——把“Inference 轨道”“第 4 天”“7 月 2 日”映射到 `tracks` / `placeableSlotsByDayRoom` 分组（日期 + 房间）。
2. **查找删除项**——通过 `assignment` / `speaker` 查询：公司（“Perplexity”）、演讲者姓名（“Denis Yarats”）、标题子串。
3. **消歧**——如果范围内有多个结果，则按轨道/日期/时间选择或询问用户；优先选择**位于指定轨道**的 assignment。
4. **查找放置位置**——该轨道/房间中最早的可放置样本（`open` 或 `placeholder`）；用户未指定时间 → 选择一个，并在答案中**明确说出**。
5. **摄取 JSON 块**——把 `speaker` / `session` / `description` / `proposal_id` 映射到补丁字段 + CFP 关联键；不要因为句子同时包含自然语言就忽略该数据块。

**智能体循环：** 复合请求通常需要先返回 `need_more`（查询轨道 + assignment），再返回包含**所有**提案的 `final`。第一次查询后就停下，只说“我会删除 X”却没有任何草稿，是一种失败模式。

**顺序与试运行：**

- 按逻辑顺序输出提案：先**释放容量**（取消/取消排程），再**填充**（创建/更新占位符）。
- 累计试运行必须模拟**整个批次**——如果某个创建只有在同批次取消之后才可行，只要顺序正确，它仍应被 `kept`。
- 如果取消项被丢弃，导致创建目标时段仍被占用，应在答案中说明。

**多步骤答案形式：**

- 简短计划：范围、查询内容、所提议内容。
- 与草稿卡片 1:1 对齐的**编号列表**（例如“1. 取消 Perplexity……2. 取消 Denis Yarats……3. 将 Lin Qiao 放到 11:40 Track 9……”）。
- 对整组使用不确定语气：“我起草了 3 项变更……”——而不是“我删除并添加了”。

**UX 预期：**

- 一条回复可展示**多张**草稿卡片；用户可以全部应用、应用部分或逐个忽略。
- 部分应用后，会话结果必须反映哪些子集为 APPLIED，哪些仍为 DRAFT。
- 提示中出现大型 JSON 很正常——不要求拆分到多个聊天轮次。

**规划器提示补充：**

- 明确允许在一个 `final` 响应中包含**多个提案**。
- “Remove”/“take off the schedule” → 取消或取消排程，除非用户要求交换，否则不要 swap。
- 公司演讲（“Perplexity's talk”）→ 先通过 assignment 索引中的赞助商/公司/标题解析，再以演讲者作为后备。

### 用户提供的结构化字段

- 当用户粘贴 JSON/CSV 字段（外键、导入 ID、哈希）时，将其**全部复制**到提案补丁中。
- 同时记录规范补丁键和常见别名（`proposal_id` → `cfpProposalId`）。
- 在验证前于服务端**规范化别名**——模型对用户键的复现并不一致。

### 会话/后续上下文

重放最近轮次时应包含**权威提案结果**，而不只是助手文本：

```
DRAFT     → 尚未写入规范数据
IGNORED   → 人工已拒绝；日程未变
APPLIED   → 已写入规范数据
FAILED    → 人工点击了 Apply，但写入被拒绝；规范数据未变
```

给模型的前言：*只有 APPLIED 表示变更已发生；如果结果显示 DRAFT/IGNORED，即使文本写着“我移动了”，也应忽略。*

在 Apply/Ignore 时追加明确的用户行：`[Human applied draft "…"]` / `[Human ignored draft "…"]`。

**应用失败需要反馈闭环——缺失的第 4 种结果。** 如果你只建模 draft/applied/ignored，那么被拒绝的应用（数据库约束、验证、冲突）会成为死路：应用处理程序在 `status = applied` *之前*抛出异常，因此提案保持 `draft`，不会写入会话行；规划器下一轮再次读取时，会把它当作无害的“待审核”——**完全不知道写入已失败**。错误只存在于 UI 中。修复方式：

- 应用出错时，在重新抛出前**记录权威会话行**：`[Apply FAILED for "…"] — write REJECTED (<reason>); canonical data NOT changed; do not re-propose verbatim — diagnose and correct.` 在写入*之前*解析会话键，使失败仍可归因。
- 告诉规划器 `[Apply FAILED …]` 是权威结果（与 DRAFT/IGNORED 状态相同）：**重新规划，不要再次输出完全相同的提案。** 否则机器人会循环：提议 → 拒绝 → 再次提出相同内容。
- 这是反应式修复（下一轮生效）。还应搭配上方确定性的 create→move 护栏，使常见原因根本不会触达用户。

### 验证修复轮次

当验证器丢弃提案时，执行一次重试提示，列出**每个提案的原因**及允许的补丁键——防止出现零草稿却静默声称“成功”的回答。

### Slack 内联标志（`!help`、`!model`、`!audit`）——存在原因

Slack 没有模型下拉框，也没有“History access”复选框。用户需要在消息中使用**明确且在规划前移除的标志**（与 Web 使用相同的编排核心；标志仅影响 Slack 适配器）。

| 标志 | 用途 | 为什么不隐式处理？ |
|------|---------|-------------------|
| **`!help`** | 发布完整能力指南（Block Kit）；**不调用模型** | 空 @mention 和“你能做什么？”应立即响应；避免为静态文档消耗 token |
| **`!model <slug>`** | 为当前请求覆盖规划器模型 | 默认模型快速且便宜；审计和困难推理需要更强层级，但不应改变全局配置 |
| **`!advanced`** | 解锁第 2 层可组合原语 + 原子 `batch` | 长尾词汇受到控制，使默认模型保持使用符合人体工学的高频路径（参见 [tiered-operation-harness.md](tiered-operation-harness.md)） |
| **`!audit [duration]`** | 选择性启用审计/操作历史 + 预取 | 历史敏感且耗费 token——绝不默认开启；除非 `!model` 覆盖，否则 `!audit` 还会自动选择**审计默认模型**（详见 [audit-log.md](audit-log.md)） |
| **`!mine`** | 历史：仅请求者自己的编辑 | 适配器必须知道请求者的电子邮件 |
| **`!verbose`** | 在历史结果中显示完整前后差异 | 默认保持紧凑；verbose 会撑爆上下文 |
| **“not by me”**（自然语言） | 在历史预取中映射为 `exclude:<email>` | 用户使用这种说法比标志更频繁 |

**解析规则（适配器）：**

1. 从原始消息解析标志 → 移除标志 → 将**清理后的文本**作为 `message` 传给 `runAiebotQuery`。
2. `!help`（或仅有 `help` / 空 mention）→ 立即返回 `buildHelpBlocks()`；不要调用规划器。
3. 无效的 `!model` slug → **忽略**（回退到默认/审计默认值）；在帮助中列出有效 slug。
4. `historyQueryPrefix`（例如 `after:…`、`actor:…`、`exclude:…`）由服务端添加到每个 `history` 查询前——模型不能“忘记”时间窗口。
5. **审计模式：** 服务端在第 1 轮前**预取**历史；系统提示禁止用“我会检查……”来拖延回答。

**Web 对等关系：**

| Slack | Web |
|-------|-----|
| `!model openai-gpt-5.4-high` | 模型下拉框（`/api/ai/chat` 上的 `modelSlug`） |
| `!advanced` | “Advanced”复选框（`/api/ai/chat` 上的 `mode: "advanced"`） |
| `!audit` | “History access”复选框 |
| `!help` | “What can aiebot do?”示例面板 |
| 已选网格时段上下文 | 使用 slot/assignment id 自动填充编辑器 |

**模型 slug** 存放于前后端共享的单一注册表（`AI_MODEL_OPTIONS`）中。在 `!help` 中记录每个 slug。典型默认值：快速 mini 用于问答；**中档推理层级**（例如 `…-medium`）用于 `!audit`，除非 `!model` 胜出——**不要**使用最慢/最高层级（高强度推理导致审计路径被静默终止的原因，参见 [audit-log.md](audit-log.md)）。

**最佳实践：**

- 组合标志：`@aiebot !model openai-gpt-5.4-high !audit 2d summarize edits not by me`
- 新用户引导优先使用 `!help`；让 `SLACK_HELP_TEXT` 保持为指向 `!help` 的单行文本
- 绝不能在使用移除标志后的消息和原始消息时采用不一致的路由分类——在持久化**之前**移除标志，而不是在帮助检测之前移除
- 在每次运行中记录所选模型 slug + `historyAccess`，以便调试“为什么这次这么笨？”

参考：`functions/_lib/slack-flags.ts`、`functions/_lib/slack.ts`（`buildHelpBlocks`）、`src/domain/aiModels.ts`。参见 [slackbot-builder](../slackbot-builder/level-3-interactive.md) § 内联标志。

### 超长审计请求（无服务器执行预算）

审计/历史是你拥有的**最慢路径**（选择性预取 + 大量 token 上下文 + 容易让人选择最强模型 + 多轮循环），而在无服务器后台任务（`waitUntil`、Lambda）中，超过执行预算的运行会被**中途终止**——没有回复、没有错误 reaction、没有遥测记录。缓解措施包括：对**每次供应商调用设置硬超时**（流式调用使用空闲重置，一次性调用使用总时长上限）、使用**中档审计默认模型**、**限制审计轮数**、在 `finally` 中发出终态，以及记录**每次运行的遥测**（静默终止表现为记录缺失）。完整教训、诊断和持久化运行器升级方案见 [audit-log.md](audit-log.md)。关于同一事故的*消息界面*侧——处理程序级超时上限、卸载到持久执行、保护**所有**入口界面（mention/DM/slash/button/cron），以及 ack→progress→保证返回结果或错误的三阶段模式——请参见 [slackbot-builder L5](../slackbot-builder/level-5-hardened.md) § *Never run agent work inline*。

## UX

> 本节介绍**草稿→应用数据流**（队列、卡片、版本控制、错误）。关于副驾驶*界面本身*的行为——浮动/可停靠面板、唤出快捷键**尺寸状态机**（循环：最小化 → 50% 侧栏 → 80% 侧栏 → 居中 → 最小化）、自定义尺寸调整协调、屏幕范围限制及吸附动画——请参见 [surface-ux.md](surface-ux.md)。

### 请求队列（长时间智能体循环）

复合/查询密集型轮次可能运行**数分钟**。编辑器必须保持可用——将后续消息排入队列，而不是阻止发送。

**客户端队列（FIFO，单一进行中任务）：**

| 状态 | UI | 用户操作 |
|-------|-----|-------------|
| **queued** | `aiebot is queued…`（无已用时间计时器） | **Remove**——从队列移除并删除待处理气泡 |
| **active** | `thinking` / `writing` + 已用时间；工具行（`looked up assignment: …`） | **Stop**——中止流；将消息恢复到编辑器 |
| **done** | 助手气泡 + 草稿卡片 | — |

**发送时（始终执行）：**

1. 立即添加**用户**气泡 + **待处理**占位符（`queued: true`）。
2. 清空编辑器——不要等待网络。
3. 将任务推入 `queueRef`；`processQueue` 每次运行一个任务（由 `processingRef` 控制）。

**顺序语义：**

- 在任务 *N* 结束（成功、错误或中止）之前，任务 *N+1* 不调用 API。这样可避免规划器运行重叠，以及重复的 `proposals` 状态互相覆盖。
- **服务端会话**仅在 *N* 完成后才获得第 *N* 轮（`recordSessionTurn`）。排队的问题（例如“X 已经有场次了吗？”）在规划时**看不到**仍在执行的 *N* 的草稿/结果，除非 *N* 已经落地。不要假定模型能看到仍在流式生成的工作。
- 当消息排在进行中任务之后时，可选产品文案：*“已排队——将在当前回复完成后运行。”*

**编辑/清空：**

- 用户消息上的 **Edit**：清空队列、静默中止活动任务、截断该索引之后的聊天，并将文本恢复到编辑器。
- **Clear chat**：清空队列 + 中止；如果需要重置连续性，则轮换会话键。

**后端：** 每个任务使用一个 HTTP/流即可；除非增加 Slack/电子邮件 worker，否则不需要服务端队列——应记录队列所在位置（浏览器或 worker）。

**异味：**

- 在 `pending` 时禁用发送 → 不利于多步骤延迟。
- 因无关错误丢弃排队任务。
- 并行启动任务 *N+1* → 导致 `proposals`、会话轮次和快照版本竞争。
- 用户在 *N+1* 已带着过期 `expectedVersion` 排队时应用第 *N* 轮草稿——应搭配下方的**版本轮询/过期横幅**。
- 每次 `onResult` 都替换全局 `proposals` 数组 → 排队的后续任务运行时会**移除前一轮卡片**。应按提案 id **合并**。

### 草稿卡片（每条回复）

- 每个生成提案的助手轮次内联显示 **Apply** / **Ignore**。
- 应用前允许编辑补丁 JSON（面向高级用户）。
- 文案：*“N 项待处理变更——在点击 Apply 前不会更新任何内容。”*
- **状态（三种结果）：**
  - `draft` → **Pending review**（尚未操作——仍显示 Apply/Ignore）。
  - `applied` → **Applied**（已进入规范存储；隐藏按钮）。
  - `ignored` → **Ignored**（软拒绝——未进入日程；机器人会话记忆将其视为已拒绝）。
- Apply/Ignore 后，卡片仍**保留显示**在所属助手轮次中（徽章 + 辅助文本），因此**排队的**后续回复不会移除先前草稿。
- 全局 `proposals` signal = **合并后的目录**（每次结果调用 `mergeProposals`）；`setProposalStatus` 同步目录及拥有该 `prop_*` id 的每个助手轮次。
- 只读排队问题不能清除第 *N* 轮草稿——只应**合并**第 *N+1* 轮中的新 `prop_*` id。

### 批量审核/批量批准（单轮多个草稿）

一个多步骤请求（例如对名单中每个人执行“创建演讲者 + 起草演讲”）通常会在一条回复中生成 **8–14 个草稿**。纵向堆叠完整 Apply/Ignore 卡片会迫使用户滚动 N 次并点击 N 次。只要一个轮次包含 >1 个草稿，就将其折叠为**表格**：

| 元素 | 行为 |
|---------|----------|
| **行** | 每个提案一行：`[checkbox] summary … [status badge] [▸]`——紧凑且摘要截断 |
| **复选框** | 草稿**默认勾选**（= 将会应用）；取消勾选只会将其排除在批次外（仍保持 `draft`，而不是 ignored） |
| **表头** | `N/M selected to apply` + 全选切换 |
| **展开（▸）** | 点击行/箭头 → 显示 `targetType:targetId`、证据、可编辑补丁 JSON，以及单行的 **Apply just this** / **Ignore** |
| **表尾** | 一个 **`Apply N selected`** 按钮——执行批量批准 |
| **已处理行** | `applied`/`ignored` 仅显示徽章，不显示复选框；没有草稿后，表头切换为 `N changes resolved` |

**批量应用必须串接版本，不能扇出。** 每次应用都会递增 `expectedVersion`；以相同起始版本并行执行全部 N 项，会导致第 2 到第 N 项抛出 `version_conflict`。因此：

- **顺序**应用，将每次应用返回的 `result.version` 传给下一次（`version = applied.result?.version ?? version + 1`）。
- 仅在**最后刷新一次**快照，而不是每次应用之间刷新（避免 N 次网格闪烁/N 次快照重新获取）。
- 单行出错时：在该行记录错误，执行 `refreshAll()` + 从实时快照重新同步 `version`，然后**继续执行**——一个坏草稿不能中止其余项。
- 发布摘要阶段行：`Applied 5 of 7 selected changes — 2 need attention, see below`。
- 为了与单卡片操作保持一致，动词默认使用应用现有的 **Apply**，而不是“Accept”。

**异味：** 复选框表示“忽略未勾选项”（令人困惑——未勾选只应表示*跳过*，并保持草稿）；使用单个固定 `expectedVersion` 批量应用；在循环内刷新整个快照；重新渲染时丢失单行编辑/错误状态（按 `prop_*` id 为展开/补丁/错误映射设置键，使其在状态变化时仍保留）。

参考：`src/frontend/components/AiebotPanel.tsx`（`ProposalReviewTable`）。

### 版本/过期状态（乐观并发控制）

- 每个变更都发送 `expectedVersion`；过期时服务端返回 `409 version_conflict`。
- 应用/保存时**绝不能静默失败**——显示内联错误 + 人类可读消息（本地 vN 与服务端 vM）。
- 登录期间约每 30 秒**轮询**轻量级 `GET …/version`（而不是完整快照）。
- 当 `clientVersion !== serverVersion` 时显示**持久横幅**：Reload schedule（刷新数据）+ Reload page（加载新 bundle）。
- 任何 `version_conflict` 也应设置过期标志。

### 错误与聊天

- 区分**聊天错误**（模型/供应商）与**应用错误**（冲突、验证）。
- 在助手消息中显示被丢弃的提案（项目符号列表），而不只是在开发者工具中显示。

## 服务端验证清单

添加新的可补丁字段时：

1. 领域操作接受该字段
2. `ASSIGNMENT_CONTENT_KEYS`（或等价项）包含该字段——**否则验证器会静默移除它**
3. 系统提示 + 修复提示列出该键
4. 如果用户使用其他名称，则添加别名映射
5. 测试：包含该字段的提案通过 `validateAiDraftResult` 后仍保留

其他验证器习惯：

- **试运行必须模拟每个数据库不变量**，而不只是占用——包括唯一外部/导入 id、外键、CHECK。数据库强制执行但快照未模拟的任何内容，都是“通过审核、应用失败”的缺陷，并且智能体的自我修复重试也看不到它（因为重试只是重新运行同一个验证器）。
- **应用不得扩大已审核草稿的范围（TOCTOU）。** 如果普通放置的目标时段在起草与应用之间被占用，则必须**失败**（`409 slot_occupied` → 重新起草），绝不能静默降解成 `cancel + place`。替换应在起草时决定（显示为可见卡片）；应用时拒绝合成。将该规则推广到任何破坏性降解（create→cancel、级联删除）。参见*应用 == 审核*。
- **重复的唯一外部 id → 将 `*_create` 改写为对现有行的更新/重新激活**（包括仍持有键的软删除行）；护栏谓词必须与*索引*谓词匹配（占用排除 cancelled；外部 id 可能不会）。
- `assignment_create` 仅用于真正空闲的时段；将占位符上的 create **改写**为 `assignment` 更新
- 移除放错位置的键（补丁中的 `slotId` → 应位于 `targetId`）
- 当放置使用未知的 `kind: "text"` 演讲者时自动执行 `speaker_create`
- 累计试运行捕获相互影响的提案（两场演讲 → 同一时段）

## 实现异味

- 助手轮次存入会话时**没有**提案状态 → 后续幻觉
- `recordSessionTurn` 仅存储自然语言，不存储结果
- 应用处理程序没有 `try/catch` → 控制台出现 `Uncaught (in promise)`
- 应用失败仅在 UI 中显示（没有 `FAILED` 会话行）→ 规划器永远不知道，并再次提出相同的被拒变更
- 应用路径根据实时状态**重新推导**操作，并可能输出比已审核草稿*更具破坏性*的操作（例如取消）→ 静默覆盖（TOCTOU）；在起草时决定破坏性降解，在应用时拒绝扩大范围（一个降解函数，支持 `preview` 与 `apply` 模式）
- 试运行/验证器只模拟占用，但数据库还强制唯一外部 id/外键 → “通过审核、应用失败”
- create→move/去重护栏过滤 `status != 'cancelled'`，而唯一索引覆盖所有行 → 已取消行仍阻止插入
- 数据库强制的唯一键未被任何查询索引 → 智能体无法去重并创建重复项
- 仅靠模型强制“不要声称已应用”，却没有结果行
- 版本轮询获取完整日程 → 成本高；添加仅返回版本的端点
- 将用户消息内容用于确定性分支与模型分支的路由，而本应仅由 `contextNote` 提供事实依据

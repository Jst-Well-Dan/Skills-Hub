# 智能实体解析

广泛搜索，延后决策，修补缺口，并展示备选项。目标不是构造一个完美的字符串查询，而是将模糊的人物或组织请求转换为透明的候选集；当普通检索遗漏明显记录时，使用 LLM 规划检索；用证据丰富候选项；让重排序器结合上下文进行选择；并保留足够的次优候选信息，使人工或后续代理能够快速纠正错误。

此技能适用于名人/参考图像搜索、演员阵容和团体、CRM/联系人数据库、组织目录、类似 IMDB 的档案、上市公司数据库，以及任何多个记录可能共享名称、别名或部分标识符的系统。

## 核心原则

将实体解析视为分阶段调查，而不是一次查找。精确搜索、slug 查找、受欢迎程度和 LLM 判断都是有用信号，但任何一个都不应在无提示的情况下支配其他信号。

始终区分三个问题：

- 覆盖范围：是否枚举了所有请求的实体？
- 身份：此候选项是否代表所请求的人物或组织？
- 实用性：这是否是最适合当前任务的可用记录？

身份依据薄弱但实用性高的记录存在误报风险。正确但稀疏的记录可能可以接受，但如果内容更丰富的备选项有可能代表同一实体，系统应将其展示出来。

## 工作流程

1. 搜索前先对查询进行分类。判断它是单个实体、实体列表，还是模糊的团体/演员阵容/成员/团队/组织查询。`members`、`cast`、`lineup`、`team`、`company`、`subsidiaries` 和 `leadership` 等词通常意味着需要展开。

2. 查找前先解析指令式查询。用户经常将实体提示包装在任务文本中，例如 `find the full profiles for...`、`guess the grouping that includes...` 或 `resolve these partial names...`。提取实体提示区域，保留原始指令作为上下文，不要将整段指令字符串作为字面数据库查询发送。

3. 将模糊查询展开为实体组。需要时使用 LLM 加 Web/搜索工具枚举个人或组织。将同一实体的别名归为一组，例如艺名、法定姓名和罗马化拼写。不要过早压平别名，以免不同实体在同一个全局候选池中竞争。

4. 针对每个实体组进行广泛搜索。对于每个实体，搜索多个别名、清理后的变体、目标数据库支持的精确 slug 或直接 ID 候选项，以及 `<group> <short name>` 之类带上下文的短名称查询。使用实体级的本地查询追踪；全局查询去重可能使带有常见别名的后续实体得不到充分搜索。

5. 当检索为空或结果薄弱时，使用 LLM 检索规划器或修复步骤。这与重排序是不同的任务：让它提供下一步要尝试的直接 ID、URL slug、精确名称探针、别名探针和上下文搜索。向其提供原始查询、已解析的实体标签、分组别名以及失败的已尝试探针。返回的探针应保持少量且高精度。

6. 按稳定的记录标识合并候选项。使用档案 ID、slug、规范 URL、数据库 ID 或其他稳定键去重。保留发现候选项的每个查询和来源，而不是只保留得分最高的路径。

7. 重排序前先丰富候选项。收集涵盖身份、来源、实用性、歧义性和置信度的概念性证据。绝不能要求重排序器只根据名称进行选择。

8. 在硬性预算内运行自适应 LLM 重排序循环。默认最多进行 3 轮。仅当覆盖不完整、所有候选项置信度都较低，或更多证据可能区分排名靠前的候选项时才继续。当所有请求实体都有可信候选项、预算耗尽，或继续搜索不太可能有帮助时停止。

9. 每次都返回或展示备选项。输出应包含选中的候选项，以及排名前 3-6 的次优候选项，并提供足够证据，使用户或代理能够理解并推翻该选择。

10. 将未解析和不确定视为一等结果。优先返回 `needs review`、`no plausible match` 或 `ambiguous`，不要悄无声息地填入实用性高但错误的候选项。

## 部分名称与模糊指令

当查询主要包含名字、短别名、首字母缩写或部分组织名称时，不要认为原始数据库命中就已足够。直接搜索短名称通常会返回看似合理但错误或不完整的档案。当查询包含分组词、包含关系词、完整档案/完整名称意图，或列表中的大多数项目都是单词名称时，强制执行展开/分类步骤。

保留查询的两种表示：

- `originalQuery`：完整的用户指令和上下文。
- `entityHints`：提取出的待解析候选名称或别名列表。

展开模型应同时看到两者。要求它推断可能的共享上下文，并返回带有分组别名的具体实体。对于每个展开后的实体，保留一个标签及其别名，然后在该实体分支内搜索这些别名。对于简单的精确名称，仍可运行直接搜索路径，但当覆盖范围依赖于从部分提示推断完整身份时，不应让直接搜索抑制展开。

覆盖范围与结果数量是两回事。五个请求提示产生大量原始候选项，并不意味着已经解析完成；只有每个提示都映射到选定实体，或得到明确的未解析/有歧义结果，才算完成。追踪 `expectedCount`、`resolvedCount`、`ambiguousCount` 和 `unresolvedHints` 或等效字段。

## 检索规划与缺口修复

不要指望重排序器挽救检索阶段从未返回的记录。将 LLM 的参与拆分为不同角色：

- 展开模型：“目标实体是谁或是什么？”
- 检索规划器或修复模型：“针对这个目标，检索器接下来应尝试哪些精确 ID、slug、直接 URL、别名和搜索探针？”
- 重排序模型：“给定这些经过丰富的候选项，哪一个才是正确记录？”

当已知数据库搜索不可靠、可以预测直接 slug 或 ID，或者某个实体分支没有候选项、没有可用数据，或只有薄弱的常见名称匹配时，在查找前或查找过程中使用检索规划。规划器应看到原始查询、已解析的实体标签、分组别名、已尝试的探针、失败来源的状态，以及任何可用的来源特定约束，例如 URL slug 格式。它应返回探针，而不是最终答案。

限制修复循环次数。一个实用默认值是：每个外层循环中，每个未解析实体调用一次修复，并提供 3-6 个直接 ID 或 slug 探针以及 3-8 个搜索查询。对这些探针运行确定性检索，然后在重排序前合并并丰富恢复出的候选项。如果修复后检索仍为空，则将该实体标记为未解析并附上来源信息，而不是假装重排序器拒绝了它。

## 日志与扇出

实体解析应生成能够解释调查过程的阶段追踪。至少记录 `classified query`、`extracted entity hints`、`expanded entity groups`、`searched alias`、`scored candidates`、`planned retrieval repair`、`searched repair probes`、`enriched candidates`、`reranked candidates`、`selected entity`、`unresolved entity` 和 `resolution complete`。包含计数和经过清理的预览；除非视图明确仅供本地使用，否则不要记录原始私密文本。

对于相互独立的实体组，在服务端以有限并发进行扇出。将每个组视为一个子代理分支，拥有自己的 `parentId`、`depth`、`lane`、别名、重试、超时、取消信号和本地暂存状态。分支不应直接修改共享的去重集合、结果上限或已选数组。按输入顺序或明确的排名规则串行合并分支结果，以免完成顺序改变被接受的实体。

当重试影响解析质量或延迟时，应在阶段中明确展示。对于来源/提供方的瞬时故障，使用有上限的退避策略重试；但不要重试用户取消、认证/验证失败、内容政策拒绝或普通的无匹配结果。超时阶段应指出具体超时的分支或工具。取消操作应将正在运行和排队中的实体分支标记为已取消，而不是失败。

最终日志应同时汇总质量和实用性：预期实体、已解析实体、有歧义实体、未解析实体、选中候选项的 ID/slug、图像/数据可用性、重试次数、超时次数，以及是否使用了任何回退路径。该汇总是调试“技术上成功但实际运行错误”的最快方式。

## 证据模型

让证据保持概念性和可移植性。不要过度拟合某个网站的字段。

- 身份证据：精确名称或 ID 匹配、别名、艺名、法定姓名、罗马化变体、共享词元、缺失的主要词元、上下文匹配、已知组织/团体关系以及冲突名称。
- 来源证据：哪个查询发现了候选项，以及它是否来自搜索、精确 slug、直接 URL、数据库 ID、API 查找、Web 结果、用户提供的来源、检索规划器探针或恢复流程。
- 实用性证据：图像数量、档案完整度、活跃度、受欢迎程度、浏览量、投票数、列表数量、员工数量、关系数量、验证状态、时效性，以及记录是否包含任务可用的媒体或元数据。
- 歧义证据：简短/常见名称、仅姓氏匹配、首字母缩写、重复记录、团体/项目页面、包含 “and the” 的页面、稀疏记录、冲突别名、旧名称、已合并组织、子公司或名称相似的公众人物。
- 置信度证据：选中的候选项、次优候选项、重排序器给出的理由、未解析状态、需要人工审查标志，以及原始查询的覆盖状态。

## 重排序规则

当数据库混乱时优先使用 LLM 重排序，但要通过证据和预算对其进行约束。

- 向重排序器提供原始查询、已解析的实体标签、别名、候选项的名称/ID/URL、来源、身份证据、实用性证据和歧义警告。
- 指示它先判断身份，再考虑实用性。如果身份证据薄弱，它不得选择图像丰富或热门的候选项。
- 对于可能属于同一身份的候选项，让实用性决定选择。如果公开艺名或品牌名记录具有更强的任务相关证据，它们可以优于法定名称记录。
- 除非有上下文、精确 ID/slug、更丰富的别名重叠或强外部证据支持，否则将单词别名视为有歧义。
- 避免硬性接受规则。直接别名命中是一种信号，而不是证明。
- 避免硬性拒绝规则。罗马化、品牌重塑、稀疏或仅有艺名的记录可能看起来不完整，但仍可能正确。
- 如果 LLM 选择了实用性较低的候选项，而同一身份的另一个候选项实用性明显更高，应优先进行第二次重排序或展示内容更丰富的备选项，而不是静默覆盖。
- 记录或展示选中候选项的理由，并保持备选项可见。

## 失败模式

当解析器“基本可用”但感觉不对时，用以下内容作为审查检查项。

- 精确数据库搜索可能漏掉真实记录。可用时探测精确 slug、直接 URL、ID 或其他端点。
- 短名称会产生误报。`Lisa`、`Rose`、`Sunny`、`Tiffany`、`Yuri` 以及类似的单词名称需要上下文搜索和歧义警告。
- 法定名称记录的实用性可能更差。公开名称/艺名或品牌名可能拥有更完整的档案、更多图像或更新的元数据。
- 实用性信号很强，但不能单独安全使用。计数、投票、浏览量和受欢迎程度只能在身份可信之后用于打破平局。
- 复合别名是有用的上下文，但通常不适合作为字面搜索字符串。将其拆分为多个别名，同时保留组身份。
- 硬性直接接受逻辑很脆弱。它可能仅仅因为某个别名匹配，就抓取一个普通的重复记录。
- 硬性身份门槛很脆弱。当名称稀疏、经过翻译、罗马化、品牌重塑或仅有艺名时，它可能隐藏正确记录。
- 覆盖数量不等于正确性。找到 6 个实体中的全部 6 个并不代表成功，如果其中一个选中记录对应的是错误的人物或组织。
- 全局查询去重可能使后续实体得不到充分搜索。常见别名应按实体组分别追踪。
- 来源不稳定是结果的一部分。超时、403、404、重试和部分数据应呈现在来源信息或调试日志中。
- 重排序器无法修复缺失候选项。如果目标分支没有候选项，应在重排序前插入检索规划或修复步骤，而不是期待重排序器推断出隐藏记录。
- 指令文本可能污染字面搜索。从查找查询中剥离任务短语，同时将其保留为展开和重排序的上下文。
- 快速直接结果可能抑制必要的展开。如果查询要求分组、包含关系、完整档案，或主要由短名称组成，即使直接搜索返回了候选项，也应运行展开。
- 并行分支的完成顺序可能产生不确定的胜出者。分支需要本地状态以及确定性的父级合并。
- 隐藏的重试、超时和取消会让解析器显得随机。将它们公开为结构化阶段和来源信息。

## 输出模式

对于每个请求的实体，优先采用包含以下概念的输出结构：

- 已解析的实体标签和别名。
- 带稳定 ID/slug/URL 的选中候选项。
- 选择理由以及置信度或审查状态。
- 提供足够证据以供比较的首选备选项。
- 覆盖状态：已匹配、有歧义、无可信匹配、无可用数据或需要审查。
- 来源：已搜索的查询、来源端点、重试/恢复尝试和失败说明。
- 检索修复详情：规划的直接 ID/slug、额外搜索探针、哪些探针成功以及哪些失败。

对于面向用户的工具，应让人工纠正变得容易。合适的控件包括 `choose this candidate`、`search only this candidate`、`copy id/slug`、`show evidence` 和 `mark unresolved`。

## 审查问题

在声称解析器有效之前，请检查：

- 展开步骤是否枚举了每个请求的人物或组织？
- 别名是否按实体分组，还是所有别名都变成了一个全局集合？
- 每个实体是否都有多个候选搜索，包括针对简短/常见别名的上下文搜索？
- 重排序器是否看到了名称之外的证据？
- 当候选项缺失时，重排序前是否存在检索规划器或缺口修复步骤？
- 在声明无匹配之前，是否针对明显的精确别名尝试了直接 ID、slug 和 URL 探针？
- 选中的候选项和次优候选项是否可见？
- 在进行字面查找之前，是否将指令式文本与实体提示分离？
- 部分名称或主要由短名称组成的列表是否强制执行展开，而不是信任直接命中？
- 最终汇总是否区分了预期实体覆盖范围与原始候选项/结果数量？
- 阶段追踪中是否展示了分支扇出、重试、超时、取消和确定性合并行为？
- 用户能否在不重启整个工作流的情况下覆盖错误的第一名候选项？
- 身份、实用性和覆盖范围是否分别衡量？
- 是否允许未解析和有歧义的结果？
- 测试是否包含常见名称误报、稀疏的正确记录、丰富的错误记录、重复记录、精确搜索遗漏，以及通过直接 ID/slug 恢复？
- 来源失败和重试是否足够可见，以便调试不一致的结果？

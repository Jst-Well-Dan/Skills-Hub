# 代码库可维护性护栏

使用此技能来抵消编码模型常见的漂移倾向，避免出现巨型文件、含糊的工具代码堆放处、全局 CSS 无序扩张，以及悄然改变产品行为的清理工作。

## 默认立场

- 除非用户明确说明代码可丢弃，否则将现有应用视为生产应用。
- 重构时保持行为不变。除非错误修复已被明确提出并经过测试，否则不要将大范围清理与行为变更混在一起。
- 保护持久化状态、已存储的模式、localStorage、数据库行和已部署的 API 契约。优先使用兼容性规范化器和迁移，而不是重置。
- 保持每个实现切片都可构建、可审查。每个阶段性重构都应让仓库更便于下一个智能体编辑。

## 代码结构规则

- 保持应用入口点轻量。`main`、`App`、路由文件、布局和顶层样式表应负责编排，而不应承载产品行为。
- 优先使用职责聚焦的模块，而不是巨型文件。在实际可行时，每个源文件的目标应大致为 250-400 LOC。任何超过 500 LOC 的文件都需要有理由，并应考虑拆分。
- 按产品功能和行为拆分，而不是放入含糊的 `utils` 类别中。良好的模块名称应描述领域，例如 `messageActions`、`themeModel`、`ReferenceImagePicker`、`providerRetry` 或 `characterDraftWorkflow`。
- 将纯领域逻辑与 React 渲染及副作用分离。将模式、归约器、规范化器、提示词构建器、重试辅助函数、提供商解析和转换放入可测试的纯模块中。
- 在客户端与服务器的边界处集中管理前端/后端契约和共享的请求/响应类型。
- 避免透传式属性块。组件属性应明确且以行为为导向，但 `message`、`character`、`operation` 或 `theme` 等稳定领域对象除外。
- 将重复的解析、重试、提供商、API 和日志辅助逻辑整合到小型且命名清晰的模块中。

## 前端与 CSS 规则

- 在可用时使用 Tailwind，但保持样式归属于相应功能。
- 将全局 CSS 限制在重置、令牌、浏览器修复和小型共享基础样式。
- 将语义化主题令牌作为唯一事实来源。避免在组件中散布一次性的硬编码调色板。
- 不要让原型页面成长为永久性的上帝组件。对于全新应用，应尽早创建功能文件夹和类型化契约。

## 安全性与可观测性

- 在高风险 UI 区域周围添加结构化客户端日志和可恢复的错误边界。
- 默认不要记录完整的私密内容或用户生成内容。除非有明确意图，否则将包含提示词或大量用户内容的调试数据保留在本地。
- 将布局回归视为产品缺陷。当 UI 变更较为重要时，应检查移动端、桌面端、iPad/平板和超宽屏上的真实截图。

## 测试标准

- 测试应发挥实际价值。优先为纯辅助函数和高价值 E2E 流程编写聚焦测试，而不是大量重复的快照测试。
- 为高风险路径添加或更新测试：迁移、模式兼容性、API 契约、提供商解析、重试行为、归约器和用户可见流程。
- 对于浏览器/E2E 质量检查，应目视检查截图，而不只是确认产物已生成。

## 完成前

检查：

- 没有入口点或路由变成上帝文件。
- 没有源文件在缺乏明确理由或后续拆分计划的情况下超过 500 LOC。
- 没有新增诸如 `utils`、`helpers` 或 `misc` 之类含糊的堆放处来承载产品行为。
- 无需渲染 React 或调用网络即可测试纯逻辑。
- 共享契约经过类型化并集中管理。
- 持久化状态保持兼容。
- CSS 归属于相应功能或基于令牌。
- 高风险行为已由聚焦测试覆盖，或已明确说明验证缺口。
- 在相关情况下，UI 变更已在符合实际使用场景的视口尺寸下完成可视化检查。

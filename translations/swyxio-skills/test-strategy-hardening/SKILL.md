# 测试策略强化

使用此技能将装饰性或脆弱的测试套件转变为可信赖的工程控制手段。优化每分钟带来的信心，而不是追求原始覆盖率数字。

## 工作流程

1. **盘点测试系统**
   - 查明测试命令、框架、e2e 测试工具、fixture、mock、快照、CI 配置、覆盖率工具和运行时间。
   - 按层级对测试进行分类：纯单元测试、契约/模式测试、集成测试、e2e/浏览器测试、视觉测试、冒烟测试、负载/性能测试、迁移/数据测试。
   - 记录当前的通过/失败/不稳定/跳过状态及大致运行时间。

2. **判断测试是否充分发挥作用**
   - 找出能够锁定真实产品契约、历史回归问题、关键用户旅程、外部服务/提供方解析逻辑、迁移、权限和故障模式的测试。
   - 标记宽泛的快照、重复的正常路径、脆弱的实现细节断言、无实际作用的冒烟测试、过度 mock 的测试，以及名称所声称的验证范围超过其实际证明能力的测试。
   - 保留有价值的慢速测试，但如果它们阻碍正常开发，请将其移至显式测试套件中。

3. **编写决策完备的测试计划**
   - 定义绝不能发生回归的关键行为。
   - 选择最小化的测试套件结构：快速本地默认套件、聚焦于变更范围的套件、e2e 黄金路径、发布冒烟测试，以及可选的夜间/重型检查。
   - 在修改行为之前，明确要删除、重写的测试、新增的特征测试和 fixture。

4. **以全绿的小步方式强化**
   - 在重构之前添加特征测试。
   - 用范围更窄、能够因正确原因而失败的测试替换低价值测试。
   - 围绕外部/API/提供方边界构建契约测试。
   - 仅为用户关键旅程添加 e2e/视觉覆盖；当 UI 很重要时，应目视检查截图。
   - 保持 fixture 小巧、命名清晰、结果确定，并贴近其所证明的行为。

5. **报告结果**
   - 汇总已添加、删除、合并、跳过或隔离的测试。
   - 报告优化前后的运行时间以及信心提升之处。
   - 明确列出尚存缺口和下一批目标测试套件。

## 质量标准

- 普通开发者可以频繁运行快速测试套件。
- 关键产品旅程至少有一条高信号回归路径。
- 外部契约会在错误数据到达 UI 或业务逻辑之前明确失败。
- 测试名称清晰、mock 最少、fixture 确定可复现，并提供有用的失败消息。
- 最终报告应回答：“这个测试套件现在能够捕获哪些过去无法发现的缺陷？”

有关审计检查清单，请阅读 [checklist.md](references/checklist.md)。

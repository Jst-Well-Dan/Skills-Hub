# 使用服务将应用产品化

当代码库已经“可以运行”但需要成为持久可靠的产品时，使用此技能。这项工作不只是清理代码；还要让系统易于理解、可操作、可检查、默认安全，在适用场景下 API 优先，并对未来的人类和 AI 维护者友好。

此技能比可维护性重构覆盖的范围更广。如果任务仅涉及结构清理，请使用 `antislop-codebase`；如果任务包括产品就绪、可观测性、审计、安全、API 接口、管理体验和部署验证，请使用此技能。

## 默认技术栈

优先采用代码仓库现有的技术栈。当代码仓库是全新项目或技术选择尚未确定时，建议：

- 应用数据库：优先使用 Postgres；当产品规模适合时，再考虑 MySQL 或 SQLite。
- 身份验证：即使用户登录使用现成库，也应在应用数据库内自行管理产品专属的身份验证状态，包括 API 密钥、角色、审计日志、幂等键、会话/令牌和管理员操作。
- 可观测性：使用 PostHog 处理产品分析、功能标志曝光、管理员操作事件、AI/LLM 追踪、评估事件、漏斗，并在适当场景下使用会话回放。
- 验证：在外部服务/提供方/API 边界使用运行时模式；TypeScript 项目通常使用 Zod，其他技术栈则使用对应的原生方案。
- API 文档：尽可能根据共享模式/契约生成 OpenAPI。
- 审计评审：结束时在本地提供一个静态迁移审计微型站点。

如果代码库已经形成成熟规范，请采用其他工具。不要将此技术栈强加给 Rails/Django/Laravel/Phoenix/etc.；应将这些原则转换为符合本地模式的实现。

## 操作原则

- 在规划前，一切都要以代码仓库事实为依据：当前脚本、部署拓扑、数据库模式、身份验证模型、API 路由、前端状态模型、测试、近期提交和未清理的工作树。
- 除非用户明确要求破坏性变更，否则保留产品现有的可用行为。
- 将 UI 同步/本地状态问题与程序化 API 分离。浏览器端本地优先同步可以与直接访问服务器数据库的无状态 REST/API 处理程序共存。
- 在可行情况下，让每项重要产品操作都通过一个共享操作层执行，然后通过 UI、命令面板、tRPC/内部 RPC、REST/API、作业和 Webhook 暴露这些操作，避免重复业务逻辑。
- 将可观测性视为产品界面，而非事后补充：在适当场景下，用户/管理员应能看到健康状态、交付状态、重试情况、AI 置信度、功能状态和权限结果。
- 让系统对智能体友好：提供有文档的 API、幂等变更操作、批量操作、确定性测试、稳定模式、公开的 `skill.md`/智能体指南以及可供评审的审计输出。

## 工作流程

### 1. 识别产品边界

执行一次非变更式探索：

- 当前 git 状态、分支、近期提交、部署配置、包脚本、环境变量示例、迁移、测试工具和文档。
- 入口点、路由/API 接口、后台作业、Webhook、提供方集成、数据同步层、命令面板/操作界面和管理页面。
- 用于用户、团队/组织、角色、API 密钥、审计日志、Webhook、功能标志、幂等性、作业、通知和提供方令牌的数据库表。
- 安全态势：环境变量验证、密钥存储/加密、身份验证/会话模型、API 密钥模型、速率限制、CORS、CSRF、安全响应头、输入验证以及敏感数据日志记录。
- 可观测性态势：产品事件、服务器日志、请求 ID、错误捕获、追踪、AI/LLM 遥测、仪表板、健康/就绪路由以及用户/管理员可见性。
- 必须保持完整的产品工作流，以及明显仅为占位/演示用途的工作流。

编写计划前，请阅读 [product-principles.md](references/product-principles.md)。

### 2. 编写决策完整的执行计划

编写一份用户可在执行前或执行期间修改的计划。包括：

- 产品目标、明确的非目标、假设和风险态度。
- 当前状态发现，并附带文件/模式引用。
- 工作流：产品 UX、API/操作层、身份验证/权限、审计/合规、安全、可观测性/PostHog、功能标志、管理 UX、测试、文档、部署、迁移审计。
- 子智能体并发图：哪些界面可以独立分析或编辑、哪些文件必须由单一负责人处理，以及合并顺序。
- API 优先计划：REST 或同等的无状态程序化 API、API 密钥身份验证、作用域、批量/筛选端点、幂等性、OpenAPI、公开智能体指南以及命令面板复用。
- 验证关卡：lint/typecheck/unit/build/e2e/visual/deploy smoke、生产环境健康/就绪检查、临时记录清理、日志以及仪表板/事件检查。
- 针对迁移、环境变量变更、提供方变更和用户可见工作流变更的回滚与兼容性计划。

计划应当完整，但不应固化。随着事实变化及时更新。

### 3. 构建安全网

在进行大范围编辑之前：

- 运行现有检查，或记录无法运行的原因。
- 在重构脆弱行为前，为其添加特征测试。
- 在将 UI 决策连接到外部服务/提供方/AI/API 输出之前，为这些输出添加运行时模式。
- 在依赖部署冒烟测试前，添加或验证健康/就绪检查。
- 当前端变更较为重要时，为核心用户/管理界面截取屏幕截图。

### 4. 按产品切片执行

除非代码仓库事实表明应采用其他顺序，否则优先按以下顺序执行：

1. **生产启动和环境变量**：启动时环境变量验证、记录必需的环境变量、健康/就绪路由、部署健康检查，以及能够区分启动/数据库/提供方故障的日志。
2. **共享操作层**：将产品操作提取为类型化函数，使 UI RPC、REST、作业、Webhook 和命令面板均可调用。
3. **API 和智能体接口**：API 密钥身份验证、作用域、速率限制、REST 路由、筛选、批量操作、幂等性、OpenAPI，以及公开的 `/api/v1/skill.md` 或同等智能体指南。
4. **权限和管理 UX**：感知角色的设置/管理页面、成员只读状态、仅管理员可执行的变更操作，以及可见的能力状态。
5. **审计跟踪**：为用户/系统/规则/api 执行者创建仅追加审计条目，在适当场景下记录 IP/用户代理，提供仅管理员可见的审计查看器，并为每项重要变更操作创建审计事件。
6. **安全强化**：令牌加密、密钥处理、安全响应头、输入验证、CORS/CSRF、安全日志记录、SSRF/文件/上传/提供方限制；如果采用多实例部署，则持久化速率限制状态。
7. **可观测性和 PostHog**：服务器端/客户端事件捕获、功能标志曝光、仪表板、AI 生成追踪/评估、错误分类、延迟/成本护栏，以及可见的 Webhook/作业交付状态。
8. **产品 UX 打磨**：用可运行流程替换占位内容，添加长时间运行操作的进度、重试/空状态/错误状态，并完成移动端/窄屏/宽屏截图检查。
9. **测试和部署**：针对每项新契约编写聚焦测试，为关键流程执行 e2e 冒烟测试，完成部署，使用非永久记录执行生产环境冒烟测试，清理记录并最终检查日志。

有关详细执行规则和工作智能体提示词，请阅读 [execution-playbook.md](references/execution-playbook.md)。

### 5. 谨慎使用并发子智能体

如果子智能体可用，可将其用于相互独立的探索、测试编写、UI 评审、API 清点、迁移审计、文档/OpenAPI 评审以及安全/可观测性差距分析。

不要让多个工作智能体编辑相同的热点文件。指定一名集成负责人，负责合并变更、运行完整测试套件、部署和最终清理。

### 6. 按生产环境标准验证

每个切片结束时：

- 针对修改过的代码运行范围较小的测试。
- 在依赖手动 QA 之前补充缺失的测试。
- 部署前运行完整的 lint/typecheck/unit/build。
- 针对已变更的用户/管理流程运行 e2e/浏览器/截图检查。
- 仅在本地关卡通过后部署；除非用户明确接受存在已知风险的部署。
- 使用 `codex-smoke-*` 或同等临时记录对生产环境执行冒烟测试，然后将其清理并确认没有任何残留。
- 检查日志和可观测性仪表板，确认是否存在启动错误、身份验证/API 状态码异常、Webhook 重试、AI/提供方故障以及意外的 4xx/5xx 峰值。

### 7. 以迁移审计微型站点收尾

最后创建一个静态评审微型站点。它应包括：

- 执行摘要和范围。
- 变更前/后的架构图。
- 工作流检查清单和证据。
- 迁移台账和模式变更。
- 安全、权限、审计、API、可观测性和管理 UX 评审。
- 测试/部署证据以及已清理的冒烟测试记录。
- 剩余风险、延期工作和下一步建议切片。

在本地提供该站点并将 URL 交给用户。生成站点前，请阅读 [audit-microsite.md](references/audit-microsite.md)。

## 质量标准

一次成功的执行应使产品具备以下特征：

- 可观测：健康/就绪检查、结构化日志、产品分析，以及管理员可见的交付/作业/AI 状态。
- 可审计：仅追加的审计跟踪，包含执行者类型、资源、操作、元数据和受限查看器。
- 安全：角色关卡、API 密钥作用域、速率限制、加密的令牌/密钥、环境变量验证、安全响应头和安全日志记录。
- 便于产品管理：管理设置、功能标志、文档、公开 API/智能体指南和仪表板。
- 可通过 API 驱动：无状态程序化 API、批量操作/筛选/幂等性、OpenAPI，以及命令面板/操作复用。
- 可由机器人维护：小型类型化模块、共享操作层、聚焦测试、迁移文档、稳定契约和审计微型站点。
